title: "AI Agent & IDE Protection"
description: "Status of kepr's AI agent protection: why protect-agent is disabled and what replaces it."
---

## Status

`kepr protect-agent` is **disabled**. Running it prints an explanation and
exits without starting the agent.

The original command started the harness (Claude Code, Cursor, Windsurf,
Aider) with the key in a sealed `memfd` and only `KEPR_FD_<KEY>=3` in the
environment. That had two problems:

1. **No harness reads `KEPR_FD_*`.** They read `ANTHROPIC_API_KEY`,
   `OPENAI_API_KEY` and so on, so the agent started without credentials.
2. **The memfd was inherited by everything the agent ran.** Any shell
   command the agent executed could print the key with `cat <&3`.

## What replaces it

Sealed agent sessions: `kepr agent run`. The agent gets a worthless
placeholder, a local proxy (`kepr-gate`) swaps in the real key on the wire
toward that key's own API host, and the agent runs in a sandbox whose only
network route is the proxy. The agent can use the key but never hold it.
See the [Keeper parity & agent vault plan](/docs/agent-vault-plan).

## Until then

If you accept that the agent and every tool it runs can read the keys:

```bash
kepr exec --env ANTHROPIC_API_KEY -- claude
```

This keeps keys out of shell history and dotfiles, but they are visible in
the agent's environment and `/proc/<pid>/environ`.

`kepr exec --memfd` remains supported for your **own** programs that read
the fd once and close it before starting subprocesses. Don't use it for
agents or shells.

## Auditing agent access

```bash
journalctl -t kepr-daemon KEPR_OP=get
```
