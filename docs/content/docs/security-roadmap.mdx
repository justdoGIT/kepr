# Security Extension Roadmap

This page separates implemented master-key sealers from future alternatives and
qualification work. The current daemon uses AES-256-GCM for credential files
and Argon2id + AES-256-GCM for a passphrase-protected master key. Source presence
is not proof of native-platform or hardware qualification.

Optional integrations must not silently become dependencies of the local
user-mode baseline. Explicitly selected TPM, token, key-service or desktop
backends must fail closed when unavailable; they must not silently become an
unprotected key file. The ordinary local user-mode sealer remains a deliberate
owner-only key file until passphrase protection is configured.

`daemon_seal/startup.rs` refuses new-key generation when the master-key file is
missing but the credential directory is non-empty and no recovery key is
enrolled. Previously enrolled recovery permits locked startup and explicit
recovery instead. A restart cannot repair wrong-key/damaged ciphertext; do not
delete keys or reset the store to bypass that boundary.

## 1. Hardware-backed master-key wrapping

### Goal

Prevent an attacker who steals the credential directory and the protected
master-key envelope from recovering the master key without possession of the
machine's hardware or an enrolled authenticator.

### TPM2 backend

The daemon already has source implementations in `daemon_seal/tpm*.rs` for
TPM2 PIN/counter sealing through tpm2-tools, plus a systemd-creds host/TPM
selection path. Native TPM availability, PCR changes, recovery and hardware
qualification remain deployment-specific. The reference documents the current
`KEPR_MASTER_KEY_SEAL` options; this roadmap does not replace them.

A direct Rust TSS backend behind an optional `tpm2` feature is a future
alternative, not the present implementation. It should:

- Generate a TPM-sealed wrapping key or use a TPM-protected sealing object.
- Bind unsealing to an explicit PCR policy, documented per distribution.
- Keep the random 256-bit kepr master key as the payload; never derive it
  directly from PCR values.
- Fail closed when the TPM is unavailable, reset, or the PCR policy changes.
- Require an enrolled recovery mechanism before changing the boot-bound seal;
  do not require plaintext master-key export.
- Keep the explicit default user-mode local-file sealer unchanged when the
  alternative feature is disabled.
- Update the systemd unit's `PrivateDevices`, device allow-list, and
  capability policy only for TPM-enabled deployments.

Candidate implementation choices:

- Prefer a maintained Rust TSS binding such as `tss-esapi`.
- Avoid invoking `tpm2_*` command-line tools from the daemon.
- Pin the TSS dependency and document supported TPM/TSS versions.

Required tests:

- Mock sealer round trips.
- PCR-policy mismatch fails closed.
- TPM absence does not silently fall back to plaintext key storage.
- Restart and recovery behavior after TPM lockout.

### FIDO2 wrapping or unlock

Two existing mechanisms must be kept distinct: per-credential FIDO2 assertion
gating and `kepr lock --fido2`, which already combines the passphrase-derived
key with an authenticator `hmac-secret` result to wrap the master key. The
latter uses fido2-tools; it is not merely a public-key signature. See
[passphrase plus security key](/docs/reference/features#passphrase-plus-security-key).
Native authenticator/hardware qualification is not established here.

A future direct-transport or multi-authenticator master-key mode should:

- Use a standard WebAuthn/CTAP2 resident or discoverable credential flow.
- Derive only a key-encryption key from a verified assertion response.
- Include the RP ID, credential ID, user handle, and version in authenticated
  metadata.
- Require user presence and, where configured, user verification.
- Never treat a public-key signature alone as a password-equivalent secret.
- Support multiple enrolled authenticators and an explicit recovery policy.
- Rate-limit failed ceremonies and invalidate challenges after one use.

Direct authenticator transport would require a maintained library and new
qualification. Do not confuse the per-credential `KEPR_FIDO2_HELPER` assertion
boundary with the existing `lock --fido2` master-key wrapping flow.

## 2. Desktop keyring backends

### Goal

Use an already-authenticated desktop session to protect the kepr master key,
without making desktop services a requirement for servers or headless hosts.

The core `KeyringBackend` API currently provides Linux's raw, permissions-
protected local envelope. Its macOS and Windows backends explicitly report
unavailable and refuse sealing/unsealing, including legacy raw envelopes;
unsupported platforms do not inherit Linux behavior. These placeholders must
not be described as native Keychain or DPAPI protection.

The daemon has a *separate* opt-in macOS Keychain sealer in
`src/daemon_seal/keychain.rs`; it is not the core trait implementation and has
no native CI qualification here. IPC identity, sandbox, networking, signing,
installation and rollback remain separate macOS/Windows work.

Kepr's existing `secret-service run` is a Secret Service **server** backed by
its vault. That does not implement the external desktop keyring **sealer**
proposals below.

### Secret Service / GNOME Keyring

Add a feature-gated `SecretServiceSealer`:

- Use a maintained D-Bus client rather than the `secret-tool` executable.
- Store one random master-key blob under a stable application/service label.
- Authenticate the item as non-exportable where the service supports it.
- Bind the item to the kepr user and deployment mode.
- Return a clear locked-session error when no Secret Service is available.
- Never fall back from an unavailable keyring to an unprotected file silently.

### KWallet

Add a feature-gated `KWalletSealer` with equivalent semantics:

- Use the KWallet D-Bus API.
- Store only the wrapped random master key, not individual plaintext
  credentials.
- Handle closed wallets and wallet reauthentication explicitly.
- Preserve the same lock/unlock protocol used by the Argon2id backend.

### Backend selection

Future proposal only; these `KEPR_MASTER_KEY_BACKEND` settings are not implemented:

```text
KEPR_MASTER_KEY_BACKEND=local       # dependency-free default
KEPR_MASTER_KEY_BACKEND=argon2      # password envelope
KEPR_MASTER_KEY_BACKEND=secret-service
KEPR_MASTER_KEY_BACKEND=kwallet
KEPR_MASTER_KEY_BACKEND=tpm2
```

Selection must be visible through `kepr status`, recorded without secrets in
the audit log, and rejected when the requested backend is unavailable.
There must be no silent downgrade from TPM2, FIDO2, Secret Service, or KWallet
to local plaintext key storage.
Current daemon selection uses `KEPR_MASTER_KEY_SEAL`, documented in the
[feature reference](/docs/reference/features#master-key-protection). Keep any
future interface explicit and migrate callers rather than implying these
proposed names already work.

## 3. Dependency and supply-chain maintenance

- Retain the implemented `release.yml` exact annotated-tag commit gate and
  dependency audit/deny jobs; execution and repository protections still need
  candidate-specific evidence. Current qualification test/lint commands omit
  `--release`; use release-mode acceptance before claiming release qualification.
- Review cryptography and D-Bus/TSS dependencies separately from ordinary
  application dependencies.
- Keep `Cargo.lock` committed and review lockfile changes for transitive crypto
  updates.
- Keep the release workflow's SBOM, isolated build and signing stages, and
  qualify their output, provenance and rollback against the exact candidate.
- Add reproducibility evidence and native platform artifact/signing qualification.
- Record the Rust toolchain, target triple, and enabled security features in
  release metadata.
- Add a scheduled dependency update job that opens reviewable pull requests;
  do not auto-merge cryptography updates.
- Re-run the threat model whenever the key-sealing backend or daemon privilege
  boundary changes.

## Acceptance criteria for future work

A backend is ready only when it has:

1. An explicit opt-in feature and configuration path.
2. No plaintext master-key fallback on backend failure.
3. Recovery and re-enrollment documentation.
4. Locked, unlocked, restart, wrong-secret, and unavailable-backend tests.
5. Permission and process-boundary review for Linux distributions that package
   it.
6. A documented threat model describing what root and same-user malware can
   still do.

Until a proposed backend meets those criteria, an explicit baseline is:

```text
Argon2id password unlock
+ AES-256-GCM master-key envelope
+ AES-256-GCM credential encryption
+ SO_PEERCRED validation
+ owner-only filesystem permissions
+ daemon rate limiting
```

This is a configuration target, not a claim that every install has enabled it
or passed qualification. Local-only agent routing and device-wide offline
enforcement remain unavailable; private-cloud masking does not provide anonymity.
No fresh full-suite, native-platform or hardware pass is claimed by this page.
