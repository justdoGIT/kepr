## The idea

Enter a key once in your own terminal. A protected agent can **use** it without
receiving its plaintext value:

- `kepr agent add` stores a **sealed**, destination-bound credential;
  plaintext retrieval/export APIs, including `kepr get`, refuse it;
- the agent receives a session **placeholder** (`kepr-ph-…`) and a local
  gate URL, not the real key;
- the daemon releases the credential only to the gate for an authorized
  binding, and the gate injects it toward that destination over TLS.

This protects sessions launched with `kepr agent run`; installing a plugin
alone does not protect an existing shell, all applications, or the device.
If a session was started normally, relaunch it with `kepr agent run <harness>`.

## Quick start

```bash
kepr agent add ANTHROPIC_API_KEY --for anthropic
kepr agent run claude
```

Run `add` yourself, outside the agent. At `Paste … (input hidden):`, type or
paste the value and press Enter. Terminal echo is disabled: no characters or
asterisks appear. Do not put the value in chat, command arguments, shell
exports, or harness configuration files.

Use the exact provider binding for the destination you intend. For example,
`--for openai` binds `api.openai.com:443`, `--for xai` binds `api.x.ai:443`,
`--for agentrouter` binds `agentrouter.org:443`, and `--for selora` binds
`api.selora.lol:443`. A reseller's OpenAI-compatible API is not OpenAI's host.
For a custom HTTPS endpoint, an explicit binding is possible:

```bash
kepr agent add WORK_API_KEY --for api.example.com:443:bearer
```

Omitting `--for` uses a recognizable prefix or variable-name hint; a bare
`sk-` prefix is ambiguous. Explicit binding avoids guessing. Check the names
and bound hosts with `kepr agent ls` (no values). A binding is not proof that
the provider accepts the credential or offers a particular model.
Custom bindings must also use a route supported by the selected launch
policy; binding an arbitrary host does not add private-cloud inspection for it.

Model-provider presets include anthropic, openai, xai, google, mistral,
deepseek, groq, openrouter, agentrouter, selora, fireworks, moonshot,
venice, and Cloudflare AI Gateway.

### Cloudflare AI Gateway

Cloudflare needs a token, an account ID, and a gateway ID. If the three
entries already exist in kepr as `CLOUDFLARE_AI_GATEWAY_API_KEY`,
`CLOUDFLARE_ACCOUNT_ID`, and `CLOUDFLARE_GATEWAY_ID`, convert them without
printing or exporting any value:

```bash
kepr agent add-cloudflare
kepr agent install omp
kepr agent run omp
```

`add-cloudflare` validates all three entries inside the daemon, then replaces
the token entry with a sealed structured login bound only to
`gateway.ai.cloudflare.com:443`. The account and gateway source entries are
left unchanged. Missing, malformed, expired, or incompatible protected
entries are refused without a partial conversion; the command never returns
their values. Existing policies are preserved or conversion fails closed.

The OMP plugin directs Cloudflare requests to the session gate. OMP sees
only `KEPR_PH_CLOUDFLARE`; the gate supplies the account/gateway URL and the
`cf-aig-authorization` header. Do not export the real API token, bind it to
OpenAI, or use `!kepr get` as the protected session's credential source.
Normal use does not need Cloudflare account/gateway environment variables.
Cloudflare token permissions, configured gateway provider credentials, and
upstream model availability still apply.

The gateway uses Cloudflare's [documented native and OpenAI-compatible
endpoints](https://developers.cloudflare.com/ai-gateway/usage/chat-completion/).


## Already have keys in `.env` or your shell profile?

```bash
kepr agent adopt                 # lists keys found in .env, .envrc, ~/.bashrc, ~/.zshrc …
kepr agent adopt --yes           # imports them as sealed keys
kepr agent adopt --yes --remove  # …and deletes the plaintext lines
```

Values are never printed. A name found with different values in two
places, or already stored in kepr, is skipped rather than overwritten.
`--remove` keeps no plaintext backup, on purpose.

Without FILE arguments, adopt also reads the config files where agent
harnesses save keys, since the agent can read those inside its session and
a harness may use a key there instead of the gate's placeholder:
`~/.codex/auth.json` (`OPENAI_API_KEY`), `~/.grok/user-settings.json`
(grok-cli's `apiKey`), `~/.aider.conf.yml` (`openai-api-key`,
`anthropic-api-key`, `api-key` items) and `~/.config/omp/agent/models.yml`
(`apiKey`). These default adoption locations do not follow every custom
`CODEX_HOME`, `PI_CODING_AGENT_DIR`, or XDG location; supply explicit FILE
arguments for those. These JSON/YAML files are never rewritten: with
`--remove`, kepr tells you to delete the key by hand. Variable names and
references (`KEPR_PH_ANTHROPIC`, `${VAR}`, `{env:VAR}`) are not keys and are
left alone.

It also reads your shell history: `$HISTFILE` (or `~/.bash_history`),
`~/.zsh_history` and `${XDG_DATA_HOME:-~/.local/share}/fish/fish_history`.
A key typed as `export XAI_API_KEY=xai-…`, `set -gx OPENAI_API_KEY sk-…` or
`OPENAI_API_KEY=sk-… python app.py` is found; one read from elsewhere
(`$(pass show …)`, `$OTHER`) is not a key. With `--remove` the whole
history entry is deleted and the other lines stay byte-identical. Open
shells keep their history in memory and may write the line back when they
exit, so run `history -c` in them or close them. A history file that is not
valid UTF-8 (zsh stores non-ASCII bytes its own way) is read but never
rewritten; kepr names the lines to delete by hand. Keys passed other ways,
such as `curl -H "Authorization: Bearer …"`, are left to `kepr scan
~/.bash_history`.

`grok` means **Grok Build**; `grok-cli` means the separate community CLI.

`kepr agent install omp|grok|opencode` updates the harness integration,

are **dynamic per session**; do not hard-code port 7878. OMP's plugin uses
`KEPR_GATE_URL`; Grok Build receives its session base URL; opencode uses
`{env:KEPR_GATE_URL}/anthropic/v1` and `{env:KEPR_PH_ANTHROPIC}`. An explicit
`--port N` is an opt-in fixed-port configuration, not the default.

Host configuration paths are:

- OMP: `$PI_CODING_AGENT_DIR/models.yml`, otherwise
  `${XDG_CONFIG_HOME:-~/.config}/omp/agent/models.yml` (absolute XDG path);
- Grok Build: `~/.grok/config.toml`;
- opencode: `${XDG_CONFIG_HOME:-~/.config}/opencode/opencode.json`.

Protected workspace launches use a generated private home rather than
copying host authentication, history, or configuration. OMP gets an embedded
kepr extension and an empty generated `models.yml`; do not assume custom
host model definitions or other installed plugins are copied into it.
In configurations the OMP extension does load, API-key references are matched
to sealed credentials by name and exact HTTPS host. Missing bindings make
that provider unavailable, not a fallback to `kepr get` or direct networking.

The reviewed OpenAI-compatible OMP defaults include Fireworks
(`https://api.fireworks.ai/inference/v1`), Moonshot CN
(`https://api.moonshot.cn/v1`), and Venice
(`https://api.venice.ai/api/v1`). Their exact hosts and chat paths are
allowlisted for the private-cloud adapter; unsupported endpoints, provider
extensions, media, and opaque state remain refused. Model availability and
live provider behavior are not tested by these bindings.

### Provider credential lifecycle qualification

OMP routes do not retrieve API keys from providers. Operators add the sealed
credential to kepr; the gate only resolves it for the exact bound host. The
reviewed provider control planes expose the following lifecycle capabilities:

| Provider | Official lifecycle evidence | Kepr automation |
| --- | --- | --- |
| OpenAI | [organization admin-key create](https://developers.openai.com/api/reference/resources/admin/subresources/api-keys/methods/create) and [delete](https://developers.openai.com/api/reference/resources/admin/subresources/api-keys/methods/delete) | `rotate --provider openai --bootstrap ADMIN_KEY` |
| OpenRouter | [management-key create](https://openrouter.ai/docs/api/api-reference/api-keys/create-a-new-api-key) and [delete](https://openrouter.ai/docs/api/api-reference/api-keys/delete-an-api-key) | `rotate --provider openrouter --bootstrap MANAGEMENT_KEY` |
| Venice | [Admin-key management](https://docs.venice.ai/guides/getting-started/managing-api-keys), including create and revoke | `rotate --provider venice --bootstrap ADMIN_KEY` |
| Fireworks | [control-plane API-key create](https://docs.fireworks.ai/api-reference/create-api-key) requires account and user identifiers; it is not a generic OMP key-only flow | Manual lifecycle; no automatic provider rotator |
| Moonshot CN | [official quickstart](https://platform.moonshot.cn/docs/guide/start-using-kimi-api) documents dashboard-created API keys and inference use, not an authenticated key-management endpoint | Manual lifecycle; no automatic provider rotator |

For automated rotation, `ADMIN_KEY`/`MANAGEMENT_KEY` is a separate sealed
credential. The daemon sends only credential names to a rotation gate; the gate
creates, validates, commits, and cleans up failed replacements without returning
secret values to the CLI. Provider model availability and live account
permissions still require a separate operator check.

Codex reads the selected provider from `$CODEX_HOME/config.toml` (default
`~/.codex/config.toml`) before entering the private home. A selected
`--profile NAME` also loads `NAME.config.toml` from that directory. Supported
API credentials are:

| Selected API | `env_key` | Required HTTPS host |
| --- | --- | --- |
| OpenAI | `OPENAI_API_KEY` (default for provider `openai`) | `api.openai.com` |
| AgentRouter | `AGENTROUTER_API_KEY` | `agentrouter.org` |
| Selora | `SELORA_API_KEY` | `api.selora.lol` |

AgentRouter and Selora require a matching HTTPS `base_url` and must not set
`requires_openai_auth = true`. Store only the environment-variable name in
`env_key`, never the key. Kepr grants the selected provider's sealed credential
and pins CLI overrides to the dynamic gate with ephemeral auth storage:

```bash
kepr agent add SELORA_API_KEY --for selora
kepr agent run codex -- codex --profile selora
```

This assumes that non-secret Selora provider/profile configuration already
exists. Arguments after `--` include the **executable** (`codex`), not just
its flags. Cached `auth.json` files and their symlink targets are masked;
inline credentials and alternate authentication helpers are refused. Unlocking
the vault does not replace a missing selected-provider credential or binding.

`kepr agent install claude` adds kepr's
guidance for the model as a Claude Code skill
(`~/.claude/skills/kepr/SKILL.md`, or under `$CLAUDE_CONFIG_DIR`), and
`kepr agent install codex` adds it as a marked block in Codex's global
`~/.codex/AGENTS.md` (or under `$CODEX_HOME`), leaving the rest of the file
alone. It is the same text as Grok Build's skill: keys are placeholders,
never put one in a file, command or commit, use `kepr mcp`'s `call_api`,
and run `kepr leaked NAME` when a real key shows up.

### Plugins for omp and Grok Build

`kepr agent install omp|grok` installs a plugin that makes the harness
itself keep secrets out of the conversation. Both plugins ask
`kepr hook` for their decisions, so the rules are the same in each.

| What it does | omp | Grok Build |
| --- | --- | --- |
| Sends supported, bound provider calls through the session gate with placeholders | yes (credential-name and exact-host matching) | via session base URL |
| Refuses tool calls that would print a stored value (`kepr get`, `env`, `exec`, `totp`, `inject`, `copy`, `record`, `recovery-kit`, `share`, `sync-push`) | yes | yes |
| Refuses tool calls that contain a real key (a command, or file content) | yes | yes |
| Refuses a prompt with a pasted key, before it reaches the model | interactive sessions | yes |
| Removes keys from user messages before every model request | yes (covers `omp -p` and RPC) | – |
| Tells the model that its keys are placeholders | system prompt | a `kepr` skill |
| `kepr mcp` as an MCP server | – | yes |
| Status command | `/kepr` | – |

- **Where they go:** the OMP extension is installed under
  `$PI_CODING_AGENT_DIR/extensions/kepr/`, otherwise
  `${XDG_CONFIG_HOME:-~/.config}/omp/agent/extensions/kepr/`. The Grok Build
  plugin's source goes into `~/.local/share/kepr/plugins/grok/kepr/`, and kepr
  registers it with `grok plugin install … --trust`, or updates it after an
  upgrade. If `grok` is absent from `PATH`, kepr prints the registration command.
- **Protection boundary:** hooks help guard conversation/tool traffic, but
  they are not a replacement for the gate and required isolation. Protected
  launches generate a private home; host-installed Grok Build plugins are
  not copied there. Do not treat a successful host plugin install as proof
  that hooks are active inside that private home.
- **Qualification:** these integration paths describe source behavior, not
  a current release certification or live-provider/model availability test.

Pass your own command line after `--`:

```bash
kepr agent run codex -- codex --profile selora
```

Any real key already exported in your shell (for example
`ANTHROPIC_API_KEY=sk-ant-…`) is removed from the agent's environment.

### Typing the harness's own command: `kepr agent shim`

```bash
kepr agent shim claude            # writes ~/.local/share/kepr/shims/claude
export PATH="$HOME/.local/share/kepr/shims:$PATH"   # in your shell profile
claude                            # now runs: kepr agent run claude -- /path/to/claude
```

The shim is a four-line `sh` script holding only paths: the real binary
(the first one on `PATH` outside the shim directory) and `kepr`. Inside a
`kepr agent run` session it starts the real binary directly, so sessions
never nest. The default directory is
`${XDG_DATA_HOME:-~/.local/share}/kepr/shims`, never `~/.local/bin`, where
Claude Code, for one, installs its real binary; `--dir DIR` picks another.
kepr never replaces or removes a file that isn't one of its shims:
`kepr agent shim claude --remove` (or deleting the file) undoes it.

## The sandbox

Protected launches require Linux user, mount, PID, and network namespace
isolation and a private workspace. If required isolation is unavailable,
launch fails closed; it does **not** silently run on the host.

- The credential store, daemon state/socket, desktop keyring sockets, and
  cached Codex authentication are hidden from the harness.
- The harness runs with a generated private home, no capabilities,
  `no_new_privs`, and a seccomp filter restricting process inspection and
  privileged operations.
- Gate-only network access is the default (`--isolate-net` is already on).
  Arbitrary direct networking and package downloads are not available.
- Disabling Landlock or allowing the desktop session bus is rejected in
  protected mode; do not use isolation overrides to repair a failed launch.

```bash
kepr agent run claude
kepr agent run claude --security-preset private-cloud
kepr doctor
```

`private-cloud` applies bounded local pattern masking before supported cloud
requests. It is not anonymity, complete sensitive-data detection, or a claim
of zero external disclosure. `local-only` currently refuses launch before a
cloud gate starts because local inference routing is not implemented.

`--compatibility` is an explicit **security downgrade**: it disables privacy
filtering and required isolation and runs in the real working folder without
an automatic workspace snapshot. It can fall back without a sandbox; only
that mode accepts `--no-sandbox` (Codex still refuses it). Do not choose it as
a workaround for a lock, authentication, binding, or isolation failure.
Native macOS/Windows protected launch enforcement is not qualified by these
Linux instructions.

## What the agent can change: the workspace snapshot

A protected `kepr agent run` does not run in your real folder. Before the
harness starts, kepr copies the current directory (or `--workspace PATH`)
into a private session, mounts that copy as the harness's working directory
under the user and mount namespaces, and leaves the host tree untouched.
When the harness exits, every change stays in the session:

```bash
kepr agent run claude                    # snapshot the current folder
kepr agent run claude --workspace ~/src/app
kepr workspace review <SESSION>          # diff, patch file, approval digest
kepr workspace export <SESSION> --approve <DIGEST> --output ~/src/app-reviewed
```

Run review/export from your operator terminal, not from inside the agent.
`review` writes a patch and prints a digest that expires after an hour and
binds the captured file contents and modes. Inspect that patch before using
the digest. Export refuses changed/expired approvals and an existing
destination; the approval is consumed once. The new bundle contains changed
files under `files/` and `manifest.json` (including deletions); it does not
modify your original tree or automatically apply deletions.
`--workspace-session SESSION` selects a previously **prepared, not yet run**
session instead of creating another snapshot. It does not resume a finished
harness session. Protected source-tree snapshots exclude credential/config
paths and links; path-unsafe, binary, over-limit, control-character and
unscreenable files are omitted and counted in the preparation result. Explicit
`--file` inputs remain UTF-8 text only and fail closed when they cannot be
screened.

## Asking before a key is used

```bash
kepr agent add ANTHROPIC_API_KEY --for anthropic --requires-consent
```

Before the daemon hands such a key to a gate, polkit asks you to approve
the agent process (the desktop's authentication dialog). No answer within
60 seconds, or no polkit agent, means no. One approval covers the gate's
cache window (5 minutes, or until the key changes).

## MCP: `kepr mcp`

For agent platforms that talk to tools over MCP, `kepr mcp` is a stdio MCP
server with these tools:

- `list_secrets`: names of your sealed keys and the hosts they're bound to;
- `call_api`: an HTTP call to a provider API (`provider`, `method`, `path`,
  optional `body` and `headers`). The call goes through a gate session, so
  the key is injected by kepr, prompt DLP applies, and the model never sees
  the key.
- `db_query`: one SQL statement (`target`, `sql`) on a sealed PostgreSQL
  login (`kepr agent add-db`), through the gate's database proxy: the gate
  logs in, the model never gets the password.
- `ssh_run`: a command (`host`, `cmd`) over ssh, signed with a key that
  stays in the daemon (`kepr ssh generate`). Only for hosts you list with
  `--ssh`; ssh runs in batch mode, so the host must be in `known_hosts`.

```bash
kepr mcp --read-only --ssh deploy@web1 \
  --context "APP_DB=Analytics replica: tables orders, users" \
  --context "deploy@web1=Ubuntu 24.04, app in /srv/app"
```

`--read-only` runs every statement read-only (`SET
default_transaction_read_only = on`, inside a `READ ONLY` transaction): a
guard against mistakes, not a permission boundary, so give the login a
read-only role for that. `--context` attaches an `ai_context` note that is
returned with each result for that target.

No tool returns a secret value, and key-shaped strings in results are
masked. Example client entry:

```json
{ "mcpServers": { "kepr": { "command": "kepr", "args": ["mcp"] } } }
```

## Tools the agent runs: `gh`, `curl`, SDKs

The protected default only enables inspected model-provider routes; it does
not automatically grant arbitrary tool credentials. The general HTTPS-proxy,
database, and Google Cloud capabilities below are separate routes, not a
promise that `kepr agent run claude` grants them in protected private-cloud
mode. Uninspected database/tunnel requests are refused there. Do not disable
protection merely to make a tool work.

Where an explicitly selected non-private-cloud policy permits an HTTPS tool
route, the gate acts as its proxy. For example, store a GitHub token privately:

```bash
kepr agent add GITHUB_TOKEN --for github
```

- **Bound hosts:** for a host a sealed key is bound to (here
  `api.github.com`), the gate terminates TLS with a CA made for this
  session. It swaps the placeholder for the real key and re-encrypts to the
  real host, trusting only its compiled-in roots.
- **The CA:** it lives only in the gate's memory, lasts 24 hours, and is
  name-constrained to the session's bound hosts, so its key can't sign a
  certificate for any other site.
- **How tools trust it:** the harness gets the CA through `SSL_CERT_FILE`,
  `REQUESTS_CA_BUNDLE`, `CURL_CA_BUNDLE`, `GIT_SSL_CAINFO` and
  `NODE_EXTRA_CA_CERTS`. Those point to the system bundle plus the session
  CA, so other HTTPS keeps working.
- **Real tokens in your shell:** a `GH_TOKEN` or `GITHUB_TOKEN` you exported
  is replaced by the placeholder and never reaches the agent.
- **Other hosts:** tunnelling is available only when network isolation is
  explicitly not required. Protected launches deny unbound destinations.

### Google Cloud: `kepr gcp add`

A long-lived Google credential never reaches the session. Store a
service-account key, or the `authorized_user` file that
`gcloud auth application-default login` writes, sealed:

```bash
kepr gcp add GCP_DEPLOY --key-file sa.json
kepr gcp add GCP_ME --key-file ~/.config/gcloud/application_default_credentials.json \
  --impersonate deploy@my-proj.iam.gserviceaccount.com
# A stored login is not automatically granted to protected model sessions.
```

- **Bindings:** `www.googleapis.com` and the common `*.googleapis.com`
  services gcloud calls, with the scope `cloud-platform` unless you pass
  `--scope URL` (up to 8).
- **Tokens:** the gate mints a 1-hour access token per session, from a
  signed service-account JWT or the refresh token, then for the
  `--impersonate` service account if you named one. It renews the token 5
  minutes before it expires. Tokens come only from
  `oauth2.googleapis.com`; a `token_uri` in the file is ignored.
- **Errors** carry the HTTP status only, never Google's reply.

## Databases

```bash
kepr agent add-db PROD --url postgres://app@db.internal:5432/prod   # asks for the password
# A stored database route is not automatically granted to protected model sessions.
```

- **What the agent gets:** `DATABASE_URL` and `PGHOST`/`PGPORT`/`PGUSER`/
  `PGPASSWORD`/`PGDATABASE`, pointing at a local gate port, with the
  session placeholder as the password. With several databases, each one gets
  `KEPR_DB_<NAME>_URL`.
- **What the gate does:** it checks the placeholder, then logs in to the
  real server with the sealed login using SCRAM-SHA-256 or cleartext (MD5 is
  refused). From then on it relays the session unchanged.
- **TLS to the server:** it's verified against public roots by default.
  Use `--ca FILE` for a managed database's own CA; do not disable TLS as an
  authentication troubleshooting workaround.
- **The login itself:** the user name, database and password stay sealed,
  and `kepr get PROD` is refused. The agent can run queries as that user but
  can't take the password anywhere.

### Rotating the password

```bash
kepr agent rotate-db PROD
```

- **How it works:** the daemon adds a random 48-character password to the
  sealed record as pending. A gate started for this database logs in with
  the current password and runs `ALTER ROLE CURRENT_USER PASSWORD` with a
  SCRAM verifier, so the new password never appears in SQL text or server
  logs. The daemon then makes the pending password the current one.
- **Who sees it:** nobody. Neither the old nor the new password reaches
  the CLI, the terminal or the agent.
- **If it's interrupted:** the pending password is kept. Running the
  command again finishes the job, even when the server already has the new
  password. `kepr agent rotate-db PROD --abort` drops a pending password.
- **What the role needs:** it must be allowed to change its own password,
  which PostgreSQL allows by default.

## Spending and rate limits

```bash
kepr agent run claude --max-requests 500 --max-tokens 2000000 --rate 30
```

The gate enforces these per session:

- `--max-requests`: total forwarded requests.
- `--max-tokens`: total tokens, counted from the provider's own `usage`
  fields as responses stream back. A response that crosses the limit
  completes; the next request is refused.
- `--rate`: requests per rolling minute.

When a cap is reached, the agent gets `403` with error type `kepr_limit` and
a message naming the limit. That stops it rather than leaving it to retry.
The rate limit answers `429` with `Retry-After`. Refusals appear in the gate
journal as `"blocked":"limit"`.

## Emergency stop

```bash
kepr panic
```

Stops every running gate for your user (their cached keys die with them)
and, if the store is passphrase-protected, locks it until `kepr unlock`.

The user-mode daemon also does this by itself when the machine suspends or
the screen locks. That keeps keys out of RAM while a laptop sleeps. It
follows logind through `gdbus`; `kepr doctor` reports whether it can. Turn
it off with `KEPR_LOCK_ON_SLEEP=0`.

## When a key leaks

```bash
kepr leaked ANTHROPIC_API_KEY
```

This command:

1. Stops every agent session for your user, along with their cached copies.
2. Deletes the credential and its saved history.
3. Records a `leak-incident` entry in the audit chain.
4. Tells you where to revoke the key at the provider; kepr can't revoke it
   for you.

Then store the new key with `kepr agent add NAME --for PROVIDER`. To see where the old one was
used: `journalctl -t kepr-daemon KEPR_NAME=ANTHROPIC_API_KEY`, or
`kepr usage`.

## SSH keys the agent can use but never read

```bash
kepr ssh generate DEPLOY_KEY            # or: kepr ssh import DEPLOY_KEY ~/.ssh/id_ed25519
kepr ssh list                           # authorized_keys lines to install on servers
eval "$(kepr ssh-agent)"                # sets SSH_AUTH_SOCK for ssh and git
```

The Ed25519 private key stays in the daemon. `kepr get` refuses it, and the
agent socket only lists keys and signs. Requests to add, export or remove
keys fail. Add `--requires-consent` to get a prompt before each signature.
Encrypted key files must be decrypted (on a copy) before import.

## What the gate enforces

- **Placeholder check:** a request without this session's placeholder gets
  `401`. Placeholders are HMAC-bound to one session and useless elsewhere.
- **Destination binding:** the daemon releases a sealed key to the gate only
  for a host in its bindings, and the gate only talks to the provider's real
  host over TLS with compiled-in public roots (it ignores proxy and CA
  settings from the environment, which the agent could control).
- **Prompt DLP:** a request whose body contains a stored key (or something
  shaped like an API key) is **blocked** with `403`, and the agent is told
  why, e.g. `kepr blocked this request: it contains the stored secret
  ANTHROPIC_API_KEY. Remove it and retry.` Nothing is redacted silently.
- **Lifetime:** the gate exits, and wipes its cache, when the agent exits.
  Any `set`, `delete` or expiry in the store invalidates cached keys at
  once, so `kepr agent revoke` takes effect immediately.
- **Journal:** sanitized metadata-only request records include provider,
  method, templated path without query, status, sizes, and timing, never
  headers or bodies. Inspected calls also persist intent/decision metadata
  before upstream execution and outcome metadata afterward; an unknown
  outcome is not proof that an external action did not happen.

## Managing keys

```bash
kepr agent ls                        # sealed keys and their bound hosts
kepr agent revoke ANTHROPIC_API_KEY  # delete (asks for confirmation)
kepr history ANTHROPIC_API_KEY       # previous values kept (no values shown)
kepr restore ANTHROPIC_API_KEY --version 1   # undo the last change
kepr usage --days 30                 # uses, refusals, last use; never-used keys
```

A sealed key cannot be unsealed. To replace its value or correct its provider
binding, privately run `kepr agent add NAME --for PROVIDER` again. Other
updates (`kepr set`, `kepr rotate --hook`, `kepr sync-pull`, or an import with
`--overwrite`) preserve its sealed status, bindings, and consent requirement;
they are not plaintext-retrieval workarounds.

### Distinguishing failures

| Symptom | Meaning and safe response |
| --- | --- |
| `get` refuses a sealed credential | Expected write-only behavior. Use `kepr agent run`; do not export it or change it to a readable entry. |
| Vault is locked | Unlock privately with `kepr unlock` (or an already-enrolled recovery method when indicated). Sealing remains in force after unlocking. |
| Missing selected credential / no matching binding | Check `kepr agent ls` and the configured provider host and `env_key`. Privately add/re-add the correct credential with an exact `--for` binding; do not substitute another provider's key. |
| Ciphertext decryption/authentication failure | Not a sealed-key refusal or ordinary lock. Preserve the store and matching master-key/recovery material; verify the intended daemon/profile and restore a known-good matching backup or use an enrolled recovery mechanism. Restarting cannot repair authenticated ciphertext, and deleting/regenerating the master key can orphan the store. |
| Cannot connect / isolation unavailable | Check `kepr status`, `kepr doctor`, and `kepr agent doctor` outside the agent. Start the approved daemon/service if needed; do not weaken isolation or expose the socket. |

User-mode clients may start a missing daemon outside agent sessions; this is
not an upgrade restart or a repair for corrupt credentials. Agent sessions
do not auto-start the host daemon. Follow the installer/service lifecycle
instead of assuming a new CLI binary replaced an already-running daemon.

## Commands you run yourself: `kepr exec --mask`

For your own scripts that need a readable key, `--mask` replaces stored
values in the command's output with `****`, so a script that echoes a key
can't leak it into a log or an agent's context:

```bash
kepr exec --env DEPLOY_TOKEN --mask -- ./deploy.sh
```

## Current limits

- **System mode needs `kepr-gate.service`.** The root daemon forbids
  itself network sockets, so its agent sessions run in this service, under
  an unprivileged dynamic user with no access to the credential store.
  `install.sh` enables it. The daemon passes each session's channel to it
  over a root-only socket. `kepr panic` reaches these gates too.
- **TLS-inspecting networks:** if your network intercepts TLS with its own
  certificate authority, the gate refuses the connection, because it trusts
  only public roots. A root-owned CA setting is planned.
- **Root:** an attacker with root on the running machine can read any
  process's memory. Run agents as your normal user.
- **Use, not read:** an agent can still make calls with the key toward its
  bound provider. It cannot copy it or send it anywhere else.
- **FIDO2:** sealed keys can't require a FIDO2 touch yet (use
  `--requires-consent`).

`kepr protect-agent` is retired: it now explains why and exits.

## Auditing

```bash
journalctl -t kepr-daemon KEPR_OP=resolve
```

Every release of a sealed key to the gate is logged as `op=resolve`; every
refused `get` of a sealed key as `result=fail: sealed`. `kepr usage` sums
these per key from the hash-chained audit log.

## Binding the store to this machine

Set `KEPR_MASTER_KEY_SEAL=tpm2` (or `host+tpm2`) in the service
environment, optionally with `KEPR_TPM2_PCRS=7`. The master key is then
sealed to this machine's TPM, so a copied disk can't be decrypted
elsewhere, and with PCRs, not after the boot chain changes either. The
commented lines in `systemd/kepr.service` show the setting.
