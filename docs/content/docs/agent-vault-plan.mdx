# Keeper Parity & Zero-Touch Agent Vault Plan

Status: **shipped, with gaps** (2026-10-14). Every ticket from T1.01 to
T11.24 has shipped, and so have the items built before the tickets
existed (P0, P2.4, P4.3, P5.1, P5.3 and others). Two tickets are partial:
T7.16 FIPS mode (HMAC, Argon2id, X25519 and ML-KEM stay outside the FIPS
module) and T8.02 `kepr ui` (its TAGS column is always empty). A few plan
items never became tickets and are not built. The largest is P3.2: the
daemon's master key and the gate's value cache still sit in ordinary
memory, zeroized on drop; only the gate's session key lives in
`memfd_secret` pages. Each phase in section 9 ends with a status line that
names its gaps. Several features are opt-in rather than the default: the
vault image (`KEPR_STORE=image`), the TPM2 PIN and counter, the KMS and
PKCS#11 sealers, FIDO2 unlock and the `fips` build. Of the 67 Keeper rows
in section 2, 43 are ✅, 19 are 🟡 and 5 are out of scope. Each 🟡 cell
says what is still missing.
Ticket status: [Agent Vault: Implementation Tickets](/docs/agent-vault-tickets).

The plan has two halves:

1. **Parity.** Everything Keeper Security ships that makes sense for a
   local-first, developer-native vault (verified against Keeper's own docs,
   section 1), plus 17 further features from 1Password, Doppler, Infisical,
   HashiCorp Vault, Teleport, systemd and agent-specific needs (section 2.6).
2. **Zero-touch agent vault.** The user pastes a key **once**. From then on
   any agent harness (oh-my-pi, Grok Build, Claude Code, Codex, Gemini CLI,
   opencode, Aider, Cursor…) and any tool those agents run can *use* the key,
   but no process the agent controls ever *holds* it: not in the environment,
   not in a file, not in an inherited fd, not in the agent's address space.
   At rest it lives in a hardware-bound, fixed-size encrypted vault image; in
   use it lives in kernel-hidden memory of a separate, non-dumpable process.

## 0. TL;DR

| Question | Answer in this plan |
| --- | --- |
| How is this different from Keeper's agent support? | Keeper's Agent Kit and local MCP let the agent fetch the plaintext itself (protecting chat history and git, not the agent's own process). kepr never gives the agent the value. See section 1.1. |
| How does an agent use a key it never sees? | `kepr-gate`, a credential-injecting proxy. The agent is configured with a worthless placeholder (`kepr-ph-…`) and a gate base URL; the gate swaps in the real key on the wire, only toward the hosts that key is bound to. |
| How is the agent kept from bypassing the gate? | `kepr agent run` starts the harness in its own network + PID namespace (unprivileged userns) with Landlock rules. Its only route off the box is the gate. |
| How does the user configure each harness? | `kepr agent install omp\|grok\|claude\|codex\|…` writes the harness's own config file (base URL + placeholder) once. Nothing to remember afterwards. |
| Can anyone read the key back? | Credentials stored with `--sealed` (the default for `kepr agent add`) are **write-only**: the daemon refuses `Get` for them. Only the gate can resolve them, and only for a bound destination. |
| How is it stored on disk? | A pre-allocated, fixed-size, noise-filled vault image with randomised slot placement, per-record keys, a Merkle root, and a TPM2-sealed key-encryption key with an anti-rollback NV counter. |
| How is it held in RAM? | `memfd_secret(2)` pages (removed from the kernel direct map, unswappable, no core dump, no `/proc/pid/mem`), guard pages, random placement, periodic relocation, XOR key-splitting, inside a non-dumpable process. |
| What stops an agent misusing a key it can use? | Destination binding, per-agent approvals, spend caps, prompt DLP, output masking, honeytokens and one-command leak response (P9). |
| Do random addresses stop a physical attacker? | Not on their own, and this plan says so plainly. Randomisation hides metadata (count, sizes, access pattern). What stops a physical attacker is encryption bound to the TPM + measured boot + PIN, memory encryption (TME/SME) and IOMMU. See section 7. |

### 1.1 What Keeper's own docs reveal

Four findings from Keeper's documentation shape this plan:

1. **Keeper's agent integrations hand plaintext to the agent.** The Agent Kit
   is a set of `SKILL.md` files that teach the agent to run `ksm` and
   `keeper` itself, and the local MCP service offers a "Read secrets" tool.
   Either way the decrypted value ends up in a process the agent controls.
   Keeper's model protects *chat history and source control*. kepr's gate
   model also protects against the agent itself.
2. **Keeper warns about its own `ksm exec`.** Its docs say the substituted
   values "are inherited by the child process's environment" and readable via
   `/proc/<pid>/environ`. That's exactly the leak kepr was built to remove.
3. **Keeper's "Privacy Screen" is visual only.** Keeper states the hidden
   password "is still stored in the user's vault and accessible via API
   communication and browser inspection". kepr's sealed credentials (section
   4.3) enforce the same idea in the daemon: there is no API that returns them.
4. **Keeper is converging on the same broker design for infrastructure.**
   Connection Manager, Tunnels and the KeeperDB proxy all inject credentials
   at a gateway so "end users never see, type or store the credential".
   `kepr-gate` brings that model to a single developer laptop and to AI
   agents, without a cloud gateway.

## 3. What is wrong with today's agent protection

Two defects in the shipped `kepr protect-agent` path motivate P0:

1. **The harness never finds its key.** `cli_agent.rs` calls
   `cli_exec::cmd_exec(&[], &memfd_keys, argv)`. That exports only
   `KEPR_FD_ANTHROPIC_API_KEY=3`, and Claude Code, Grok, oh-my-pi and the rest
   read `ANTHROPIC_API_KEY` / `XAI_API_KEY`, not a kepr-specific fd variable.
   The protected agent starts without credentials.
2. **The memfd leaks to every subprocess.** `memfd.rs` clears `FD_CLOEXEC` so
   the fd survives `exec`. Every shell the agent spawns therefore inherits
   fd 3, and `cat <&3` (or `cat /proc/self/fd/3`) prints the key. A
   prompt-injected agent gets the secret in one tool call. The sealing stops
   *modification*, not *reading*.

memfd delivery is still right for a cooperating application that reads its
fd once and closes it (`kepr exec --memfd` for your own service). It is the
wrong primitive for an untrusted, tool-running agent. The fix is to never
hand the agent the key at all.

## 4. Zero-touch agent design

### 4.1 Invariants

- **I1. Write-only after capture.** A sealed credential's plaintext leaves
  the daemon only toward `kepr-gate`, never in a `GetOk`, `env`, `--export`,
  `exec --env`, sync push, or MCP reply.
- **I2. Destination binding.** Each sealed credential carries an allowlist of
  `(scheme, host, port, header/field)` targets. The gate refuses to inject it
  anywhere else, so a prompt-injected agent cannot send it to an attacker's
  server even by asking the gate.
- **I3. No ambient path.** Inside `kepr agent run` the agent has no route to
  the network except the gate, cannot see the gate's or daemon's processes,
  and cannot read the vault directory.
- **I4. Placeholders are worthless.** What the agent sees (`kepr-ph-…`) is
  bound to one session id, valid only inside that session's namespace, and
  useless if exfiltrated.
- **I5. Fail closed.** If the gate, daemon or namespace setup fails, the
  agent does not start or gets a 401, never a fallback to plaintext env.

### 4.2 Components

```text
 user (once)                                          upstream APIs
   │ kepr agent add ANTHROPIC_API_KEY --for api.anthropic.com          ▲ TLS (rustls,
   ▼                                                                   │  pinned roots)
┌───────────────┐ private socketpair (fd3)┌──────────────────────────┐ │
│  kepr-daemon  │◀── Resolve{name,dest} ──│  kepr-gate               │─┘
│ vault image,  │  daemon spawns the gate │  own uid (system mode),  │
│ TPM-sealed KEK│── value (memfd_secret)─▶│  dumpable, memfd_secret  │
└───────────────┘                         │  key cache, policy, audit│
                                          └────────────▲─────────────┘
                                                       │ listening fd passed into
                                                       │ the session's netns
┌──────────────────── kepr agent run omp ──────────────┼──────────────────────┐
│ new user+net+pid+mount namespaces, Landlock, no_new_privs                   │
│                                                                             │
│  omp / grok / claude  ── http://127.0.0.1:7878/anthropic ──┘                │
│   env: ANTHROPIC_API_KEY=kepr-ph-7f3a…   (placeholder, not a secret)        │
│   tools it spawns (curl, gh, git, aws) ── HTTPS_PROXY=127.0.0.1:7879 ──┘    │
│   no other route out · cannot see gate/daemon PIDs · vault dir hidden       │
└─────────────────────────────────────────────────────────────────────────────┘
```

New binaries and modules (each under the 350-line production limit):

| Unit | Kind | Responsibility |
| --- | --- | --- |
| `kepr-gate` (`src/gate.rs`) | new bin, own system user | accept loop, session table, privilege drop |
| `src/gate_http.rs` | gate | `hyper` server + client: HTTP/1.1 and HTTP/2, streaming forwarder (SSE-safe) on a tokio runtime |
| `src/gate_tls.rs` | gate | rustls client to upstream; per-session ephemeral CA for egress mode |
| `src/gate_policy.rs` | gate | destination binding, placeholder → credential mapping, rate limits |
| `src/gate_rewrite.rs` | gate | header/body substitution, AWS SigV4 re-signing (reuses `sync_aws_sigv4.rs`) |
| `src/gate_audit.rs` | gate | per-request journal (method, host, path template, status, bytes; never bodies) |
| `src/cli_agent.rs` | CLI (rewrite) | `kepr agent add/install/run/ls/revoke` |
| `src/cli_agent_adapters.rs` | CLI | per-harness config writers (section 4.6) |
| `src/sandbox.rs` | CLI | userns/netns/pidns/mount setup, Landlock, seccomp, fd passing |
| `kepr-mcp` (`src/mcp.rs`) | new bin | MCP server exposing names and gated actions, never values |

Why a separate gate binary: the daemon's unit has
`RestrictAddressFamilies=AF_UNIX AF_NETLINK` and should keep it. The gate
needs outbound TCP. Splitting them keeps the vault process network-free and
puts the only network-facing code under a different uid that holds no master
key. It also keeps `hyper` and tokio out of the daemon: they are
dependencies of `kepr-gate` only, so the daemon's dependency tree and attack
surface don't grow.

### 4.3 Sealed credentials (daemon side)

- `.meta` gains `sealed: bool` and `bindings: [{host, port, scheme, inject}]`
  where `inject` is one of `header:Authorization:Bearer`, `header:x-api-key`,
  `query:key`, `basic:password`, `sigv4`.
- `handle_get` returns the generic `"credential unavailable"` for sealed
  credentials (same sanitised error, so callers can't probe which ones are
  sealed) and audits `KEPR_RESULT=sealed-denied`.
- The daemon **starts the gate itself** (`Request::StartGate`), with a
  cleared environment and one end of a private socket pair on fd 3. Sealed
  values are resolved only over that socket pair (`GateRequest::Resolve
  { name, host, port }`), never on the public socket. That rules out an agent
  launching its own gate under a debugger or with `LD_PRELOAD`, and needs no
  `/proc` inspection of the gate (which a same-uid daemon couldn't do once
  the gate is non-dumpable). In system mode the gate is its own service
  account and the daemon accepts the private channel only from that uid.
  The daemon checks the host against `bindings` itself; it does not trust
  the gate's policy alone.
- `Unseal` is deliberately absent. Changing a binding or un-sealing requires
  re-entering the value (`kepr agent add` again) or a FIDO2 touch plus polkit.
  The user "sees it once" when pasting it, and never again unless they choose
  to re-paste.

### 4.4 kepr-gate modes

**API mode (P1).** The harness's base URL points at
`http://127.0.0.1:7878/<provider>`. The gate maps `/<provider>` to a pinned
upstream (`/anthropic` → `https://api.anthropic.com`, `/xai` →
`https://api.x.ai`, `/openai` → `https://api.openai.com`, …), checks that the
request's auth header carries this session's placeholder, swaps in the real
key, and streams the response (SSE) back. Plain HTTP on loopback is fine
here: it never leaves the session's private network namespace.

**Egress mode (P2).** For tools the agent runs (`curl`, `gh`, `git`, SDKs),
the sandbox sets `HTTPS_PROXY` / `HTTP_PROXY` to the gate and trusts a
per-session CA (`SSL_CERT_FILE`, `NODE_EXTRA_CA_CERTS`, `REQUESTS_CA_BUNDLE`,
`GIT_SSL_CAINFO`). On `CONNECT` to a host that has a binding, the gate
terminates TLS with a leaf minted from that CA, substitutes placeholders found
in the bound header or field, and re-originates TLS to the real host. Hosts
with no binding are tunnelled blind or denied, depending on the session
policy (`--net=bound-only` is the default). The CA private key exists only in
gate memory for the life of the session.

**Special cases.**

| Consumer | Mechanism |
| --- | --- |
| Bearer / API-key headers (OpenAI, Anthropic, xAI, GitHub, Stripe, GCP) | straight substitution |
| HTTP Basic (registries, Jira) | decode, substitute password, re-encode |
| AWS SigV4 | client signs with placeholder secret; gate verifies against the placeholder, then **re-signs** with the real key (`sync_aws_sigv4.rs` already implements the derivation chain) |
| git over HTTPS | `git-credential-kepr` returns the placeholder inside a session; gate substitutes |
| SSH | `kepr ssh-agent` (P2.4): private keys stay in the daemon, only sign operations cross the socket |
| Postgres / MySQL / Redis | P7.1 protocol proxies: the agent authenticates to the gate with the placeholder, the gate does SCRAM/native auth upstream |

### 4.5 Caller authentication

- The gate's listening socket is created by the gate and **passed** (via
  `SCM_RIGHTS`) into the session's network namespace by `kepr agent run`.
  Only processes in that namespace can reach it.
- Placeholders encode `session_id ‖ cred_slot ‖ HMAC(session_key, …)`. A
  placeholder from session A is rejected in session B.
- Session lifetime is tied to the harness process via a pidfd. When the
  harness exits, the gate drops the session, its placeholders and its CA.

to be exported in a shell. The adapter writes only base URLs and placeholder
*variable names*. `kepr agent run` supplies the placeholder values.

### 4.7 Capture once

- `kepr agent add NAME [--for HOST…]` prompts with masked TTY entry (existing
  `cli_input.rs`) or reads the clipboard once (`--from-clipboard`, Wayland
  `wl-paste` / X11 `xclip`) and then **clears the clipboard**.
- Known key formats (`sk-ant-`, `xai-`, `sk-`, `ghp_`, `AKIA`, `glpat-`…)
  pre-fill `--for` bindings so the user normally types nothing but the paste.
- `kepr adopt` scans `.env`, `~/.bashrc`, `~/.zshrc`, `~/.config/fish`,
  harness config files and shell history for known key formats, imports each
  as sealed, and rewrites the source line to a placeholder or comment, with a
  backup that is itself encrypted. It reports, then asks before rewriting.

### 4.8 `kepr-mcp`

For agent platforms that prefer tools over base-URL rewiring:

- `list_secrets` returns names, bindings and expiry, never values.
- `http_request(secret, method, url, headers, body)` performs the request
  through the gate (binding-checked) and returns the response.
- `run_with_secrets(cmd, secrets)` runs a command inside a nested gate
  session with placeholders set.
- No tool ever returns plaintext. This is the inverse of Keeper's MCP server,
  which returns secret values into the model's context.

### 4.9 What an agent can still do

A compromised or prompt-injected agent inside a session can still **use** a
bound key toward its bound host (for example, burn API credit or call a
GitHub endpoint the token allows). Mitigations: per-credential rate and
spend caps in the gate, path-template allowlists (`api.github.com` `GET
/repos/**` only), per-use approval for high-risk credentials (polkit / FIDO2,
already shipped), anomaly alerts (P7.5) and the request journal. It cannot
**read**, **copy** or **redirect** the key. That is the guarantee.

## 5. Storage: the sealed vault image

### 5.1 A note on "random disk addresses"

Putting secrets at random offsets is security through obscurity if it is the
only defence: an attacker with a disk image can read every block. In this
design randomised placement has one specific job, **metadata hiding**: an
attacker who images the disk cannot tell how many secrets exist, how large
they are, which slot changed between two images, or which slot is "the AWS
key". Confidentiality and tamper detection come from cryptography bound to
hardware (section 5.3). Both together are worth having.

### 5.2 Format

- **Fixed-size image.** `kepr vault init --size 64M` pre-allocates the file
  with `fallocate`, or uses a dedicated partition / LVM volume
  (`--device /dev/disk/by-partuuid/…`). The image is filled with CSPRNG
  output, so empty and used slots look the same. Size never changes, so it
  leaks nothing about the vault's contents.
- **Slots.** The image is divided into 4 KiB slots. Each record (value +
  `.meta` + history) is padded to a size bucket and written to a slot index
  drawn from `HMAC(slot_key, record_id ‖ epoch)` mod N, with linear probing.
  Every write also rewrites a few random decoy slots with fresh noise, so a
  before/after diff of two images doesn't reveal which record changed.
- **Per-slot AEAD.** XChaCha20-Poly1305 or AES-256-GCM-SIV (nonce-misuse
  resistant) with AAD = `image_id ‖ slot_index ‖ epoch`, so a slot cannot be
  moved or replayed into another position.
- **Merkle root.** A hash tree over all slots; the root and epoch are
  authenticated in the header and mirrored into a TPM NV index (anti-rollback,
  section 5.3).
- **I/O.** `O_DIRECT | O_SYNC` writes with page-aligned buffers so plaintext
  never sits in the page cache; ciphertext only ever touches disk.
  A two-phase commit (journal slot then header flip) makes writes crash-safe.
- **Erasure.** SSD wear-levelling means overwriting a block does not erase
  it. Deletion is **crypto-shredding**: each record has its own key, wrapped
  under the vault master key; deleting the record destroys its wrapped key
  and bumps the epoch.
- **Migration.** `kepr vault migrate` imports today's per-file credstore into
  the image; the old files are crypto-shredded once the import verifies.
  The per-file store stays as the default for hosts without a TPM.

### 5.3 Key hierarchy

```text
TPM2 Storage Root Key (never leaves the TPM)
  └─ sealed KEK            policy: PCR 7 (Secure Boot state)
     │                            + PCR 11 / systemd-pcrlock (UKI + kernel cmdline)
     │                            + PIN (TPM dictionary-attack lockout)
     │                            [+ FIDO2 hmac-secret as a second factor]
     │                     unsealed over a salted, encrypted TPM session
     │                     (defeats LPC/SPI bus sniffing of discrete TPMs)
     └─ Vault Master Key (VMK, 256-bit random, lives only in memfd_secret)
          ├─ slot_key   (placement PRF)
          ├─ index_key  (encrypts the name → record_id index)
          └─ record keys (one per record, AES-256 wrapped by VMK)
               └─ value, fields, history, attachments
```

- **Anti-rollback.** A TPM NV monotonic counter stores the epoch. On open,
  an image with an older epoch than the counter is rejected. Restoring an
  old disk image does not resurrect a revoked key.
- **Evil maid.** A changed bootloader, kernel or cmdline changes PCRs, so the
  KEK will not unseal. The daemon fails closed and asks for the recovery
  passphrase (Argon2id path, already shipped).
- **Recovery.** At enrolment the VMK is also wrapped under a high-entropy
  recovery key that is shown once, printable as words and a QR code, and
  optionally Shamir-split (P6.3).
- **Backends without a TPM** fall back to the shipped Argon2id envelope,
  clearly reported by `kepr status` and never silently.

## 6. RAM: the secret enclave

The key has to be in plaintext somewhere while it's in use. The aim is to
make that place as small, short-lived, hidden and hostile to readers as Linux
allows, and to put it in a process the agent cannot touch.

### 6.1 Where plaintext may exist

| Process | Holds | Never holds |
| --- | --- | --- |
| `kepr-daemon` | VMK, record keys, decrypted values on demand | network sockets |
| `kepr-gate` | resolved values for active sessions (cache, TTL ≤ 5 min) | VMK, other users' values |
| agent and its tools | placeholders only | any real value |

### 6.2 Kernel and process hardening (daemon and gate)

- **`memfd_secret(2)`** (Linux 5.14+; check `secretmem.enable` on older
  kernels): pages are removed from the kernel's direct map, cannot be
  swapped, are excluded from core dumps and hibernation images, and cannot be
  reached through `/proc/pid/mem`, `process_vm_readv` or ptrace peeks. Hold the
  VMK, record keys and the gate's value cache here. Fallback when unavailable:
  `mmap` + `mlock` + `MADV_DONTDUMP` + `MADV_WIPEONFORK`, reported by
  `kepr doctor`.
- **Random placement + guard pages.** Each secret region is mapped at a
  CSPRNG-chosen, page-aligned hint address in the 47-bit user space, with
  `PROT_NONE` guard pages on both sides. A stray read or overflow faults
  instead of leaking a neighbour.
- **Relocation.** Every 60 s (and after each unlock) the enclave allocates a
  fresh region at a new random address, copies, and zeroises + unmaps the
  old one. A memory snapshot taken at one moment doesn't tell you where the
  key will be later.
- **XOR splitting.** The VMK is stored as two shares `A` and `B = VMK ⊕ A` in
  separate random regions, re-randomised on every relocation. It is
  recombined into a stack buffer only for the microseconds an AEAD call takes,
  then zeroised. This defeats scanners that look for AES key schedules in
  cold-boot dumps.
- **Process posture.** `prctl(PR_SET_DUMPABLE, 0)` (also makes
  `/proc/pid/mem` root-owned), `PR_SET_NO_NEW_PRIVS`, `mlockall` (already
  shipped), `RLIMIT_CORE = 0`, Landlock ruleset, seccomp allowlist, and a
  dedicated uid for the gate.
- **Host recommendations** surfaced by `kepr doctor`: Yama
  `ptrace_scope ≥ 2`, `lockdown=confidentiality` (blocks root reading kernel
  memory via `/dev/mem`, kprobes, eBPF), swap encrypted or disabled,
  hibernation disabled or encrypted, IOMMU enabled with Thunderbolt DMA
  protection.

### 6.3 Hardware memory protection

| Technology | Protects against | kepr action |
| --- | --- | --- |
| Intel TME / TME-MK, AMD SME | cold-boot RAM removal, bus snooping on DIMMs | `kepr doctor` detects and recommends enabling in firmware |
| AMD SEV-SNP, Intel TDX | a malicious hypervisor reading guest RAM | supported transparently; documented for cloud VMs |
| IOMMU (VT-d / AMD-Vi) | DMA attacks through Thunderbolt / PCIe | doctor check; documented as required for "physical attacker" claims |
| TPM2 | offline disk theft, evil maid, rollback | section 5.3 |
| Intel SGX | — | not used: deprecated on client CPUs and repeatedly broken by side channels |

### 6.4 When a process must hold a key itself

Some consumers can't go through the gate (your own service reading a DB
password). For those, replace inherited memfds with **pull-on-demand**: the
process connects to the daemon socket, the daemon checks `SO_PEERCRED` plus
the exe path and a per-launch token, and sends a `memfd_secret` fd via
`SCM_RIGHTS` with `FD_CLOEXEC` set. The consumer maps it, reads it, unmaps
it. Nothing is inherited by children. `kepr-core` gets a small helper for
this, and thin Python/Node/Go clients follow in P8.

## 7. Threat model: physical and local attackers

| Attacker | Defence | Residual risk |
| --- | --- | --- |
| Steals a powered-off laptop / disk | TPM-sealed KEK + PIN, fixed-size noise-filled image | none beyond brute-forcing the PIN, which the TPM's lockout throttles |
| Evil maid (modifies boot chain, returns laptop) | PCR policy; KEK won't unseal | user must notice the recovery prompt and not type the recovery key into a tampered system |
| Sniffs the TPM bus | salted, parameter-encrypted TPM sessions | firmware TPM (fTPM) avoids the bus entirely |
| Cold-boot RAM dump | TME/SME memory encryption, memfd_secret, XOR splitting, relocation | without TME/SME, a skilled attacker with liquid-cooled DIMMs can still try; splitting raises the cost |
| DMA via Thunderbolt / PCIe | IOMMU + kernel DMA protection | firmware with IOMMU disabled |
| Rolls the disk image back to an older snapshot | TPM NV monotonic counter | none |
| Edits ciphertext on disk | per-slot AEAD + Merkle root | denial of service (corrupt image); keep encrypted backups |
| Prompt-injected agent | sealed creds, gate, namespaces, destination binding | can *use* bound keys toward bound hosts until revoked (section 4.9) |
| Same-uid malware outside the sandbox | gate uid separation, non-dumpable processes, `ptrace_scope` | can drive the gate like the agent would: same residual as the row above |
| Root on the running, unlocked machine | `lockdown=confidentiality` raises the bar | root can ultimately read any process memory or load a module. No pure-software vault defends against live root, and kepr won't claim to |

## 8. Kernel and OS feature detection

`kepr doctor` gains a "hardening" section that reports, for each item above,
present / missing / not applicable, and how to fix it: `memfd_secret`
availability, Landlock ABI version, unprivileged user namespaces (and
AppArmor's `apparmor_restrict_unprivileged_userns` on Ubuntu 24.04+), TPM2
presence and PCR bank, Secure Boot state, `lockdown` mode, Yama scope,
swap/hibernate encryption, TME/SME flags from `/proc/cpuinfo`, IOMMU groups.
`kepr agent run` refuses to start with `--strict` if a required item is
missing, and warns otherwise.

## 10. Decisions (resolved 2026-10-04)

1. **Gate dependencies: `hyper`.** It is the more robust choice: a
   battle-tested HTTP/1.1 and HTTP/2 implementation with streaming bodies,
   upstream connection pooling and well-handled edge cases (chunked encoding,
   keep-alive, backpressure) that a hand-rolled parser would have to re-earn.
   Raw speed is not the deciding factor (the gate's latency is dominated by
   the upstream LLM API), but HTTP/2 multiplexing and pooled TLS connections
   do cut per-request overhead for agents that fire many parallel calls.
   Cost: tokio and hyper join the dependency tree, of `kepr-gate` only.
2. **Sealed by default: yes.** `kepr agent add` seals by default. Plain
   `kepr set` stays readable for backwards compatibility, with `--sealed`
   available.
3. **Unprivileged user namespaces: ship an AppArmor profile** for `kepr`
   (needed on Ubuntu 24.04+). No setuid helper. `kepr doctor` reports when the
   profile is missing or namespaces are disabled.
4. **Vault image: 64 MiB default; the per-file store stays the default** on
   hosts without a TPM until P4 has a release behind it.
5. **Prompt DLP: block and tell the agent.** No silent redaction (P9.2).
