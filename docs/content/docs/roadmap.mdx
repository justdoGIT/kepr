This roadmap is the source of truth for what kepr will become and the
order it ships in. Every phase ends in a versioned release. Locked
decisions live at the bottom; the matrix shows kepr's posture at each
milestone against the alternatives a procurement lead will compare us to.

The plan was built from a public CEO-and-PhD-security review against the
codebase that landed at the rename (commit
[`56d5882`](https://github.com/justdoGIT/kepr/commit/56d5882)). Every
finding was either confirmed against the actual source (with `file:line`
citation) or refuted. See `Gap analysis` below for the audit trail.

## Versioning

| Milestone | Phase | Theme |
| --- | --- | --- |
| `v1.0.0` | Phase 0 | In-process AEAD, end-to-end zeroize, capability drop, fuzz/proptest |
| `v1.5.0` | Phase 1 | `kepr exec`, docker helper, direnv, `.kepr.toml` manifest, `kepr doctor`, public launch |
| `v2.0.0` | Phase 2 | macOS Keychain backend, rotation hooks, TTL, FIDO2 unlock, polkit consent, ESO + cloud sync, audit chain |
| `v3.0.0` | Phase 3 | Team mode (age + Git), Sigstore Rekor anchor, SLSA-3 hermetic build, STRIDE doc |

`v1.0.0` is reserved for the Phase 0 crypto rewrite — that decision
predates this roadmap and was honoured deliberately, because the
in-process AEAD migration is the one change that retroactively breaks
the encryption-format compatibility envelope.

## Gap analysis

Verdicts on the public-review findings, audited against the current
codebase. `valid` means the finding stands and is on the roadmap;
`already-done` means the property is in place and we will pin it with a
test instead of a rewrite.

## Current implementation status

The gap analysis below is the historical Phase 0 review that guided the
roadmap. The current `main` tree has since landed the Phase 0 foundation and
most of the Phase 1 and Phase 2 Linux work:

- **Shipped:** in-process AES-GCM encryption, sealed master key loading,
  end-to-end `ZeroString` protocol values, socket umask hardening, per-UID
  rate limiting, capability and syscall sandboxing, `kepr-core`, `kepr exec`,
  `kepr env`, `.kepr.toml` manifests, `kepr doctor`, Docker credential
  helper, rotation hooks, TTL expiry, polkit consent, FIDO2 registration and
  unlock, hash-chained audit verification, ESO integration, and Vault/AWS/GCP
  sync adapters.
- **Still missing:** macOS Keychain/XPC support, Phase 3 team mode, Rekor
  anchoring, bit-for-bit reproducible release builds (the release build is
  network-isolated from locked sources since T12.38), the STRIDE
  threat-model document, and committed fuzz harnesses. The Phase 0/Phase 1 release tags and the manual
  end-to-end validation gate are also still pending.
- **Operational follow-up:** the historical gap bullets should not be read as
  a report of the current tree; use the shipped/missing lists above when
  prioritising the next release.

The dependency-free security extension backlog is tracked separately in
[Security Extension Roadmap](/docs/security-roadmap). It covers opt-in TPM2,
FIDO2 master-key wrapping, Secret Service/KWallet integration, and
dependency-maintenance requirements. The current FIDO2 implementation gates
selected credential reads; it does not yet protect the master key.

### Architecture

- **Fork+exec per operation, plaintext via `Command::output()`** —
  *valid, not done.* `src/crypto.rs:46-58` spawns
  `/usr/bin/systemd-creds encrypt` per `set`; `src/crypto.rs:111-128`
  reads plaintext into a plain `Vec<u8>` on `get`. No
  `zeroize::Zeroizing` wrapper. No startup digest check on `BACKEND_BIN`
  (`src/crypto.rs:21`). Replaced in Phase 0.
- **`ZeroString` end-to-end claim is weaker than it looks** —
  *partially done.* `src/generate.rs:14-21` defines `ZeroString` over
  `String`. The decrypt pipeline at `src/crypto.rs:128-133` materialises
  through a non-zeroizing intermediate. `Response::GetOk { value: String }`
  (`src/protocol.rs:54-57`) is plain. `serde_json::to_vec` and the
  framed write path (`src/daemon.rs:138-139`) leave plaintext JSON in a
  plain `Vec<u8>`. End-to-end zeroization arrives in Phase 0.
- **Unix socket creation race** — *valid, not done.*
  `src/daemon.rs:65-68` calls `UnixListener::bind` without setting
  `umask` first; `src/daemon_socket.rs:27-39` does
  `chown` + `set_permissions(0o660)` post-bind. The window between
  `bind` and `set_socket_permissions` is racy. Fixed in Phase 0 with
  `umask(0o117)` before `bind`, plus a regression test.
- **AEAD AAD binding to uid + name** — *not applicable today;
  becomes the right thing once in-process AEAD lands.* The host-key
  backend (`systemd-creds`) carries `--name=<cred_name>` but does not
  bind the uid into ciphertext-authenticated metadata. Phase 0's
  in-process AEAD makes `uid || canonical-name` the AAD.
- **`SO_PEERCRED` connect-time-only capture** — *correct for the
  current fresh-connect-per-request pattern* (`src/client.rs:9-15`,
  `src/daemon_peer.rs:27-49`). Pinned with a regression test in Phase 0;
  if connection pooling is ever added the test will fail loudly.

### Security

- **Rate limiting / lockout** — *valid, not done.*
  `src/daemon_pool.rs` is bounded backpressure, not throttling. Phase 0
  adds `src/daemon_ratelimit.rs` with a per-uid token bucket.
- **Distinguishable wire errors** — *valid, not done.*
  `src/crypto.rs:108` returns `"credential not found"` and
  `src/crypto.rs:125` returns `"decryption failed"`. Phase 0 collapses
  the wire response into a single `"credential unavailable"`; audit log
  keeps the precise reason; a `--debug` CLI flag asks the daemon for
  the unsanitised message under the same auth path.
- **Constant-time comparisons** — *valid as a forward-looking
  guard.* No `subtle::ConstantTimeEq` use today; no current code path
  needs it. Added to the dependency set in Phase 2 with the FIDO2
  assertion verifier — and added to the code-review checklist now so
  no future PR introduces a regression silently.
- **Capability scoping in the systemd unit** — *valid, not done.*
  `systemd/kepr.service:32-51` has `ProtectSystem=strict`,
  `ProtectHome=yes`, `MemoryDenyWriteExecute=yes`, `LockPersonality=yes`.
  Missing `CapabilityBoundingSet=`, `AmbientCapabilities=`,
  `SystemCallFilter=`, `RestrictAddressFamilies=`. Phase 0 lands all
  four; once the in-process AEAD removes the `systemd-creds` runtime
  dependency, `NoNewPrivileges` flips to `yes` (currently `no` at line 35).
- **Fuzzing / proptest** — *valid, not done.* Phase 0 adds
  `proptest` over `validate_name` and a `cargo-fuzz` harness over
  `framing.rs` and `protocol.rs`.
- **Backend binary supply-chain** — *fork+exec disappears in Phase 0;
  the supply-chain finding goes away with it.*
- **Audit log tamper-evidence** — *escaping is correct
  (`src/audit.rs:48-99`), but journald entries are deletable by root.*
  Phase 2 adds a hash-chained append-only file at
  `/var/lib/kepr/audit.log`; Phase 3 anchors the chain head into
  Sigstore Rekor.
- **Same-uid consent prompt** — *accepted-risk today, addressed in
  Phase 2.* polkit on Linux for flagged creds; FIDO2 touch as a
  stronger alternative.
- **License consistency** — *bug.* `LICENSE` is LGPL-2.1 while
  `Cargo.toml:6` and `Cargo.toml:66` declare `MIT`. Phase 0 fixes this
  by re-licensing to dual `MIT OR Apache-2.0` (see *Locked decisions*).
- **No library crate** — *valid, not done.* `Cargo.toml` declares two
  `[[bin]]` targets and no `[lib]`. Modules duplicated through `mod`
  declarations in each binary (`src/main.rs:7-16`,
  `src/daemon.rs:11-21`). Phase 0 splits `crates/kepr-core/`.

### Already in place

`mlockall(MCL_CURRENT|MCL_FUTURE)` (`src/daemon.rs:50-55`); atomic
write via temp+rename (`src/crypto.rs:44, 89-97`); `validate_name`
enforced in every daemon handler (`src/daemon_handlers.rs`); per-uid
namespacing parsed back from path (`src/store.rs:21-28`); SBOM (SPDX),
cosign signing, build-provenance attestations, `cargo audit`, `npm
audit` all live in `.github/workflows/security.yml` (CodeQL is gated
on the repo flipping public). Audit log escapes CRLF and bounds field
length to 256 chars (`src/audit.rs:82-98`).

## Phase 0 — Stabilise (`v1.0.0`, weeks 1–3, ~70-90h)

Close every architectural and security gap above that doesn't require
new product surface. Ship the same shape kepr has today, but defensible
under a public security review.

**New modules.**

- `src/crypto_inproc.rs` — `aes-gcm` AEAD over a per-host master key,
  with `uid || canonical_name` as Additional Authenticated Data.
- `src/master_key.rs` — load-or-generate a 256-bit master key, sealed
  through one `systemd-creds` blob at startup; pure in-process for every
  read/write afterward. (`tss-esapi` direct TPM2 binding deferred to
  Phase 2 behind a feature flag — keeps the dep tree small.)
- `src/daemon_ratelimit.rs` — per-uid token bucket. Default 10/sec
  refill, burst 30; override via `[ratelimit]` in `/etc/kepr/daemon.toml`.
- `crates/kepr-core/` — workspace member holding `protocol`, `framing`,
  `generate::ZeroString`. Both bins re-export through it; the
  forthcoming `docker-credential-kepr` and `kepr-eso-provider` depend
  on it.

**Modified modules.**

- `src/crypto.rs` becomes a thin trait facade with two backends:
  `Backend::SystemdCreds` (kept under `--features legacy-backend`) and
  `Backend::InProc` (default).
- `src/daemon_handlers.rs` — calls the trait; gains a rate-limit gate;
  collapses "not found" and "decrypt failed" into a single
  `"credential unavailable"` wire response while still logging the
  precise reason to the audit pipeline.
- `src/protocol.rs` — `Response::GetOk { value: ZeroString }` so the
  serde path is zeroizing end-to-end.
- `src/generate.rs` — extends `ZeroString` with `Serialize` /
  `Deserialize` and `ZeroizeOnDrop`-derived behaviour.
- `src/daemon.rs:65-68` — set `umask(0o117)` before `bind`.
- `systemd/kepr.service` — adds
  `CapabilityBoundingSet=CAP_IPC_LOCK CAP_DAC_READ_SEARCH CAP_CHOWN`,
  `AmbientCapabilities=`,
  `SystemCallFilter=@system-service ~@resources ~@mount`,
  `RestrictAddressFamilies=AF_UNIX AF_NETLINK`. Once in-process AEAD
  ships, `NoNewPrivileges=yes`.
- `Cargo.toml` — `license = "MIT OR Apache-2.0"`, matching `LICENSE-MIT`
  and `LICENSE-APACHE` at repo root.
- `[dev-dependencies]` += `proptest`. New `fuzz/` directory per
  `cargo-fuzz` convention.

**Risks.**

- Wire-format change `Response::GetOk { value: String }` → `ZeroString`
  is JSON-shape compatible but pin it with a cross-version test before
  declaring it.
- Workspace rearrangement may surface dependency downgrades in
  `Cargo.lock` — gate behind a `cargo update` review.
- Master-key migration story: `systemd-creds`-encrypted creds written
  with the legacy backend must remain readable through the
  `legacy-backend` feature for at least one release; document a
  `kepr migrate` subcommand.

**Success criteria.**

- `cargo test --workspace` green.
- `cargo clippy --workspace --all-targets -- -D warnings` clean.
- `cargo fuzz run frame_fuzz -- -max_total_time=1800` finishes without
  panic in nightly CI.
- `tests/e2e.sh` passes against the new daemon.
- `systemd-analyze security kepr.service` ≤ 2.5 (currently ~3.0-3.5).
- Wire response identical for `not found` and `decrypt failed`; audit
  log retains the precise reason.
- `LICENSE-MIT` and `LICENSE-APACHE` present; `Cargo.toml` matches.
- v1.0.0 tagged.

## Phase 1 — Useful (`v1.5.0`, weeks 4–12, ~220-280h)

Make kepr genuinely useful in a developer's daily workflow on Linux.
Five high-leverage UX entry points (`exec`, `env`, `doctor`,
`.kepr.toml`, `docker-credential-kepr`) plus a fix to the latent
shell-injection in `kepr get --export`. macOS support was originally
scoped here; it is moved to Phase 2 because the launchd / XPC /
audit-token rewrite is large enough to warrant its own milestone and
needs hands-on Mac validation that the Linux engineer can't supply
alone.

**New modules — shipped.**

- `src/cli_exec.rs` (PR #63) — `kepr exec --env VAR1,VAR2 -- python
  train.py`. Fetches `Get` for each var via the `CredFetcher` trait,
  then `execvp`s the child with the env merged in. The parent
  process is REPLACED (no fork), so the secret-bearing env is never
  observable post-fact (`/proc/<pid>/environ`, shell history, temp
  files). Any single fetch failure aborts BEFORE the child runs.
- `src/cli_doctor.rs` (PR #64) — `kepr doctor`. Three production
  checks (socket presence/mode, kepr-group membership, daemon Ping)
  plus a `Diagnostic` trait so orchestration is unit-testable
  without a live daemon. ✓/✗ list with copy-pasteable remediation
  hints per check.
- `src/cli_envdump.rs` (PR #65) — `kepr env --env VAR1,VAR2`. Emits
  POSIX-safe `export VAR='value'` lines for `eval` / direnv. POSIX
  single-quote-with-backslashed-quote escape closes the latent
  shell-injection in the existing `kepr get --export` path
  (previously printed `export NAME=value` unquoted; any `$VAR` /
  `$(cmd)` would have detonated inside the user's `eval`).
- `src/cli_manifest.rs` (PR #66) — `.kepr.toml` parser with explicit
  `--manifest PATH` loading and opt-in walk-up discovery from `$PWD`.
  Safe default resolution is `--env CSV > --manifest PATH`; callers that
  intentionally trust the working tree can set `KEPR_AUTO_MANIFEST=1` to
  enable the third `auto-discovery` fallback. Both `kepr exec` and
  `kepr env` route through `cli_activity::resolve_env_for`.
- Third `[[bin]]` `docker-credential-kepr` at `src/docker_helper.rs`
  (PR #67) — implements the docker credential-helper protocol
  (`get` / `store` / `erase` / `list` over stdin/stdout JSON) by
  wrapping `client::send_request`. Same socket, same `kepr` group
  gate. URL → kepr cred-name mapping is lossy by design (scheme +
  path stripped, port preserved, non-alnum→`_`, uppercased) — the
  `validate_name` constraint is `[A-Z0-9_]`.

**Modified modules — shipped.**

- `src/cli_activity.rs` added `Exec`, `Doctor`, `Env`, plus the
  central `resolve_env_for` for the manifest precedence.
- `src/cli_args.rs` learned the `--` separator, `--env CSV`, and a
  `--manifest PATH` override.
- `src/cli_cmds.rs` wires the new activities; `--export` path now
  uses `cli_envdump::shell_escape` so values containing shell
  metachars are POSIX-quoted (the latent injection fix).
- `Cargo.toml` declares the third bin and adds `libc` + `toml` deps.
- `install.sh` and the cargo-deb / cargo-generate-rpm asset maps
  install `docker-credential-kepr` alongside the existing CLI.

**Deferred to Phase 2.**

- `crates/kepr-backend-keychain/` — macOS Keychain backend over
  `security-framework`. Originally Phase 1; moved here because the
  launchd / XPC / audit-token rewrite is large enough to warrant
  its own milestone, and validation requires hands-on Mac testing
  the Linux engineer can't supply alone. The Linux release line
  remains the gold path; macOS gets first-class support in v2.0.

**Risks (still relevant).**

- The `.kepr.toml` schema will be argued over forever. Shipped
  minimal (`[env].required = ["VAR", …]`); unknown sections are
  ignored so Phase-2 fields land additively. Document a deprecation
  policy before extending.
- `docker-credential-kepr` competes with `docker-credential-pass`
  and `docker-credential-secretservice`. Be explicit about why kepr
  is better — per-uid isolation and the audit log — in launch copy.

**Success criteria — met.**

- ✓ `kepr exec --env OPENAI_API_KEY -- python -c 'import os;
  print(os.environ["OPENAI_API_KEY"])'` works end-to-end. The parent
  process's env is clean afterwards (it never had it — `execvp` not
  `fork`).
- ✓ `kepr doctor` produces actionable diagnostics for the three
  most common setup failures (socket, group, daemon protocol).
  Fourth check (backend binary digest mismatch) folded into Phase 2
  alongside the audit chain since both want the same supply-chain
  metadata.
- ⏳ Public launch: README sells, comparison table, asciicast, v1.5.0
  tag — pending the manual Phase-0 e2e validation step that gates
  v1.0.0 first.

**Success criteria — deferred to Phase 2.**

- macOS: Homebrew tap install + `kepr set FOO --value bar && kepr
  get FOO` without a daemon. Moved with the keychain backend.

## Phase 2 — Indispensable (`v2.0.0`, months 4–6, ~340-400h)

Features that turn kepr from "nice utility" into "we depend on this."
By the end of this phase the rotation story, the hardware-key-touch
story, the Kubernetes story, and macOS support all exist. Hour budget
revised upward from the original ~280-340h to absorb the deferred
macOS work from Phase 1.

**New modules.**

- `crates/kepr-backend-keychain/` (carried over from Phase 1) —
  macOS Keychain backend over `security-framework`. The "daemon"
  goes away on macOS — the launchd service per user is enough; the
  CLI is a thin wrapper over `SecItemAdd` / `SecItemCopyMatching` /
  `SecItemDelete`. macOS has no `SO_PEERCRED`; auth uses XPC +
  audit-token instead. New doc page:
  `docs/content/docs/installation/macos.mdx`. Splits the README
  into Linux / macOS / Windows-(planned) install paths.
- `src/cli_rotate.rs` — `kepr rotate KEY --hook ./refresh.sh`. Pipes
  the new value to the hook on stdin, atomically commits on hook exit
  0, restores the prior value otherwise.
- `src/daemon_expiry.rs` — periodic sweeper thread. Deletes expired
  creds, audit-logs the removal.
- `src/fido2.rs` — wraps `libfido2`-bindings for assertion verify.
  First user of `subtle::ConstantTimeEq`.
- `src/daemon_polkit.rs` — wraps
  `polkit_authority_check_authorization` for same-uid consent on
  flagged creds.
- `src/audit_chain.rs` — append-only file at `/var/lib/kepr/audit.log`,
  each entry hash-chained
  `H_n = SHA-256(H_{n-1} || serialized_event)`. Owned `root:root 0640`,
  daemon-only writeable. New CLI: `kepr audit verify`.
- `crates/kepr-eso-provider/` — implements the External Secrets
  Operator `SecretStore` plugin contract; sidecar deployment.
- `crates/kepr-sync-vault/`, `crates/kepr-sync-aws-sm/`,
  `crates/kepr-sync-gcp-sm/` — pluggable `Syncer` trait backends
  registered through `src/sync.rs`.

**Modified modules.**

- `src/protocol.rs` — `Request::Set { ..., ttl_secs: Option<u64> }`,
  new `Request::Rotate`, new `Request::Get { name, fido2_assertion:
  Option<Vec<u8>> }`.
- `src/store.rs` — sidecar metadata file holding `expires_at` and
  `requires_consent` / `requires_fido2` flags.
- `src/daemon_handlers.rs` — `handle_rotate`, expiry-aware `handle_get`,
  consent + FIDO2 gates.
- `src/audit.rs` — write to journald *and* append to the new chain.

**Risks.**

- macOS has no `SO_PEERCRED` for Unix sockets. Use Apple XPC or
  audit-token rather than rolling a custom IPC. Budget conservatively;
  this is the largest single block of platform work in the milestone.
- `libfido2` quality varies wildly across distros; budget time for
  wrapper bugs and document supported kernels / udev rules.
- TTL sweeper interacts with `src/daemon_cache.rs`. Invalidate
  aggressively; regression-test it.
- ESO is a different mental model — write the doc page first, the
  code second. Otherwise you'll over-fit the implementation to the
  kepr POV.

**Success criteria.**

- macOS: a Homebrew tap install, then `kepr set FOO --value bar &&
  kepr get FOO` works without a daemon.
- `kepr rotate STRIPE_KEY --hook ./bin/refresh-stripe.sh` rolls forward
  on success and rolls back on hook failure (proptest with random
  hook exit codes).
- `kepr set TMP --ttl 60` shows `expires_at` in `kepr list`; entry is
  gone 65 seconds later.
- A flagged cred requires a Yubikey touch on every `kepr get`;
  unflagged creds are unaffected.
- ESO syncs a `kepr` `SecretStore` into a Kubernetes `Secret` in a
  `kind` cluster.
- `kepr audit verify` exits 0 against an honest chain and non-zero on
  a single tampered entry.
- v2.0.0 tagged.

## Phase 3 — Enterprise (`v3.0.0`, months 7–12, ~480-560h)

Team mode, hardware-key-attested team identities, public anchoring of
the audit log, formal security posture documentation. The version
where kepr stops competing with `pass` and starts competing with
`Bitwarden Teams` and `Vault`.

**New modules.**

- `crates/kepr-team/` — `age` + `git2`. A team is a list of
  FIDO2-attested age recipients; secrets are encrypted to all of them
  and committed to a Git remote. `kepr team add <pubkey>`, `kepr team
  share <KEY> <team>`, `kepr team sync`.
- `src/team_identity.rs` — generate an age identity inside a Yubikey
  via the FIDO2 `hmac-secret` extension. Never extractable; signed by
  the device's attestation cert.
- `src/audit_rekor.rs` — periodic submission of the audit chain head
  to Sigstore Rekor as a signed checkpoint. CLI: `kepr audit verify
  --rekor` independently verifies the chain head against the public
  log.
- Optional Yubikey-touch unseal at daemon startup, behind a
  feature flag.

**Documentation deliverables.**

- `docs/content/docs/security/threat-model.mdx` — full STRIDE walk
  against the architecture, with mitigations linked back to actual
  source paths.
- README badges for **SLSA-3** provenance and the published SBOM.

**Build/release deliverables.**

- `.github/workflows/release.yml` — flip to the SLSA-3 generic
  generator. Hermetic builds. OIDC-keyless cosign + Rekor identity.

**Risks.**

- Team mode is the largest scope-creep surface in the entire roadmap.
  Pre-commit to the smallest possible age + Git design. Do not write a
  server.
- SLSA-3 hermetic builds require running the build in a network-isolated
  ephemeral runner. Allow buffer time.
- Rekor anchoring requires an OIDC identity for keyless signing —
  wired to the GitHub Actions OIDC token in CI; for local builds use
  `cosign sign --identity-token`.

**Success criteria.**

- `kepr team share STRIPE_KEY engineering` encrypts to all current
  engineering members and pushes to the team Git remote. A different
  member, on a different machine, runs `kepr team sync && kepr get
  STRIPE_KEY` and reads the value.
- `kepr audit verify --rekor` independently verifies the chain head
  against the public Sigstore log.
- README displays SLSA-3 and SBOM badges that link to the latest
  release's attestations.
- The STRIDE doc lives at `/docs/security/threat-model`, references
  every relevant source file by path.
- v3.0.0 tagged.

**Read.** Today kepr beats `systemd-creds` on per-user isolation (the
only thing kepr fundamentally is) and matches `pass` on licence
cleanliness once the LGPL/MIT mismatch is resolved. The big gaps are
cross-platform (Phase 1), tamper-evident audit log (Phase 2 → 3),
and sync/team mode (Phase 3). kepr will not surpass Vault on this
matrix; the goal is to surpass `pass` / `gopass` / `sops` on the
per-user-isolation, audit-log integrity, and hardware-key axes by end
of Phase 3 while staying single-binary, daemon-on-Linux,
no-server-required.

## Why kepr is not on a blockchain (and is not tokenizing users)

Recorded once so this discussion does not recur.

- Blockchains are public, replicated, append-only ledgers. Credentials
  must be private, controlled, and revocable. **Immutability and
  revocation are mutually exclusive** for secret material — once a
  ciphertext is on chain, a future key compromise (harvest-now,
  decrypt-later) decrypts the entire history retroactively. A local
  `rm` cannot.
- **Metadata leakage** is devastating even when payloads are encrypted.
  Transaction timestamps, sizes, and addresses publicly disclose
  who-rotates-what-when, which feeds supply-chain reconnaissance.
- **Cost and latency** are 1000× wrong. Local Unix-socket round-trip
  is sub-millisecond. The cheapest L2 is seconds and dollars-per-write.
  A credential manager doing hundreds of writes per developer per
  month does not fit on chain.
- **A wallet key would itself need a credential manager.** Infinite
  regress.
- **Tokenizing users likely fails the Howey test in the US**
  (investment of money, common enterprise, expectation of profit
  derived from the efforts of others), trips MiCA in the EU and the
  expanded FCA regime in the UK. Distributing a token tied to a
  security product is unregistered securities issuance.
- **Trust destruction.** Every credential manager competes on trust.
  Procurement teams deny adoption the moment a token is in the loop.
- **Smart-contract attack surface.** Audited contracts ship with
  one-to-three exploitable findings on average. Adding contract code
  to a security tool inverts the security argument.

### Adjacent ideas tracked for Phase 3 evaluation only

- **Sigstore Rekor anchoring** of the hash-chained audit log head.
  Public, append-only, no token, no money. Already on the Phase 3
  deliverables list.
- **W3C Decentralised Identifiers + Verifiable Credentials** for
  *public-identity sharing* across machines. Cryptography, not a
  chain. Tracked.
- **Shamir Secret Sharing / threshold MPC** for team-mode key escrow.
  Lets a team recover a master key when a member loses a device,
  without any single party having unilateral access. Note: HashiCorp
  Vault auto-unseal solves the same problem at roughly 1% of the
  implementation complexity; Phase 3 will pick the cheaper option.
  Tracked.

## Open questions for evaluation during execution

These are the calls to revisit when the work itself surfaces evidence
that the locked answer was wrong.

- **Wire-error collapsing UX cost.** Confirm a typo'd cred name is
  still recoverable via `kepr list` rather than a "this name doesn't
  exist" message. If user testing in Phase 1 shows the collapse hurts
  recovery, surface a suggestion line client-side without leaking
  daemon-side knowledge.
- **Rate-limit numerics in CI.** 10/sec burst 30 may be too tight for
  a CI runner that legitimately fetches dozens of secrets at startup.
  Phase 2's `kepr exec` should warm a request batch into a single
  `Request::GetMany` to amortise the limit.
- **Master-key migration.** The `legacy-backend` feature gate on the
  `systemd-creds`-fork+exec path needs a formal end-of-life. Propose
  v2.0.0 as the version that drops the feature and emits a one-time
  migration banner.
- **macOS XPC vs Unix-socket parity.** macOS does not have
  `SO_PEERCRED`; the `audit_token` path is the closest equivalent.
  Confirm Phase 1 actually pins peer-uid identity with a regression
  test before the public launch.
- **Team-mode metadata privacy.** Plain Git transport leaks push
  timestamps and recipient-set sizes. Document this in the threat
  model in Phase 3; revisit a self-hosted relay only if a customer
  shows up with that requirement.
