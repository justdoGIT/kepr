# Agent Vault: Implementation Tickets

This page turns the [Keeper parity & agent vault plan](/docs/agent-vault-plan)
into tickets. Each ticket is sized so that a small model, working alone with
no memory of earlier tickets, can finish it in one sitting: it names every
file to touch, every type and function to add, the tests to write first, and
the exact commands that prove it's done.

**Where the code differs from the ticket text** (the code is authoritative):

- `SessionConfig`, `ReadyLine` and `GateRoute` live in
  `kepr-core::gate_protocol` (shared by daemon and gate), not in the gate's
  `config.rs`. `SessionConfig` and `Request::StartGate` carry an optional
  fixed `port` (oh-my-pi and Grok Build read a fixed base URL from their
  config files; default 7878).
- The gate's provider table has no inject style: the credential's binding,
  returned by the daemon with the value, decides how the key is injected.
- The gate, not the CLI, generates placeholders; `kepr agent run` receives
  them in `GateStarted` and never holds the session key.
- The proxy buffers request bodies (up to 8 MiB) so the DLP check can run;
  responses are still streamed.
- History slots are ordinary credentials named `NAME~N` rather than a
  separate history store: they reuse the AEAD, the AAD binding and the
  rollback counter, and `~` keeps them out of every request and listing.
- `kepr agent …` (and `totp`, `inject`, `scan`, `copy`) are parsed by
  `cli_extra.rs` / `cli_agent_cmd.rs`, not `cli_args.rs`.
- `ReadyLine` / `GateStarted` placeholders are keyed by **provider**, not
  credential name, and the provider table lives in `kepr_core::providers`.
- The gate↔daemon channel carries request ids and a `Generation` query
  (cache invalidation); T9.01 is polkit consent at resolve time rather than
  per-request terminal prompts.
- Found and fixed on the way: the user-mode daemon could not start for
  non-root users (`mlockall(MCL_FUTURE)` under an 8 MiB `RLIMIT_MEMLOCK`),
  see `src/daemon_memlock.rs`.

**Open work** (the tickets under *Open work, split into tickets* below), by
phase. Each bullet names its ticket. A bullet marked *limit* names something
the ticket text may lead you to expect that doesn't work, or that was left
out of scope.

**All phases (shared wiring)**

- New requests are grouped per batch: one untagged variant per batch at the
  end of `Request` / `Response` wraps its own enum in
  `crates/kepr-core/src/protocol_<batch>.rs` (for example
  `Request::Store(StoreRequest::Organize { .. })`), not new top-level
  variants. The main request match moved to `src/daemon_dispatch.rs`.
- Code sits in per-batch directory modules (`src/daemon_<batch>/`,
  `src/cli_<batch>/`), registered in `daemon.rs`, `daemon_extra.rs`,
  `main.rs` and `src/cli_more.rs` (verbs and help), not in the flat
  `src/daemon_*.rs` / `src/cli_*.rs` / `src/cli_extra.rs` files the tickets
  name. `CredMeta` is in `src/cred_meta.rs`, not `src/expiry.rs`. The
  bullets below skip file names except where a file is hard to find.
- Help text (limit): core `kepr --help` still says `rm KEY --force` means
  "delete without prompt" (since T11.2 it also skips the trash), lists only
  `vault:`, `aws-sm:` and `gcp-sm:` on the `sync-push` / `sync-pull` lines,
  and shows `mcp` without flags. The newer syntax is only in the batch help
  sections.

**P1 (remaining)**

- T1.23: by default `$HOME` gets one read+write rule, so the user-mode store
  and state dirs under it are left to their hiding mounts. The per-child
  split of `$HOME` that the ticket describes runs only with
  `KEPR_LANDLOCK=strict`; `KEPR_LANDLOCK=0` turns the rules off.
- T1.23: `$XDG_RUNTIME_DIR` also gets read+write. The deny list is the
  sandbox's hiding-mount list (store and state dirs, socket dir, runtime
  root, `/etc/credstore.encrypted`, `/var/lib/kepr`, `/run/kepr`; existing
  dirs only), not a separate list.
- T1.23 (limit): Landlock does not mediate `connect()` on a Unix socket
  path, so the daemon socket is protected by its hiding mount only.
- T1.23 (limit): in strict mode the directories on the way to a hidden path
  (`$HOME`, `~/.local`, `~/.local/share`) get no rule: they can't be listed,
  nothing new can be created directly in them, and a file replaced there by
  rename (such as `~/.claude.json`) loses access. That is why strict is not
  the default.
- T1.23 (limit): symlinks get no rule of their own; a symlink's target is
  reachable only where the target itself is allowed. The rules apply only
  when the sandbox runs (not with `--no-sandbox`). A failing ruleset call
  aborts the harness start.

**P2: egress and non-HTTP consumers**

- T2.02: the HTTP side is a new `crates/kepr-gate/src/aws_egress.rs`;
  `egress.rs` only routes CONNECTs to it. A CONNECT to `*.amazonaws.com` is
  intercepted only when the daemon releases one of the session's AWS keys
  for that exact host, and the session CA is name-constrained to
  `amazonaws.com`.
- T2.02: beyond the ticket, the gate answers 403 to credential-minting calls
  (STS `GetSessionToken`, `GetFederationToken`, `AssumeRole*`, `AssumeRoot`;
  IAM `CreateAccessKey`, `Create/UpdateLoginProfile`,
  `Create/ResetServiceSpecificCredential`) and to signed streaming payloads
  (`STREAMING-*` except `STREAMING-UNSIGNED-PAYLOAD-TRAILER`), and runs DLP
  on AWS request bodies.
- T2.02: `kepr agent run` sets `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY`
  for the first sigv4 key by name, `KEPR_AWS_<NAME>` for each key,
  `KEPR_SESSION` and `AWS_CA_BUNDLE`. It withholds inherited `AWS_*`
  credentials, `AWS_PROFILE`, `AWS_DEFAULT_PROFILE` and `AWS_CA_BUNDLE`.
  `kepr agent add` refuses a sigv4-bound value that isn't AWS key JSON.
- T2.02 (limit): only hosts under `.amazonaws.com` on port 443 can be bound,
  so `*.amazonaws.com.cn` and custom endpoints are refused, and each service
  or region host needs its own `--for HOST:sigv4`. A CONNECT to an AWS host
  the key isn't bound to is tunnelled unchanged (AWS rejects the placeholder
  signature), or refused under `--isolate-net`.
- T2.02 (limit): request bodies are buffered up to 8 MiB (413 above that).
  Presigned URLs, SigV4a and signed streaming uploads get 403. Only the
  per-session limiter runs on the AWS path; the T9.06 per-day caps don't.
- T2.03: `--duration` accepts 900 to 43200 s (default 3600); the behaviour
  line said 900 to 3600. Adds `--role-arn ARN` (STS `AssumeRole`, session
  name `kepr`) and `--region R`.
- T2.03: inside a session the placeholder pair comes from the session env
  (`KEPR_AWS_<NAME>`) and the daemon is never asked; `Expiration` is now + 1
  h and no `SessionToken` is printed. `KEPR_SESSION` and `KEPR_AWS_*` are
  never inherited into a session; only `kepr agent run` sets them.
- T2.03 (limit): outside a session the key must be unsealed: the CLI reads
  it with a normal `get` and signs the STS call itself, so a sealed key is
  refused there. Inside a session `KEY` must be one of that session's sigv4
  keys.
- T2.04: the docker row's host is `auth.docker.io` (Docker Hub's token
  service, Basic), not `registry-1.docker.io`. The gcloud row's host is
  `www.googleapis.com`; `--for gcloud` (and detection) also binds 16 common
  `*.googleapis.com` service hosts, and the gate intercepts a
  `googleapis.com` host only when the key is bound to that exact host.
- T2.04: stripe also accepts `rk_live_` / `rk_test_` keys, and
  `kepr_core::leak` gains the new key shapes for DLP and `kepr scan`.
  Sessions also get `REGISTRY_AUTH_FILE` (podman, skopeo, buildah) and
  `CLOUDSDK_CORE_CUSTOM_CA_CERTS_FILE`, and the gate finds placeholders
  inside Basic credentials.
- T2.04 (limit): there is no `git` over HTTPS preset, although the goal
  names `git`. `gh` works through the existing github row (`GH_TOKEN` /
  `GITHUB_TOKEN`) and `aws` through T2.02.
- T2.04 (limit): the Docker Engine pulls from its own daemon outside the
  session, so the docker preset only serves clients that call the registry
  themselves. A docker value must be stored as `USER:TOKEN` for Basic; a
  bare `dckr_pat_` token is still detected, with no check for the user part.
- T2.04 (limit): the gcloud value is an OAuth access token (`ya29.`),
  injected as Bearer and never refreshed. Other `googleapis.com` hosts need
  their own `--for HOST`.

**P3 (remaining)**

- T3.06: the wire messages are `{"cmd":"fetch_fd","name"}` and
  `{"kind":"fd_ok","len"}` inside the session batch wrapper. The handler
  runs `handle_get`'s checks and the policy file (merge 46a7d6a) and also
  audits `fetch-fd`. FIDO2-gated credentials are refused, because this path
  carries no assertion.
- T3.06: the client also checks that the fd carries the write, shrink and
  grow seals and is exactly `len` bytes. The Python and Go SDKs have
  `fetch_fd` (T8.09); Node has none.
- T3.06 (limit): `KEPR_PULL` is only a list for the command; the daemon does
  not restrict `FetchFd` to it. Any process of the same uid that reaches the
  socket can fetch any unsealed credential, as with `get`.
- T3.06 (limit): `--mask` covers the `--env` values only; kepr never sees
  pulled values. Consent-gated credentials prompt like `get` (the
  `fdfetch.rs` comment saying consent refuses is wrong); re-auth credentials
  are refused unless a reveal window is open.

**P4: vault image and hardware-bound keys**

- T4.01: version, image id, slot count, epoch and Merkle root sit inside the
  AES-256-GCM-sealed header body, whose tag is the header MAC. Only the
  magic and the KDF salt are plaintext. The header also holds the index
  length and index slot list.
- T4.01: image keys come from the daemon master key via HKDF-SHA256 with the
  image's random salt, so opening an image needs that key. `fallocate`
  reserves the space and noise is then always written in 1 MiB chunks.
- T4.01 (limit): the index is capped at 256 slots (about 1 MiB) so the
  header fits one slot. The size is fixed at creation; there is no resize.
- T4.02: the Merkle root covers used slots only, since free slots are noise.
  Leaves hash slot index ‖ ciphertext, the leaf count is hashed into the
  root, and domain bytes separate leaves, nodes and the root.
- T4.03: the part index is part of the HMAC input. Probing skips every slot
  the current state uses, so writes are copy-on-write; a full scan takes
  over when the image is nearly full, and a full image refuses writes
  ("vault image is full").
- T4.04: the journal holds the new pages' hash, not their ciphertext; new
  pages only go to free slots, so the journal fits one slot. Fault injection
  uses the `SlotIo` trait.
- T4.05: a fresh record key is drawn on every write, not once per record.
  The vault master key is derived from the daemon master key and the image
  salt (HKDF), not stored. Delete also scrubs the record's pages.
- T4.05 (limit): crypto-shred holds for the current image only: an older
  copy of the image plus the master key still opens older values. Each
  commit rewrites the whole index.
- T4.06: one image, `store_dir()/vault.img`, holds the records of every uid
  the daemon serves, keyed `kepr-<uid>-<name>`. A missing image is created
  at 16 MiB on first write. The epoch high-water mark is kept in
  `cred-versions.json`, so an older copy of the image is refused. The TTL
  sweeper and the recovery-restore key probe cover the image too.
- T4.06 (limit): with the image active, credentials still in per-file
  storage are not listed or served until `kepr vault migrate`. One mutex
  serialises every image operation. `KEPR_STORE` accepts only unset, `file`
  or `image`; any other value stops the daemon at start-up.
- T4.07: `init` and `migrate` are owner-only (the user in user mode, root
  for the system store), and `migrate` also needs a daemon running with
  `KEPR_STORE=image`. Only one migrate runs at a time, and a re-run finishes
  a stopped move. Since T4.14 it also moves trash entries, aliases and
  attachment chunks.
- T4.07 (limit): there is no reverse migration (image back to files) and no
  resize.
- T4.08: the PIN comes from a file (`KEPR_TPM2_PIN_FILE`, absolute path)
  that the tools read; it is never on argv. `KEPR_TPM2_PCRS` adds PolicyPCR.
  The counter value is sealed inside the TPM object with the key, and also
  written in the blob header.
- T4.08: the counter protects the sealed master key only, not the vault
  image; the image's rollback check is T4.06's epoch high-water mark. The
  base unit hides devices, so `systemd/kepr.service.d/tpm2.conf.example`
  opens `/dev/tpmrm0`.
- T4.08 (limit): the options apply to a newly created master key only; an
  existing key keeps the sealing it was made with. With them,
  `KEPR_MASTER_KEY_SEAL` must be unset or `tpm2`.
- T4.09: the hmac-secret output travels inside the existing passphrase
  fields (`kepr_core::seal_factor`), so unlock backoff and wipe (T11.13)
  apply unchanged. KEK = HKDF-SHA256(salt = Argon2 salt, ikm =
  Argon2id(passphrase) ‖ hmac_secret, info `kepr-fido2-kek-v1`); the
  `kepr_pw2` envelope holds the credential id and a 32-byte salt.
- T4.09: a new `Fido2UnlockParams` request gives the CLI the public
  credential id and salt. The device is `KEPR_FIDO2_DEVICE` or the first
  `fido2-token -L` entry, and tool parameters go on stdin. Recovery-kit
  creation also asks for the touch.
- T4.09 (limit): one security key per store. `kepr lock --fido2` refuses a
  store that is already passphrase-protected. Needs libfido2's tools (the
  `fido2-tools` package).
- T4.10: the 24 words are 20 key words plus 4 checksum words. Adds the
  restore direction (`kepr recovery-kit restore --words`), which re-locks
  the store under a new passphrase. Both directions use the recovery-kit
  fences (passphrase-protected store, passphrase re-checked, owner only, no
  agent gate running) and are audited `recovery-words` / `recovery-restore`.
- T4.10: an unknown word is reported by position; a checksum mismatch (a
  wrong or swapped valid word) can't name the position.
- T4.10 (limit): the words are the whole master key, not Shamir shares:
  anyone holding them can decrypt the store files. `AGENTS.md` does not yet
  list this path among the documented exceptions.
- T4.11: `KekSealer` also has `kind()` and `key_ref()`; the sealed blob
  starts with a `kepr-kek1` header naming the kind and key, and unseal
  refuses a mismatch. Key or alias ARNs are accepted, the region comes from
  the ARN and `KEPR_KMS_ENDPOINT` overrides the endpoint. The HTTP transport
  never follows redirects.
- T4.11 (limit): AWS credentials come only from the daemon environment
  (`AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, optional
  `AWS_SESSION_TOKEN`); there is no instance-role or profile lookup.
- T4.11 and T4.12 (limit): the base unit has no network, so the KMS sealers
  need `systemd/kepr.service.d/kms.conf.example` (opens `AF_INET` /
  `AF_INET6`, loads `/etc/kepr/kms.env`), and the key service must be
  reachable at every daemon start.
- T4.11 to T4.13 (limit): these sealers apply to new master keys only; there
  is no re-seal command.
- T4.12: GCP sends `additionalAuthenticatedData` `kepr:master-key`, and
  `KEPR_KMS_ENDPOINT` overrides its endpoint. Azure accepts
  `vault.azure.net`, `vault.azure.cn`, `vault.usgovcloudapi.net` and
  `managedhsm.azure.net` hosts, requires `VERSION` and uses api-version 7.4.
- T4.12 (limit): tokens are read once at start-up from `GCP_ACCESS_TOKEN` /
  `AZURE_ACCESS_TOKEN` and never refreshed, so each daemon start needs a
  valid token.
- T4.13: the hash and MGF are pinned to SHA-256, which needs OpenSC 0.23 or
  newer. The PIN reaches only the tool's own environment (`--pin
  env:KEPR_PKCS11_PIN`). `systemd/kepr.service.d/pkcs11.conf.example` has
  the YubiHSM connector and USB options.
- T4.13 (limit): the RSA key pair must already exist on the token under the
  label; kepr does not generate it. Unseal needs the PIN file.
- T4.14: adds `crypto::Backend::rename`. On the image it is one commit that
  re-keys the record under the new name and moves the meta; on files it
  moves the meta first, re-encrypts, then removes the old file. `kepr
  health` takes ages on the image from record write times (79322f8).
- T4.14 (limit): `tests/vault_image.rs` covers set and rm, trash restore,
  history, `ln`, `mv`, `history --diff`, `dupes --merge`, `doctor --verify`,
  `delete --all` and attachments, but not shares. Features merged after
  T4.14 (most of P6, P7, P9, P10 and later P11) are not run against the
  image there.

**P5: data model**

- T5.01: a bare word in `kepr tag` adds the tag, `kepr tag KEY` alone shows
  the tags, and the CLI lower-cases tags. History slots don't store tags:
  `set` carries tags and folder over, so they survive `restore`.
- T5.01 (limit): `ls --folder F` matches F and everything below it; `ls
  --folder /` lists keys with no folder. Tags and folders grant or restrict
  nothing.
- T5.02: a stage's `map` entry replaces a base entry or plain name for the
  same variable. `map` entries resolve through the T5.05 / T5.06 reference
  resolver.
- T5.02 (limit): `--stage` needs a manifest in use (`--manifest PATH` or
  `KEPR_AUTO_MANIFEST=1`) and fails with `--env`; `$KEPR_STAGE` is ignored
  when no manifest is used. The help's `MANIFEST` example still says a
  `.kepr.toml` in or above `$PWD` is used by default, but discovery only
  happens with `KEPR_AUTO_MANIFEST=1`.
- T5.03: chunks are 45 KiB, not 48 KiB (48 KiB of base64 overflows the 64
  KiB frame), and chunk names are `NAME~a<slot>~<n>` with a probed slot
  number, not a random file id. The CLI is `attach add KEY FILE [--as NAME]`
  and `attach get KEY NAME [-o OUT|-o -]` (default OUT is NAME in the
  current directory).
- T5.03: attachments follow the credential into the trash and back, are
  purged on delete, purge, expiry and `delete --all`, and `doctor --verify`
  checks manifests against chunks. SSH and share-key credentials refuse
  attachments as well as sealed ones.
- T5.03 (limit): attachments of consent- or FIDO2-gated credentials can't be
  read (there is no prompt per chunk). At most 32 files per credential, and
  one upload per credential at a time (a new upload drops unfinished ones).
- T5.04: `--profile` implies `--generate`. For `kepr set` the profile is
  named explicitly (P may name a profile, a host or a type in the file);
  host and type matching is automatic only for `record add --generate
  FIELD`. The strength estimate also penalises a built-in list of about 32
  common passwords and keyboard rows.
- T5.04 (limit): the common-password list is small and built in, not a
  breach corpus.
- T5.05: records may now hold lists, structured values and a `custom`
  object, validated by the daemon; `record add` gains `--field k[]=v` and
  `--custom LABEL=v`. `\]` and `\\` are escapes too, and templates also
  accept `\ ` for a space.
- T5.05 (limit): `file/` in `inject`, `exec` and `env` needs a UTF-8
  attachment; binary attachments go through `kepr attach get` or `kepr
  resolve`. Values still come from `get`, so sealed credentials are refused
  and gated ones prompt (once per credential).
- T5.06: `--env` is now repeatable, `\,` escapes a comma inside a reference,
  and `--memfd` takes references too. `[env.map]` entries are checked at
  manifest load, and `exec --mask` masks by the provisioned variable names.

**P6: sharing, recovery, hygiene, sync, policy**

- T6.01: HKDF salt = SHA-256(ephemeral X25519 pub ‖ ML-KEM ciphertext). The
  secret record stores the 64-byte ML-KEM seed (X25519 secret ‖ seed, 96
  bytes), not an expanded decapsulation key. `kepr share key` upgrades a v1
  key in place (same X25519 key, new ML-KEM seed).
- T6.01 (limit): ML-KEM comes from the RustCrypto `ml-kem` crate at 0.3.2,
  which is not yet 1.0.
- T6.02: `FolderImport` takes a chunked upload id, not the bundle inline.
  `kepr folder share` needs `-o FILE`, and `--sealed` asks importers to
  store the values sealed. `kepr import FILE` also opens a folder bundle.
- T6.02: the Ed25519 signing key is derived from the share secret (HKDF),
  not stored as a second key, and each wrap also carries a MAC that binds
  the signer to the share key. Re-import compares against fingerprints of
  what the previous import wrote, never against the stored value.
- T6.02 (limit): only values `get` can read now are exported; sealed, SSH,
  share-key and consent/FIDO2-gated credentials are listed by name only. A
  sealed import binds each value to its provider's host (by key prefix or
  name) and skips a value with no known provider. An existing name not from
  this folder is left alone unless `--overwrite`. At most 64 recipients;
  bundles up to 16 MiB.
- T6.03: enrolment is two file steps: the new machine runs `kepr device
  enroll TOKEN [-o FILE]`, then the first machine runs `kepr device enroll
  --from FILE`. The request HMAC is keyed by the token's SHA-256, the only
  thing the daemon stores.
- T6.03 (limit): there is no relay-blob path; enrolment goes by file or
  stdout. Pinning is one-way, so for sync (T6.10) devices must enrol each
  other both ways. At most 32 devices and 8 pending tokens.
- T6.04: the link carries the relay as `?relay=URL`; `share open` also takes
  `--from FILE` and `--as KEY`. The relay answers HEAD (200 waiting, 410
  fetched, 404 unknown) for `kepr share check` (T6.05).
- T6.04 (limit): `kepr-relay` keeps blobs in memory only (lost on restart)
  and speaks plain HTTP (TLS through a reverse proxy). Defaults:
  127.0.0.1:8737, 7-day max TTL, 60 requests/min per IP, 64 connections.
- T6.04 (limit): a link is a bearer link, not bound to a recipient key.
  Without a relay, single use is enforced per receiving store (its
  received-id list); the file blob itself is not consumed.
- T6.05: adds a per-user sent-share ledger and `kepr share check`, which
  asks relays (HEAD) which links were opened. A new `set` cancels the
  self-destruct mark.
- T6.05 (limit): the owner's daemon learns of an open only when it receives
  the share itself, when `kepr share check` sees the relay blob gone, or at
  link expiry. A file-based link opened elsewhere self-destructs only at
  expiry.
- T6.06: requests carry an HMAC under HKDF(X25519(contact, owner)) of the
  two share keys, not a signature (share keys can't sign). The contact's
  daemon makes the request (`kepr emergency request OWNER_KEY`) and the
  owner's daemon takes it in (`kepr emergency request --proof FILE`); adds
  `EmergencyRemove` and `EmergencyProve`.
- T6.06: the minimum delay is 1 hour, and `--names A,B` or `--all` must be
  given. `kepr status` warns of pending requests, and a release also writes
  a daemon log line.
- T6.06 (limit): there is no relay transport: requests and released
  envelopes move by file or through the same daemon. Released envelopes are
  held on the owner's daemon for 30 days (`kepr emergency fetch -o DIR`), so
  a contact on another machine needs someone with access to that daemon to
  pass them on.
- T6.06 (limit): release runs from the owner's daemon sweeper, so that
  daemon must be running. A request older than 7 days is refused. Sealed,
  SSH, share-key and consent/FIDO2-gated values are never released.
- T6.08: adds a `json` format; the format is guessed from the URL host when
  `--format` is omitted, and the URL may be `kepr:NAME` (read from the
  vault). Posting runs in the CLI (the daemon has no network), with no
  retry.
- T6.09: besides sealed, SSH and share-key items, consent/FIDO2-gated values
  and unstarted view windows (T11.15) are listed by name only. Import
  reports create, update (with `--overwrite`) or unchanged and never
  replaces sealed or SSH credentials. Policy checks import as `set` and
  export as `export`. The bundle passphrase must be at least 10 characters.
- T6.09 (limit): the whole bundle is capped at 16 MiB; items or attachments
  beyond the budget are listed as omitted (`size`). Exported meta is a
  subset: record type, tags, folder, expiry and re-auth.
- T6.10: sync bundles carry value and meta only, no history or attachments.
  The change time is the value file's mtime, and a merged delete moves the
  credential to the trash. Senders are authenticated with a per-wrap X25519
  MAC, not a signature.
- T6.10 (limit): devices must enrol each other both ways. Sealed, SSH,
  share-key and gated credentials never sync and are never replaced or
  deleted by a merge. Sync runs only on `kepr sync now`; there is no
  background schedule. S3 uses `AWS_*` environment credentials
  (`KEPR_S3_ENDPOINT` overrides); git uses the `git` CLI with a clone under
  `~/.cache/kepr/sync`.
- T6.11: the daemon enforces the policy before dispatch, not through
  per-handler `policy::check` calls. It also governs `set` and `seal`, and
  since later commits one-time share links (as `share`), `kepr serve` reads
  and `FetchFd`. Adds `kepr policy status` and `kepr policy reload`;
  `KEPR_POLICY_FILE` overrides the path; the unit gains `ExecReload`
  (SIGHUP). An invalid file denies every governed op.
- T6.11 (limit): `exe`, `parent` and `harness` come from `/proc`; in system
  mode `ProtectProc=` hides other users' processes, so such rules don't
  match there (deny). Harness detection is a routing aid, not an isolation
  boundary. A denied read answers "credential unavailable"; the reason goes
  to the audit log as `policy-deny`.
- T6.12: also lists aliases and the policy rules that allow the credential,
  and counts one-time share links (5776602). Audit-derived rows come from
  the caller's own audit-chain entries.
- T6.13: RS256 verification uses `ring`, not the `rsa` crate
  (RUSTSEC-2023-0071, 86f87e3). The first machine re-verifies the ID token
  in its CLI and can pin `--subject`; both enroll steps take `--oidc` and
  `--client-id`.
- T6.13 (limit): the daemon only checks that an identity from the token's
  issuer comes with the enrolment; JWT signatures are verified by the
  owner's CLI, not the daemon. `alg: none`, HMAC algorithms and RSA keys
  under 2048 bits are refused; clock leeway is 60 s.
- T6.14: `kepr escrow open FILE` returns a 2-of-2 recovery kit for `kepr
  recovery-kit restore`, not the key itself; adds `kepr escrow status`.
  `kepr escrow disable` needs the passphrase and warns that copies of
  `escrow.bin` already handed out still open the key (971dbfc).
- T6.14 (limit): the administrator gets `escrow.bin` from the state
  directory by other means.

**P7: PAM-lite**

- T7.01: `kepr agent add-db` infers Redis from `redis://` and `rediss://`
  URLs (`--kind` only cross-checks the URL), and upstream TLS follows
  `sslmode` (`rediss://` means verify-full, `redis://` means disable).
  Agents get `REDIS_URL`.
- T7.01 (limit): only the client's first command is parsed, and `HELLO` is
  forwarded without its credentials. Upstream login is `AUTH` (one-argument
  form for the default user), plus `SELECT` when the database is not 0.
- T7.02: the gate greets the agent with its own nonce and
  `caching_sha2_password`, and strips SSL and compression capabilities on
  the loopback leg. Agents get `MYSQL_*` variables. The wire and scramble
  code is in kepr-core, which gains SHA-1.
- T7.02 (limit): `caching_sha2_password` full authentication happens only
  over TLS; the RSA public-key path for plaintext connections is not
  implemented.
- T7.03: tunnel routes are `tcp:NAME` targets that never resolve a
  credential. Under `--isolate-net` the egress proxy lets exactly these
  targets through, and the relay (`src/cli_sandbox_relay.rs`) also carries
  database and tunnel ports. The agent finds each port in
  `KEPR_TUNNEL_<NAME>`.
- T7.03 (limit): `HOST` must be a fully-qualified name or an IPv4 address.
- T7.04: the CLI logs in through the gate as user `kepr_rotate`; if the
  pending password already logs in, the gate reports success so the CLI
  commits.
- T7.04 (limit): unlike Postgres (SCRAM verifier), the statement carries the
  password in SQL text, so it relies on upstream TLS (on unless
  `sslmode=disable`). The password is quoted with `'` doubled; backslash and
  NUL are refused.
- T7.05: the new key is verified with STS (same ARN, retried) before it is
  stored, not after. On a failed verification or store, the new key is
  deleted and the old one kept. `DeleteAccessKey` is signed with the new
  key.
- T7.05 (limit): sealed keys are refused (the CLI can't sign with them). The
  stored value must be JSON with `access_key_id`, `secret_access_key` and an
  optional `session_token`, and calls go to `iam.amazonaws.com` (commercial
  partition) for the calling user only.
- T7.06: generic SigV4 signing is `kepr_core::sigv4_req`, and kepr-core's
  `serde_json` becomes a normal dependency. Adds `kepr aws whoami KEY`
  (sealed keys refused). Errors carry only the provider's `Code` and
  `Message`.
- T7.07: `--every off` stops a schedule. The schedule survives `set`, which
  restarts its clock and clears failures. Backoff starts at 15 min and
  doubles, capped at a day or the interval. The hook's generator kind uses
  the existing `--gen-kind` flag.
- T7.07 (limit): the system (root) daemon never runs user hooks: there the
  schedule is only shown, and `kepr rotate KEY --scheduled` must be run by
  hand. Intervals are 1 hour to 10 years; a run times out after 600 s.
- T7.08: the gate, not the CLI, signs the RS256 app JWT (with `ring`, not
  `rsa`) and exchanges it for the token, so the key, the JWT and the token
  never leave the gate. The verb is `kepr github-app add KEY --app-id N
  --installation-id N`.
- T7.08 (limit): bound to `api.github.com:443` only (no GitHub Enterprise
  Server). Tokens are cached per key until 5 minutes before expiry; errors
  carry the HTTP status only.
- T7.09: the gate sends recording batches to the daemon, which writes the
  file. Only the agent's side is recorded (HTTP bodies after DLP, database
  and tunnel streams after login), and echoed keys are masked.
- T7.09 (limit): 50 recordings are kept per user, up to 256 MiB each; beyond
  8 MiB of unsent data, chunks are dropped (and counted). `scriptreplay`
  export covers PostgreSQL sessions only.
- T7.10: adds `--jit on|off`, `--revoke [--to HARNESS]` and a show form
  (`kepr grant KEY`). Grants survive rotation and `kepr list` shows them. An
  approved T7.12 request on a jit credential opens a persisted `*` grant
  marked `approved`, the only kind that satisfies an approvals requirement
  (merge 7914def).
- T7.10 (limit): the harness name is claimed by whoever starts the session,
  so a grant bounds when a credential is usable, not which program uses it.
  Windows last up to 7 days. Revoke bumps the gate generation, but when a
  window runs out on its own a gate can keep a cached value for up to its
  cache TTL (300 s).
- T7.11: `kepr checkin --rotate` runs the credential's T7.07 schedule
  (`rotate --scheduled`), so it needs a configured schedule, and keeps the
  hold if that fails. A `set` keeps the hold (the `CredMeta` comment saying
  "Dropped by `set`" is wrong).
- T7.11 (limit): credentials are per uid, so a hold can't block another
  user; within one account it is a coordination marker, and the owner can
  always read. The token is saved under `$XDG_STATE_HOME/kepr/holds`, so any
  session of the same user with that state dir can check in without
  `--token`. Holds last at most 24 h; the sweeper clears spent holds only in
  user mode.
- T7.12: the CLI verb is `kepr quorum` (`set`, `request`, `approve`, `sign`,
  `ls`). For a non-jit credential an approved request opens an in-memory use
  window (the sweeper closes it and bumps the gate generation); a jit
  credential gets a persisted `approved` T7.10 grant instead. Lowering N or
  turning it off is itself a request that needs the current N. `kepr serve`
  refuses quorum-gated credentials (b77b8f8).
- T7.12 (limit): approvers are devices, not people: each enrolled device of
  the same user counts once. Use windows last up to 24 h (default 1 h), and
  in-memory windows are lost on daemon restart (fail closed). Device
  approvals are carried by hand (`kepr quorum sign` output pasted into
  `kepr quorum approve ID --with`).
- T7.13: auto-revoke runs `kepr panic`, which stops every gate (journal
  lines name a route, not a credential), not a per-credential revoke. Hits
  post through `notify.rs` with the rules file's own webhook and throttle,
  not through T7.15's `alerts.toml`. The default source is the daemon's
  per-user gate journal (9fa54dd); `--journal FILE|-` reads JSON lines, and
  entries older than 10 minutes only teach the baseline.
- T7.13 (limit): `kepr anomaly run` is a CLI process the user must keep
  running. Off-hours uses local time.
- T7.14: forwarding runs in the CLI through a new `audit_tail` request,
  since the daemon has no network. The OTLP URL may be `kepr:NAME`.
- T7.14 (limit): non-root callers get only their own entries; root on the
  system daemon gets everyone's. Syslog is UDP only, and delivery is at
  least once.
- T7.15: adds `kepr alerts check`. Held matches are counted in the next
  alert, and the first run starts at the log's end. The webhook URL may be
  `kepr:NAME`.
- T7.15 (limit): `kepr alerts run` is a CLI process the user must keep
  running.
- T7.16: only AES-256-GCM and SHA-256 (daemon) and rustls with the session
  CA (gate) go through aws-lc-rs; HMAC (SigV4, SCRAM, share HKDF) stays on
  RustCrypto. The daemon side sits behind a `CipherSuite` seam, and a new
  `crypto_info` request feeds `kepr status`.
- T7.16: `--features fips` alone links AWS-LC's ordinary build. The
  validated module also needs `aws-lc-rs/fips` (daemon) or `rustls/fips`
  (gate), which the CI fips job adds; `kepr status` claims FIPS only when
  that module is linked and passed its self tests.
- T7.16 (limit): Argon2id, X25519, ML-KEM and other primitives are not
  routed through the FIPS module.
- T7.17: the generator is referenced by tag `v2.1.0` (as it requires), with
  `private-repository: true`. The existing `actions/attest-build-provenance`
  step is skipped on private repositories. Provenance covers the .deb, .rpm
  and tarball only.
- T7.18: the flag is `kepr agent run --grant NAME=ROLE:ADMIN`. The grant
  runs before the route's first client login, not at gate start (the daemon
  serves the gate channel only after the ready line). The grantee is the
  route record's user, not `CURRENT_USER`, because the statement runs on the
  admin connection. An existing membership is left alone and never revoked.
- T7.18 (limit): a gate killed outright (for example by `kepr panic`) can't
  run `REVOKE`; the role stays until an administrator revokes it. PostgreSQL
  only.

**P8: ecosystem**

- T8.01: there is no persistent daemon connection: each line runs as a child
  `kepr` with the terminal inherited, because the daemon serves one request
  per connection. Adds `history`, `!N`, `!!` and `help`.
- T8.01 (limit): lines carrying inline values are refused and not recorded
  (`--value`, `-v`, `--stdin`, and `--field k=v` unless the value is `-`).
  Ctrl-C interrupts the child, not the shell.
- T8.02: the TAGS column is always empty: `tags_of` in `src/cli_eco/tui.rs`
  is a stub that was never wired to `CredInfo.tags`. Copy runs a child `kepr
  copy NAME`; delete sends the plain delete request, which moves the
  credential to the trash (T11.2).
- T8.03: the resource can generate the value (`generate` =
  `hex|base62|pass|uuid|words`), and a generated value never enters
  Terraform state. The data source also returns record `fields`,
  `record_type`, `tags`, `expires_at` and `modified`; sealed keys are
  refused.
- T8.03 (limit): data-source values are written to Terraform state. The
  provider is not published to a registry (local builds with `dev_overrides`
  only), and the release workflow doesn't build it. Changing `name`,
  `generate`, `ttl_secs` or `requires_consent` forces replacement.
- T8.04: `kepr://NAME` is also accepted. Without an installed client, the
  plugin falls back to the checkout's `sdk/python`.
- T8.04 (limit): `kepr://NAME/field` reads only a top-level string field;
  index notation, nested paths and linked-record paths are rejected. Ansible
  isn't installed in CI, so tests use stub Ansible modules; the live round
  trip runs only with `KEPR_SDK_LIVE=1`.
- T8.05: `VAULT` may also be a full sovereign-cloud Key Vault host
  (`.vault.azure.cn`, `.vault.usgovcloudapi.net`,
  `.vault.microsoftazure.de`).
- T8.05 (limit): bearer token only; there is no client-secret, certificate
  or managed-identity flow.
- T8.06: other values are kept, but keys are written back sorted, so the
  original key order and formatting are lost.
- T8.06 (limit): a key that itself contains a dot can't be addressed. Pull
  returns numbers and booleans as their JSON text. The file holds plaintext
  values.
- T8.07: both share `integrations/ci/kepr-ci.sh`. The install is
  cosign-verified, and OIDC login covers AWS STS, GCP STS with impersonation
  and Vault JWT. GitLab can't mask values that appear at run time, so its
  template never prints values and has no masking step. `actionlint` runs
  against a manual example workflow.
- T8.07 (limit): secret schemes are `vault:`, `aws-sm:` and `gcp-sm:` only
  (no `azure-kv:` or `json:`). Only the x86_64-linux tarball is installed,
  with a per-job `kepr-daemon --user`. The GitLab image needs bash, curl, jq
  and cosign.
- T8.08: plain JavaScript with no build step. Adds a `kepr: Refresh lock
  state` command. Hovers also show the field, the last-modified time and the
  sealed/consent/FIDO2 flags; picking a credential in the list inserts its
  `kepr://NAME` reference.
- T8.08 (limit): `package.json` declares `os: linux`, and the extension is
  not published to the Marketplace. The reference matcher handles `NAME` and
  one lowercase field only (no index notation).
- T8.09: the Node SDK has no `fetch_fd`, because Node can't receive file
  descriptors without a native addon. `set` also takes `requires_fido2`, and
  each SDK adds a `generate` helper and `credentials()` / `info()`.
- T8.09 (limit): SDK `delete` moves the credential to the trash (T11.2); no
  SDK call skips the trash. A generated value is never returned by `set`.

**P9: agent safety (remaining)**

- T9.04: desktop prompts use `notify-send --wait` actions (libnotify 0.7.10
  or newer), not `gdbus`. Answers come through a registered approver process
  (`kepr approvals serve`, one polkit prompt to register); with no live
  approver, polkit is used as before. Setting `approve_via` (`kepr approvals
  set KEY --via desktop|ntfy|any`) also needs polkit. `get`, gate resolves
  and SSH signing share the new consent check.
- T9.04 (limit): no answer within 60 s is a deny, and an approver that
  hasn't polled for 15 s counts as gone. The ntfy buttons call back to
  `--listen ADDR:PORT` over plain HTTP by default, with the one-time token
  in the URL inside the ntfy message, so anyone who can read the topic and
  reach the callback can answer.
- T9.05: `db_query` is PostgreSQL-only: it logs in with the session
  placeholder and sends one statement. Besides `kepr mcp --read-only`, it
  takes a per-call `read_only`; read-only mode sets
  `default_transaction_read_only` and also wraps the statement in
  `BEGIN READ ONLY` … `ROLLBACK`. `ssh_run` goes through an in-process
  ssh-agent socket that relays to the daemon's sign-only keys, not through
  a gate route. `ai_context` notes come from
  `--context TARGET=NOTE` flags, not from credential metadata.
- T9.05 (limit): read-only is a guard against mistakes; the boundary is a
  database role without write grants. `ssh_run` reaches only hosts listed
  with `--ssh`, runs ssh in BatchMode (unknown host keys refused) and needs
  the `ssh` binary. `db_query` returns at most 500 rows or 256 KiB.
- T9.06: gates report through a new `GateRequest::DayUsage`, and
  `GateLimits` moved to `kepr_core::gate_limits`.
- T9.06 (limit): caps are flags on each `kepr agent run`, not stored on the
  credential, and a session started without a daily cap doesn't report, so
  its traffic isn't counted. Database and tunnel connections and the AWS
  SigV4 path (T2.02) are not counted. The day is the daemon's local calendar
  day; if the daemon can't answer, the request is refused.
- T9.07: the price table is a plain-text file, `~/.config/kepr/prices` (host
  glob and USD per 1M tokens, first match wins; `--prices FILE` overrides).
  Gate journal lines gain `tokens`; the daemon records each session's
  route-to-credential map at `StartGate`, and `kepr agent run` names its
  harness.
- T9.07 (limit): one blended price per host glob (no separate input and
  output prices), and only JSON and SSE responses are metered. Sessions
  without a recorded harness show `unknown`.
- T9.08: alerts go through the audit log (a `kepr alerts` rule with `ops =
  ["canary-tripped"]`), because the daemon can't open TCP connections.
  Provider-side webhooks are received by `kepr canary listen` at
  `/kepr-canary/<trip id>`. Reading a decoy with `kepr get` also trips it.
  Import, discover and adopt skip planted canaries (f430934).
- T9.08 (limit): decoy formats are anthropic, openai (default), xai, google,
  groq, openrouter and github. Decoys pass kepr's own key-shape checks only:
  GitHub `ghp_` decoys carry no valid checksum, and no decoy is registered
  with a provider.
- T9.09: the value is read before the leak is reported, because the daemon
  deletes it.
- T9.09 (limit): only AWS IAM user keys are rotated (T7.05, signing with the
  leaked key itself). STS credentials and `ghs_` tokens get a note that they
  expire on their own. Sealed keys and unknown values fall back to the
  revocation URL.

**P10: platform extras**

- T10.01: per-open checks (owner uid, `--exe` digest, `--consent`) run in
  the user's own `kepr mount` process, not in the daemon. Values are fetched
  with a normal `get`, so the daemon sees the `kepr` binary as the reader.
  `--consent` runs `pkcheck` (`io.kepr.read-credential`) for the opener's
  pid and start time, with 60 s to decide.
- T10.01: `*.json` files render an object, a single key in a file not named
  `.env` renders the bare value, and anything else renders dotenv lines.
- T10.01 (limit): runs in the foreground (Ctrl-C or `fusermount3 -u DIR`
  unmounts) and never sets `allow_other`.
- T10.02: also adds the `aes` crate next to `cbc`, `chacha20` and `flate2`.
- T10.02 (limit): key files, AES-KDF and KDBX 3.x are refused. Title becomes
  NAME (the password), plus `NAME_USERNAME`, `NAME_TOTP` and `NAME_<FIELD>`
  for protected custom fields. URLs, notes, unprotected custom fields,
  attachments, history entries and the recycle bin are not imported.
- T10.03: a fingerprint can't derive the key-wrapping key, so this is a
  quick unlock only. With the opt-in daemon setting
  `KEPR_FINGERPRINT_UNLOCK=DURATION`, a soft lock (idle timer, sleep
  watcher) keeps the master key in memory for that window. Consent prompts
  needed no code: they are already polkit `auth_self` prompts.
- T10.03: also fixes `io.kepr.policy`, which was malformed (`--` inside a
  comment), so polkit had been skipping it.
- T10.03 (limit): user-mode, passphrase-protected stores only. After a
  daemon restart, `kepr panic` or the end of the window, only the passphrase
  unlocks. Needs `pam_fprintd` in polkit's PAM stack and enrolled fingers.
- T10.04: the key goes to `/usr/bin/security -i` on stdin as hex. The
  master-key file keeps only a marker (service, plus an account derived from
  the key's fingerprint), checked on read. The sealer is built on every
  target and refuses outside macOS.
- T10.05: adds `--decode hex|base64` for binary payloads. `@t` and `@p` are
  refused because they die with kepr; the default keyring is `@u`.
- T10.05 (limit): payloads are at most 32767 bytes, and fscrypt, ext4 and
  f2fs descriptions need a 16-hex-digit descriptor. Sealed, SSH and share
  keys are refused, as with `get`.
- T10.06 (limit): needs systemd 250 or newer. Without `--tpm2` the line
  decrypts only on hosts with this host's key.
- T10.07: values are stored as `PODMAN_<ID>`. Secret data that is exactly
  `kepr://NAME` is a reference, resolved to NAME's current value at each
  lookup.
- T10.07 (limit): values must be non-empty UTF-8 (one trailing newline is
  dropped), and sealed and SSH keys can't back a secret. Consent or FIDO2
  credentials prompt on every container start. A reference takes a bare
  NAME only (no fields). `delete` runs `kepr delete --force`, which skips
  the trash.
- T10.08: all objects are fetched in one batch (`POST /v1/secrets` on
  kepr-eso-provider). `-write-files` also writes the files itself, for
  drivers before v0.0.21. Object versions reported to the driver are a
  per-process HMAC, not a hash of the value.
- T10.08 (limit): a mount gets every listed object or fails; at most 100
  objects. The bearer token comes from the volume's `nodePublishSecretRef`
  (key `token`) or `-token-file`, and `http://` URLs are accepted. No
  Kubernetes manifests or Helm chart are shipped, and the release workflow
  doesn't build the provider.
- T10.09: adds `kepr exe KEY` to show a binding, `kepr exe KEY --allow PATH`
  to replace it and `kepr exe KEY --clear` to clear it; identities are
  computed by the client. Bindings are sticky across `set`, and only an
  allowed program can change or clear one (otherwise delete and re-create
  the credential).
- T10.09 (limit): new bindings are refused when the daemon can't open the
  caller's `/proc/<pid>/exe`; a system daemon needs `CAP_SYS_PTRACE` for
  that, which the shipped `kepr.service` bounding set doesn't include. The
  checked peer is the process that connected, so `kepr exec -- psql` is
  checked as `kepr`.
- T10.09 (limit): the check doesn't stop same-uid ptrace or `LD_PRELOAD` of
  an allowed program, an allowed interpreter running another script, or
  socket hand-off.
- T10.10: no `rcgen`: its `time` dependency needs Rust 1.88 or carries
  RUSTSEC-2026-0009, so certificates are DER-built in
  `kepr_core::x509_build` and signed with `p256`. Adds `kepr pki ca`. The CA
  key is the sealed credential `KEPR_PKI_CA` with no bindings; leaf keys are
  made by the CLI, which sends only the public point. Health uses a new
  finding kind, `cert`.
- T10.10 (limit): P-256 only. The CA has pathlen 0 and no name constraints,
  and there is no CRL or OCSP. Leaf validity defaults to 30 days (max 825),
  and `kepr pki ls` tracks the last 200 issued certificates.
- T10.11: `tpm2_quote` runs in the CLI, and the daemon verifies the quote
  against its own single-use nonce. The AK is enrolled with `kepr pki
  tpm-enroll --ak-pub ak.pem --ak HANDLE|CTX`; once enrolled, every SVID
  needs a quote. Output files use spiffe-helper's names (`svid.pem`,
  `svid_key.pem`, `svid_bundle.pem`).
- T10.11 (limit): enrolment is trust on first use: the attestation key is
  not checked against an EK certificate. ECDSA P-256 AK and the SHA-256 PCR
  bank only; replacing an enrolment needs a new CA (`kepr pki init
  --force`). There is no SPIFFE Workload API; output is files only.
- T10.12: no macOS CI job was added, although the ticket's test calls for
  one; Linux CI covers the read path with fakes only. There is no fallback
  to a prompting read.
- T10.12 (limit): a failed read fails the unseal: the item is gone, the
  keychain is locked, there is no login session, or a rebuilt daemon binary
  no longer matches the access list.

**P11: Keeper re-check**

- T11.1: also matches the record field `user` (database and server logins)
  and, after T11.5, alias names. Record fields are searched only when a
  plain `get` would succeed without a prompt; sealed, SSH, share-key,
  consent/FIDO2-gated and expired credentials match on name, tags, folder
  and type only.
- T11.1 (limit): the `/regex/` matcher has `.`, `*`, `^`, `$`, classes and
  `\` escapes only (no `+`, `?`, groups or alternation). Patterns are at
  most 256 characters.
- T11.2: `rm --force` skips the trash as well as the prompt (a new
  `DeleteNow` request). Trash entries keep the whole `.meta`, and history
  slots and attachments move along. The plain delete request (SDKs, `kepr
  ui`) now goes to the trash; the leak response skips it. `rm` on a locked
  store is refused.
- T11.2 (limit): restore takes the newest trash entry for that name. `kepr
  trash purge` with no name needs `--yes`.
- T11.3: refused for sealed, SSH, share-key, consent/FIDO2-gated and expired
  credentials and for versions saved while sealed, so set-then-diff can't
  test a guess. Version 0 is the current value, 1 the newest saved one.
- T11.4: `--merge KEEP` first moves the other members' values to the trash,
  then makes each an alias of KEEP, keeping its tags and folder.
- T11.4 (limit): exact SHA-256 equality only. Consent/FIDO2-gated and
  expired values are left out, as well as sealed, SSH and share keys.
- T11.5: `get` resolves the alias before any policy check, so the target's
  seal, consent, FIDO2 and expiry apply; the reply keeps the requested name.
  `rm ALIAS` removes only the alias.
- T11.5 (limit): deleting the target leaves dangling aliases (warned on
  `rm`, reported by `doctor --verify`).
- T11.6: links are followed client-side with one `get` per record, so every
  get policy applies to each target, and up to 4 links are followed (the
  ticket asked for one hop). Links can also sit in list items and custom
  fields; `record add --ref k=OTHER` writes one.
- T11.6: on write the daemon refuses self-links and links to sealed, SSH or
  share-key credentials (or an alias of one). Longer cycles are refused only
  at resolve time.
- T11.7: built-in types moved to `kepr_core::record_types`. The daemon
  accepts any well-formed type name; only the CLI checks it against the type
  table. Convert runs in the daemon, keeps policy, tags, folder and
  attachments, and moves the old value to history, so `kepr restore` undoes
  it.
- T11.7 (limit): user types are per-user CLI config and never reach the
  daemon. A broken type file is skipped with a warning. Sealed records, SSH
  and share keys, and aliases can't be converted.
- T11.8: `--from-file` takes a filled `record template` or a bare JSON
  object. Fields of a `ref` kind given as names become links. Unknown and
  custom fields are masked too.
- T11.8 (limit): required and masked rules are enforced by the CLI, not the
  daemon. `--clone` reads OTHER with a normal `get`, so its prompts apply.
- T11.11: hygiene rules are their own TOML file, sent with the health
  request, not part of `policy.toml` (the access policy). `--period` accepts
  `N[d|w|m|y]`.
- T11.11 (limit): values the caller can't `get` (sealed, consent- or
  FIDO2-gated) are checked for age only.
- T11.12: the lock is the same as `kepr panic`. `status` and `ping` polling
  don't count as activity.
- T11.13: the wipe replaces the envelope with a tombstone instead of
  deleting it, so a restarted daemon stays locked rather than making a new
  key; it is audited `unlock-wipe`. The backoff also covers recovery-kit
  creation and re-auth.
- T11.13 (limit): online only: a copied envelope can still be attacked
  offline.
- T11.14: a separate `Reauth { name, passphrase }` request and `kepr reauth
  KEY` open the window; `Get` gained no passphrase field. It also covers
  `exec`, `kepr://` notation, attachments, `share send` and one-time links.
  `kepr reauth KEY --on|--off` toggles the flag (off needs an open window).
- T11.14 (limit): needs a passphrase-protected store; in system mode only
  root can use it. The window is per (uid, credential), so any process of
  that user can read KEY during it (`kepr serve` does not borrow it).
  Refused on sealed, SSH and share-key credentials.
- T11.15: `--to` still accepts a raw public key. View windows apply to

  ledger with the audit chain.
- T11.15 (limit): a name stays pinned to one key (remove it before
  re-adding). kepr does not scan QR codes: the `KQ<i>/<n>:` chunk text must
  be fed to `kepr share receive`. "Opened" is known only for one-time links
  (relay check) or when the recipient uses the same daemon.
- T11.16: profile directories nest under the default ones
  (`$XDG_RUNTIME_DIR/kepr/profiles/NAME/`, and the same under the share and
  state dirs), not `$XDG_RUNTIME_DIR/kepr-NAME/`, so the agent sandbox's
  hiding mounts cover every profile. `--profile` re-executes kepr with
  `KEPR_PROFILE` set.
- T11.16 (limit): user mode only: with `KEPR_SYSTEM_MODE` set, a profile is
  an error.
- T11.17: `kepr sync import` also lists `azure-kv:` and `json:` sources.
- T11.17 (limit): the dry run fetches remote values and compares SHA-256
  hashes in the CLI; no value or hash is printed. There is no `pull --map`.
  Sealed, SSH and share keys are skipped. Import pulls values only with
  `--yes`.
- T11.18: `kepr batch -` reads from stdin, and every line is checked before
  the first one runs. Besides `--value`, lines with `-v`, `--stdin` or an
  inline `--field k=v` are refused. Batch files are at most 1 MiB.
- T11.19: there is no `--insecure-network` flag; only loopback and a Unix
  socket are served. Reads go through a new `GetQuiet`, which refuses
  credentials that need consent, FIDO2, re-auth or M-of-N approval instead
  of prompting (971dbfc, b77b8f8). Requests are due within 5 s, and
  connections past 16 get 503.
- T11.19 (limit): read-only (`list`, `get`), plain HTTP, one token from
  `KEPR_SERVE_TOKEN_FILE` (no group or other access, at least 16
  characters).
- T11.20: `match` is `SOURCE:GLOB` or a bare `GLOB`, matched
  case-insensitively against the kepr name. `ask` skips the entry without a
  terminal, and a broken rules file stops `kepr discover`.
- T11.21: the new key is created as `KEY_NEXT`, so a failed run can be
  resumed; adds `--port`. The commit keeps KEY's consent flag.
- T11.21 (limit): one host per run. After the commit the old key is gone
  (SSH keys keep no history), so other hosts that trust only the old key
  lose access. Ed25519 only; only `~/.ssh/authorized_keys` is edited, and
  the old key's lines are removed whatever their options. The host must
  already be in `known_hosts`.
- T11.22: gates send their journal entries (metadata only) to the daemon
  over the private channel, and the command reads that T1.11 journal for
  every session, not the T7.09 recordings. Entries gain `host`.
- T11.22 (limit): kept per user as two rotating JSONL generations of about
  512 KiB each; older entries are dropped.
- T11.23: adds `--unignore`. Breach ignores are applied in the CLI.
- T11.24: `StatusOk` gains a flattened, all-optional `StatusInfo`, so older
  daemons still print the store line.
- T11.24 (limit): the sealer field reports only passphrase, file (user mode)
  or host (system mode, the credential backend); it doesn't reflect
  `KEPR_MASTER_KEY_SEAL` (TPM2, KMS, PKCS#11, Keychain). Escrow means
  `escrow.bin` exists in the state dir, and the gate count is the caller's
  own.

## How to work a ticket (read this first, every time)

1. **One ticket per branch / PR.** Never combine tickets. Never start a
   ticket whose "Depends on" tickets aren't merged.
2. **Read only the files the ticket lists**, plus `AGENTS.md`. If you need
   another file, the ticket is wrong: stop and say so instead of guessing.
3. **Write the tests first** (they're listed under *Tests*). Run them and
   confirm they fail for the reason you expect. Then write the code.
4. **Copy existing patterns.** When a ticket says "follow the pattern in
   X", open X and imitate it exactly (naming, error handling, test setup).
5. **Done means all of these pass**, run from the repo root:

   ```bash
   cargo fmt --all -- --check
   cargo clippy --workspace --all-targets --all-features -- -D warnings
   cargo test --workspace
   cargo test --test file_size_limit
   ```

   Known exception: `version_state::tests::with_next_reverts_in_memory_on_persist_failure`
   fails when tests run as root (it relies on directory permissions). Ignore
   only that test, and only when running as root.
6. **Never do these**, whatever the ticket seems to need:
   - log, print, `Debug`-format, or put in an error message any secret value;
   - convert a `ZeroString` to `String` except at the socket boundary;
   - name the encryption backend in user-facing text (say "the credential backend");
   - skip `store::validate_name` on a name that came from a request;
   - trust a uid or pid sent in a request body (only `SO_PEERCRED` is trusted);
   - add a dependency the ticket doesn't list;
   - disable, skip or loosen a test to make CI pass.
7. **File size.** No `.rs` file may exceed 350 lines of production code
   (tests at the bottom don't count). If yours would, split by concept into a
   new file and list it in your PR. `src/daemon.rs` and `src/cli_cmds.rs`
   are at their ceilings: put new logic in new files and add only the
   minimal dispatch line there.
8. **New request type?** It always touches three layers: a variant in
   `crates/kepr-core/src/protocol.rs`, a client call, and a daemon handler
   that calls `audit::log`. The ticket will say which.
9. **Security-critical tickets** are marked 🔒. They need a human (or strong
   model) review of the diff before merge, even if CI is green.

### Ticket sizes

- **S**: under ~150 lines changed, one concept. Fine for a small model.
- **M**: ~150–400 lines, a few files. Small model OK if it follows the steps literally.
- **L**: needs design judgement. A strong model or a human should implement
  it, or first split it into S/M tickets using the template at the bottom.

## P1: sealed credentials and the gate

Design decisions already made (don't revisit them in a ticket):
the gate uses `hyper` 1.x on tokio with `hyper-rustls` and compiled-in
`webpki-roots`; `kepr agent add` seals by default; the gate lives in its own
workspace crate so its dependencies never reach the daemon.

P1 ships in two security stages:

- **Stage A (T1.01–T1.17):** the user-mode daemon spawns the gate (same uid
  as the user, clean environment, private socket pair for resolves) and the
  gate makes itself non-dumpable. The agent never
  receives the key and cannot ptrace or read the gate's memory. The agent can
  still reach the network directly (it just has no key to use there).
- **Stage B (T1.18–T1.19):** sandboxed network namespace and a gate running
  as its own system user.

### T1.01 Binding types (S)

**Goal:** shared types that say where a sealed credential may be sent.

**Depends on:** nothing.

**Files:** create `crates/kepr-core/src/binding.rs`; modify
`crates/kepr-core/src/lib.rs` (add `pub mod binding;`).

**Add:**

```rust
#[derive(Debug, Clone, PartialEq, Eq, serde::Serialize, serde::Deserialize)]
#[serde(tag = "kind", rename_all = "snake_case")]
pub enum Inject {
    Bearer,                    // Authorization: Bearer <value>
    Header { name: String },   // <name>: <value>, e.g. x-api-key
    Query { param: String },   // ?<param>=<value>
    Basic,                     // Authorization: Basic base64(user:<value>)
}

#[derive(Debug, Clone, PartialEq, Eq, serde::Serialize, serde::Deserialize)]
pub struct Binding {
    pub host: String,          // lowercase DNS name, no scheme, no path
    #[serde(default = "default_port")]
    pub port: u16,             // default 443
    pub inject: Inject,
}

fn default_port() -> u16 { 443 }

/// Ok(()) or a short reason. Rules: host is 1..=253 chars of [a-z0-9.-],
/// does not start or end with '.' or '-', contains at least one '.';
/// port != 0; header/param names are 1..=64 chars of [A-Za-z0-9-_].
pub fn validate_binding(b: &Binding) -> Result<(), String>;

/// Parse the CLI form "host[:port]:inject" where inject is one of
/// "bearer", "basic", "header=NAME", "query=NAME".
/// Example: "api.anthropic.com:header=x-api-key".
pub fn parse_binding(s: &str) -> Result<Binding, String>;
```

**Tests** (in `binding.rs`): JSON round-trip of each `Inject` variant;
`port` defaults to 443 when missing from JSON; `validate_binding` rejects
`"https://x.com"`, `"x.com/path"`, `"EXAMPLE.COM"`, `"localhost"`, port 0,
header name with a space; `parse_binding` accepts
`"api.openai.com:bearer"` and `"h.example.com:8443:query=key"` and rejects
`"api.openai.com"` (no inject) and `"a.b:99999:bearer"`.

**Done when:** the standard commands pass.

### T1.05 Daemon starts the gate; private resolve channel (M) 🔒

**Goal:** only a gate process that the daemon itself started can obtain a
sealed value, and only for a host the credential is bound to.

Why the daemon starts the gate: if any process could start a gate and then
ask the daemon for keys, an agent could start one under a debugger or with
`LD_PRELOAD` and read the key out of it. A process the daemon spawns with a
clean environment, reached over a socket pair only the daemon holds, has no
such hole, and needs no `/proc` inspection (which the daemon couldn't do
anyway once the gate is non-dumpable).

**Depends on:** T1.03, T1.06 (the binary must exist to test end to end; unit
tests don't need it).

**Files:** `crates/kepr-core/src/protocol.rs`; `src/daemon.rs` (one dispatch
arm); create `src/daemon_gate.rs` (add `mod daemon_gate;` next to the other
`mod daemon_*;` lines).

**Public protocol (on the normal socket):**

```rust
// Request
StartGate { routes: Vec<GateRoute> },
// Response
GateStarted { port: u16, placeholders: HashMap<String, String>, gate_pid: i32 },

#[derive(Serialize, Deserialize, Debug, Clone)]
pub struct GateRoute { pub provider: String, pub cred: String, pub slot: u16 }
```

**Private protocol (only on the socket pair; never accepted on the public socket):**

```rust
#[derive(Serialize, Deserialize)] #[serde(tag = "cmd", rename_all = "lowercase")]
pub enum GateRequest { Resolve { name: String, host: String, port: u16 } }
#[derive(Serialize, Deserialize)] #[serde(tag = "kind", rename_all = "snake_case")]
pub enum GateResponse { ResolveOk { value: ZeroString, inject: Inject }, Err { error: String } }
```

Put these two enums in a new file `crates/kepr-core/src/gate_protocol.rs`.

**`handle_start_gate(uid, peer_pid, username, routes) -> Response`:**

1. If `!user_mode()`: return `Response::fail("agent sessions need the user-mode daemon for now")`
   (system mode comes with T1.19). Audit it.
2. Validate: 1..=16 routes, every `cred` passes `validate_name`, slots unique.
3. Generate `session_id` (8 random bytes, hex) and `session_key` (32 bytes) with `getrandom`.
4. `std::os::unix::net::UnixStream::pair()` → `(daemon_end, gate_end)`.
5. Spawn the gate with `std::process::Command`:
   path from the daemon's own env `KEPR_GATE_BIN` (default
   `/usr/local/bin/kepr-gate`); `.env_clear()`; `.env("PATH", "/usr/bin:/bin")`;
   stdin and stdout piped; stderr inherited; in `pre_exec` `dup2` the gate end
   to fd 3 and clear its `FD_CLOEXEC`. Pass `--owner-pid {peer_pid}` (the
   pid comes from `SO_PEERCRED`, never from the request).
6. Write the T1.06 `SessionConfig` JSON to the gate's stdin, then close it.
7. Read the ready line from its stdout (5 s timeout). Parse port and placeholders.
8. Spawn a thread that serves `GateRequest`s on `daemon_end` (framed with
   `kepr_core::framing`) until EOF, calling `resolve_for_gate(uid, ...)`.
9. Return `GateStarted`. Audit `op: "start-gate"` with `Ok`. Zeroize `session_key`.

**`resolve_for_gate(uid, username, name, host, port) -> GateResponse`:**

1. `validate_name(name)`.
2. Read the meta (same helpers `precheck_meta` uses). Require `sealed == Some(true)`; expiry still applies.
3. Find a binding with `host == host.to_lowercase()` and the same port. None → `Err("credential unavailable")`.
4. Decrypt exactly as `handle_get` does after its prechecks (call the same function).
5. Audit `op: "resolve"` with `Ok` or the precise failure reason. Never log the value or the host.

**Tests:** `resolve_for_gate` refuses a non-sealed credential, an unbound
host, a wrong port and an expired credential (all `"credential unavailable"`);
route validation (17 routes, duplicate slot, bad name); JSON round-trips of
all new types; a test that `Request` JSON with `"cmd":"resolve"` does **not**
deserialize on the public socket.

### T1.10 Forwarding proxy (L → do as M by following the steps) 🔒

**Goal:** swap the placeholder for the real key and stream the upstream
response back.

**Depends on:** T1.07, T1.09.

**Files:** create `crates/kepr-gate/src/proxy.rs`; wire it into `main.rs`
replacing the 404 fallback.

**Per request:**

1. `routes::split_path` → provider and rest-of-path; unknown → `404`.
2. Find the route in `SessionConfig.routes` with that provider; none → `404`.
3. Read the credential header for that provider (`Authorization: Bearer X`
   or the named header). Missing, not a placeholder, or `verify` fails →
   `401` with body `{"error":{"type":"kepr","message":"invalid or missing kepr placeholder"}}`.
   The placeholder's slot must equal the route's slot.
4. `vault` cache → real value and inject (host = provider host, port 443).
   Error → `502` with a generic message (no value, no daemon detail).
5. Build the upstream request: `https://{host}{rest}{?query}`, same method,
   same body (streamed, don't buffer), copy headers except hop-by-hop ones
   (`connection`, `keep-alive`, `proxy-*`, `te`, `trailer`,
   `transfer-encoding`, `upgrade`) and `host`; set the credential header
   with the real value per `inject`.
6. Send with a `hyper_util` client using `hyper_rustls::HttpsConnectorBuilder::new().with_webpki_roots().https_only().enable_http1().enable_http2()`.
   Never read proxy settings or CA files from the environment.
7. Stream status, headers (minus hop-by-hop) and body back unchanged
   (Server-Sent Events must flow chunk by chunk).

**Testability:** make the upstream base URL a field of a `Forwarder`
struct; production code always builds `https://{host}`; tests construct a
`Forwarder` pointing at a local plain-HTTP hyper server via a
`#[cfg(test)]`-only constructor.

**Tests (in `proxy.rs` or `crates/kepr-gate/tests/`):** a fake upstream
asserts it received the real key and never the placeholder; a wrong
placeholder gets `401` and the upstream receives nothing; a placeholder for
slot 1 on a slot-0 route gets `401`; a streamed response arrives in at
least two chunks; hop-by-hop headers are stripped.

The image is an optional second store (`KEPR_STORE=image`). The per-file

### T4.01 Vault image: header, slots and noise fill (M) 🔒

*Shipped in 4b95c1c; differs: see status.*

Goal: `VaultImage::create(path, size)` writes a fixed-size file of CSPRNG
noise with an authenticated header, in 4 KiB slots.
Depends on: nothing.
Files: create `src/vault_image.rs` (daemon only; `mod` it from
`src/daemon.rs`).
Add: header in slot 0 = magic `kepr_vi1`, version, image id (16 random
bytes), slot count, epoch (u64), KDF salt, Merkle root (32 bytes), header
MAC. `create(path, size_mib)` uses `fallocate` (fallback: write noise in
1 MiB chunks), `O_EXCL`, mode 0600, fsync. `open(path)` reads the header and
checks magic and size. Size must be a multiple of 1 MiB, 1..=4096 MiB.
Tests: created file has exactly the requested size; two images differ
everywhere except the magic; `open` refuses a wrong magic, a truncated file
and a size that doesn't match the slot count.

### T4.02 Per-slot AEAD and the Merkle root (M) 🔒

*Shipped in ac82d13; differs: see status.*

### T4.04 Journal slot and two-phase commit (M) 🔒

*Shipped in cad1323; differs: see status.*

## Ticket template

Copy this when splitting an L item. A ticket isn't ready for a small model
until every field is filled in with concrete names.

```text
### TX.YY Title (S|M) [🔒 if it touches secrets, auth, crypto or the sandbox]

Goal: one sentence, user-visible outcome.
Depends on: ticket ids, or "nothing".
Files: exact paths to create / modify. Nothing else may change.
Add: exact types, function signatures, protocol variants, CLI syntax.
Steps: numbered, each one checkable.
Tests: named cases with inputs and expected outputs, written first.
Out of scope: what NOT to do in this ticket.
Done when: the standard commands pass (+ any extra command).
```
