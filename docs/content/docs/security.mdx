## Threat Model

Kepr protects against:

| Threat | Protection | Mechanism |
|--------|-----------|-----------|
| **Plaintext on disk** | ✅ Yes | AES-256-GCM encryption at rest |
| **Environment variable snooping** | ⚠️ Delivery-dependent | `exec --memfd` avoids putting values in the environment; protected agent launches use provider-bound placeholders. Ordinary environment delivery exposes values to the receiving process. |
| **Shell history exposure** | ⚠️ Operator-dependent | Masked terminal entry avoids a secret in argv/history; typing a value into a command line still exposes it. |
| **Same-UID process inspection** | ⚠️ Partial | `F_SEAL_WRITE` blocks tampering with the sealed memfd's contents, but a same-uid process can still read it via `/proc/<pid>/fd` where ptrace policy allows |
| **Child process inheritance** | ⚠️ By design | `FD_CLOEXEC` is deliberately *cleared* (not set) so the exec'd agent can read the fd at all; any further descendant the agent spawns also inherits it — this is a consequence of Unix fd inheritance, not an auto-close guarantee |
| **LLM context logging** | ⚠️ Partial | memfd delivery stops *accidental* leakage via `/proc/<pid>/environ`, shell history, and env-dump logging. It does not stop an agent that intentionally reads the fd and echoes the value back into its own output/context |
| **Unattended workstation** | ✅ Yes | Master key locked with Argon2id passphrase (`kepr lock`) |
| **Cross-user isolation** | ✅ Yes | Credentials namespaced by UID; daemon reads peer ID from kernel |

Protected `kepr agent run HARNESS` requires Linux sandbox/network isolation
and snapshots the current folder (or `--workspace PATH`). Host changes require
operator workspace review and digest-approved export. Missing isolation refuses
launch, not a silent unsandboxed retry. Explicit `--compatibility` disables
privacy filtering and required isolation; it is not a credential-recovery fix.
Per-session gate ports/URLs are dynamic unless configured explicitly.

`private-cloud` is bounded local pattern masking, not anonymity or proof of zero
disclosure. The provider sees account identity, public source IP, timing, model
and network metadata; custom encodings and semantic re-identification remain
risks. `local-only` launch is unavailable and stops before starting a cloud
gate. Device-wide offline/egress enforcement is not implemented. Browser,
renderer, telemetry or other apps outside the protected session are not covered.

MCP credentials and SSH keys require explicit grants; database tools default
to read-only with finite request budgets (500/session, 60/minute). Operator
tenant/workspace/connector labels, typed arguments and SQL class checks exist,
but do not establish verified work-IdP identity, exact-action approval or a
remote command/path allowlist. Use least-privilege database roles.

The Linux endpoint adapter requires trusted ClamAV/bubblewrap and official
definitions, scans immutable staged input without network/socket access and
reports unavailable/incomplete executions as `unknown`. Malware detection,
definition-update provenance and quarantine are not qualified guarantees.

Kepr does **NOT** protect against:

| Threat | Why | Mitigation |
|--------|-----|-----------|
| **Compromised root account** | Daemon runs as `root`; attacker gains full system access | Use filesystem encryption (LUKS, FileVault) |
| **Physical memory attacks** | RAM contents in plaintext after decryption | Deploy on trusted hardware; enable DRAM encryption (AMD SME, Intel TME) |
| **Cold boot attacks** | Attacker freezes RAM and extracts keys | Use full-disk encryption; enable Secure Boot & TPM 2.0 |
| **Kernel compromise** | Kernel can read any process memory | Update kernel regularly; use Verified Boot |
| **Compromised systemd** | Daemon service hijacked | Verify systemd binary checksum; audit `/usr/lib/systemd/` permissions |

## Cryptographic Guarantees

### Master Key Protection (Locked State)

**Algorithm**: Argon2id KDF + AES-256-GCM authenticated encryption

- Memory cost: 64 MiB (prevents rainbow table / GPU attacks)
- Time cost: 3 passes (slows brute-force to ~300ms per attempt)
- Salt: 16 bytes CSPRNG (`getrandom`)
- Key derivation: 32-byte output → AES key

**Security**: ~128 bits against online attacks; ~2^40 guesses for 1-hour attack on modern hardware.

### Credential Encryption (Unlocked State)

**Algorithm**: AES-256-GCM with 96-bit nonce per credential

- Nonce: 12-byte random per operation (prevents repeated ciphertext attacks)
- Tag: 16-byte GMAC (detects tampering)
- AAD: Encodes credential name + UID (prevents cross-user or cross-name attacks)

**Security**: 256-bit key strength against brute-force; authentication tag prevents forged credentials.

### Memory Zeroization

**Mechanism**: `zeroize::zeroize` with volatile writes

- All secret buffers use `ZeroString` and `Zeroizing<Vec<u8>>`
- Volatile writes prevent LLVM from optimizing away zeroization
- Occurs on `Drop` automatically for stack and heap allocations

## Known Limitations

### 1. Master Key at Rest (Unlocked)

When the store is unlocked, the 32-byte master key resides unencrypted in the daemon's process memory.

**Mitigation**:
- Use `kepr lock` to encrypt the master key between sessions
- Enable swap encryption (systemd-swap with LUKS)
- Disable swap entirely on sensitive workstations

The daemon's startup path refuses to generate a replacement if the master-key
file is missing while the credential directory is non-empty and no recovery
key is enrolled. With a previously enrolled recovery key it starts locked for
explicit recovery; a protected passphrase envelope also starts locked. Restore
only matching backups or use an enrolled recovery mechanism on a trusted host.
Do not delete/reset key files to bypass the refusal. Vault unlock does not
unseal write-only agent credentials; ciphertext authentication/decryption
failure is a separate fault, not a normal sealed-key refusal or something a
restart repairs.

`kepr-core::keyring::KeyringBackend` uses a permissions-protected raw local
envelope on Linux. Its macOS/Windows placeholders fail closed for seal/unseal
and legacy raw envelopes; they are not native Keychain/DPAPI implementations.
The daemon's separate macOS Keychain sealer exists in source, but native secret
storage, IPC, sandbox, networking, signing and installation remain unqualified.

### 2. Daemon Process Memory

The daemon process holds plaintext secret values in memory during decryption operations.

**Mitigation**:
- Run the daemon on trusted hardware
- Restrict daemon process permissions (`ProtectSystem=strict`, `ReadWritePaths=/etc/credstore.encrypted/`)
- Monitor daemon CPU/memory usage for anomalies

### 3. Unix Socket File Permissions

System mode uses `/run/kepr/kepr.sock`; user mode uses an owner-scoped runtime
socket. Socket access is not blanket permission to read another UID's vault:
the daemon authenticates kernel peer credentials and namespaces credentials by
UID. Permissions, per-credential restrictions and daemon policy all matter.

Audit group membership and socket ownership, and protect the state/credential
directories. Same-user compromise and administrator/kernel access remain
important boundaries; a filesystem ACL is not a substitute for peer identity.

### 4. No Attestation or Trusted Execution Environment (TEE)

Kepr does not use Intel SGX, ARM TrustZone, or AMD SEV.

**Mitigation**:
- Deploy on systems with hardware security modules (Thales Luna, Gemalto)
- Use filesystem encryption for credentials at rest

## Responsible Vulnerability Disclosure

### Report Security Issues

If you discover a security vulnerability, **please do not open a public issue**. Instead:

1. **Email**: security@kepr.dev with:
   - Description of the vulnerability
   - Steps to reproduce
   - Potential impact
   - Your name and contact info

2. **Response SLA**: We will acknowledge within 48 hours and provide a public fix within 7 days.

3. **Responsible Disclosure**: We will coordinate public disclosure with you. You may request attribution in the security advisory.

## Security Audit & Testing

### Source mechanisms and evidence limits

Unit/integration and parser-fuzz targets exist in source; this page is not an
independent cryptographic audit or a fresh execution report. The latest broad
full-suite run was user-aborted. Historical runs and focused checks must not be
represented as current release or native-platform qualification.

The hash-linked credential audit is separate from gate journaling. Gate HTTP
forwarding waits for daemon-fsynced metadata intent; failed persistence blocks
forwarding. Results are attempted at upstream headers/send failure, not after
proof of business completion. Failed result writes cannot undo forwarding;
daemon startup reconciles retained unmatched IDs to `Unknown` and refuses
startup on reconciliation failure. Repeated identical HTTP calls currently
share an ID (empty nonce), so this is not per-attempt idempotency. Actor refs
are session refs, classification/policy fields are fixed labels, and non-HTTP
tool actions do not inherit this guarantee. The separate queued request/usage
journal remains best-effort. No full legal-disclosure ledger is claimed.

### Continuous integration and release acceptance

`ci.yml` defines lint/test checks; `security.yml` defines dependency auditing,
policy checks and bounded scheduled/manual parser-fuzz jobs. Configured jobs
are not proof that a campaign or candidate release passed. PR execution uses
hosted runners and checkout credentials are disabled. Actual repository/tag/
runner protections still require operational review.

`release.yml` resolves an annotated tag on `main` to an immutable commit and
requires Linux qualification before packaging, signing and publication. Its
qualification test/lint commands currently omit `--release`; do not infer
release-mode qualification from a successful binary build. Maintainer
release-mode acceptance commands (not run for this update):

```bash
cargo test --release --workspace --all-targets --locked
cargo clippy --release --workspace --all-targets --all-features --locked -- -D warnings
cargo fmt --all -- --check
```

See the [suite plan](/docs/security-suite-plan) for source locations, scoped
evidence and native-platform, privacy, endpoint and release-assurance gaps.
