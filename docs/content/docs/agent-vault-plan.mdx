# Keeper Parity & Zero-Touch Agent Vault Plan

Status: **shipped, with gaps** (2026-10-14). Every ticket from T1.01 to
T11.24 has shipped, and so have the items built before the tickets
existed (P0, P2.4, P4.3, P5.1, P5.3 and others). Three tickets are
partial: T2.04 placeholder presets (no `git` over HTTPS preset, although
its goal names `git`), T7.16 FIPS mode (HMAC, Argon2id, X25519, ML-KEM and
several AES-256-GCM uses, the vault image's among them, stay outside the
FIPS module) and T8.02 `kepr ui` (its TAGS column is always empty). A few
plan items never became tickets and are not built. The largest is P3.2:
the daemon's master key and the gate's value cache still sit in ordinary
memory, zeroized on drop; only the gate's session key lives in
`memfd_secret` pages (where the kernel offers them). Each phase in
section 9 ends with a status line that names its gaps. Several features
are opt-in rather than the default: the vault image (`KEPR_STORE=image`),
the TPM2 PIN and counter, the KMS and PKCS#11 sealers, FIDO2 unlock and
the `fips` build. Of the 67 Keeper rows in section 2, 43 are ✅, 19 are 🟡
and 5 are out of scope. Each 🟡 cell says what is still missing.
Ticket status: [Agent Vault: Implementation Tickets](/docs/agent-vault-tickets).

The plan has two halves:

1. **Parity.** Everything Keeper Security ships that makes sense for a
   local-first, developer-native vault (verified against Keeper's own docs,
   section 1), plus 17 further features from 1Password, Doppler, Infisical,
   HashiCorp Vault, Teleport, systemd and agent-specific needs (section 2.6).
2. **Zero-touch agent vault.** The user pastes a key **once**. From then on
   any agent harness (oh-my-pi, Grok Build, Claude Code, Codex, Gemini CLI,
   opencode, Aider, Cursor…) and any tool those agents run can *use* the key,
   but no process the agent controls ever *holds* it: not in the environment,
   not in a file, not in an inherited fd, not in the agent's address space.
   At rest it lives in a hardware-bound, fixed-size encrypted vault image; in
   use it lives in kernel-hidden memory of a separate, non-dumpable process.

## 0. TL;DR

| Question | Answer in this plan |
| --- | --- |
| How is this different from Keeper's agent support? | Keeper's Agent Kit and local MCP let the agent fetch the plaintext itself (protecting chat history and git, not the agent's own process). kepr never gives the agent the value. See section 1.1. |
| How does an agent use a key it never sees? | `kepr-gate`, a credential-injecting proxy. The agent is configured with a worthless placeholder (`kepr-ph-…`) and a gate base URL; the gate swaps in the real key on the wire, only toward the hosts that key is bound to. |
| How is the agent kept from bypassing the gate? | `kepr agent run` starts the harness in its own PID and mount namespaces (unprivileged userns) with Landlock rules, so it can't see the gate, the daemon or the vault. With `--isolate-net` it also gets its own network namespace, whose only route off the box is the gate; without it, the harness keeps the host network but holds only placeholders. |
| How does the user configure each harness? | `kepr agent install omp\|grok` writes the harness's own config file (base URL + placeholder variable) once. Claude Code, Codex, Aider and grok-cli need no install step: they read the variables `kepr agent run HARNESS` sets. |
| Can anyone read the key back? | Sealed credentials (what `kepr agent add` stores) are **write-only**: the daemon refuses `Get` for them. Only the gate can resolve them, and only for a bound destination. |
| How is it stored on disk? | A pre-allocated, fixed-size, noise-filled vault image with randomised slot placement, per-record keys, a Merkle root, and a TPM2-sealed key-encryption key with an anti-rollback NV counter. |
| How is it held in RAM? | `memfd_secret(2)` pages (removed from the kernel direct map, unswappable, no core dump, no `/proc/pid/mem`), guard pages, random placement, periodic relocation, XOR key-splitting, inside a non-dumpable process. |
| What stops an agent misusing a key it can use? | Destination binding, per-agent approvals, spend caps, prompt DLP, output masking, honeytokens and one-command leak response (P9). |
| Do random addresses stop a physical attacker? | Not on their own, and this plan says so plainly. Randomisation hides metadata (count, sizes, access pattern). What stops a physical attacker is encryption bound to the TPM + measured boot + PIN, memory encryption (TME/SME) and IOMMU. See section 7. |

### 1.1 What Keeper's own docs reveal

Four findings from Keeper's documentation shape this plan:

1. **Keeper's agent integrations hand plaintext to the agent.** The Agent Kit
   is a set of `SKILL.md` files that teach the agent to run `ksm` and
   `keeper` itself, and the local MCP service offers a "Read secrets" tool.
   Either way the decrypted value ends up in a process the agent controls.
   Keeper's model protects *chat history and source control*. kepr's gate
   model also protects against the agent itself.
2. **Keeper warns about its own `ksm exec`.** Its docs say the substituted
   values "are inherited by the child process's environment" and readable via
   `/proc/<pid>/environ`. That's exactly the leak kepr was built to remove.
3. **Keeper's "Privacy Screen" is visual only.** Keeper states the hidden
   password "is still stored in the user's vault and accessible via API
   communication and browser inspection". kepr's sealed credentials (section
   4.3) enforce the same idea in the daemon: there is no API that returns them.
4. **Keeper is converging on the same broker design for infrastructure.**
   Connection Manager, Tunnels and the KeeperDB proxy all inject credentials
   at a gateway so "end users never see, type or store the credential".
   `kepr-gate` brings that model to a single developer laptop and to AI
   agents, without a cloud gateway.

## 3. What is wrong with today's agent protection

Two defects in the shipped `kepr protect-agent` path motivate P0:

1. **The harness never finds its key.** `cli_agent.rs` calls
   `cli_exec::cmd_exec(&[], &memfd_keys, argv)`. That exports only
   `KEPR_FD_ANTHROPIC_API_KEY=3`, and Claude Code, Grok, oh-my-pi and the rest
   read `ANTHROPIC_API_KEY` / `XAI_API_KEY`, not a kepr-specific fd variable.
   The protected agent starts without credentials.
2. **The memfd leaks to every subprocess.** `memfd.rs` clears `FD_CLOEXEC` so
   the fd survives `exec`. Every shell the agent spawns therefore inherits
   fd 3, and `cat <&3` (or `cat /proc/self/fd/3`) prints the key. A
   prompt-injected agent gets the secret in one tool call. The sealing stops
   *modification*, not *reading*.

memfd delivery is still right for a cooperating application that reads its
fd once and closes it (`kepr exec --memfd` for your own service). It is the
wrong primitive for an untrusted, tool-running agent. The fix is to never
hand the agent the key at all.

## 4. Zero-touch agent design

### 4.1 Invariants

- **I1. Write-only after capture.** A sealed credential's plaintext leaves
  the daemon only toward `kepr-gate`, never in a `GetOk`, `env`, `--export`,
  `exec --env`, sync push, or MCP reply.
- **I2. Destination binding.** Each sealed credential carries an allowlist of
  `(scheme, host, port, header/field)` targets. The gate refuses to inject it
  anywhere else, so a prompt-injected agent cannot send it to an attacker's
  server even by asking the gate.
- **I3. No ambient path.** Inside `kepr agent run` the agent cannot see the
  gate's or daemon's processes, and cannot read the vault directory or reach
  the daemon socket. With `--isolate-net` it also has no route to the network
  except the gate; without it, the agent keeps the host network but holds
  only placeholders. The sandbox is best-effort: when the kernel can't
  provide it, the harness runs unsandboxed with a warning, unless
  `--strict-sandbox` or `--isolate-net` is given.
- **I4. Placeholders are worthless.** What the agent sees (`kepr-ph-…`) is
  bound to one session id, valid only inside that session's namespace, and
  useless if exfiltrated.
- **I5. Fail closed.** If the gate, daemon or namespace setup fails, the
  agent does not start or gets a 401, never a fallback to plaintext env.

### 4.2 Components

```text
 user (once)                                          upstream APIs
   │ kepr agent add ANTHROPIC_API_KEY --for api.anthropic.com          ▲ TLS (rustls,
   ▼                                                                   │  pinned roots)
┌───────────────┐ private socketpair (fd3)┌──────────────────────────┐ │
│  kepr-daemon  │◀── Resolve{name,dest} ──│  kepr-gate               │─┘
│ vault image,  │  daemon spawns the gate │  own uid (system mode),  │
│ master key    │── value (framed JSON) ─▶│  non-dumpable, value     │
└───────────────┘                         │  cache, policy, journal  │
                                          └────────────▲─────────────┘
                                                       │ --isolate-net: each connection
                                                       │ relayed out over SCM_RIGHTS
┌──────────────────── kepr agent run omp ──────────────┼──────────────────────┐
│ new user+pid+mount namespaces (+net with --isolate-net), Landlock, seccomp  │
│                                                                             │
│  omp / grok / claude  ── http://127.0.0.1:7878/anthropic ──┘                │
│   env: ANTHROPIC_API_KEY=kepr-ph-7f3a…   (placeholder, not a secret)        │
│   tools it spawns (curl, gh, git, aws) ── HTTPS_PROXY=127.0.0.1:7879 ──┘    │
│   cannot see gate/daemon PIDs · vault dir hidden · --isolate-net: no other  │
│   route out (without it: host network, placeholders only)                   │
└─────────────────────────────────────────────────────────────────────────────┘
```

The value travels from the daemon to the gate as a length-prefixed JSON
frame over the private socket pair, and the gate caches it in its own
memory (section 6.1).

Why a separate gate binary: the daemon's unit has
`RestrictAddressFamilies=AF_UNIX AF_NETLINK` and should keep it. The gate
needs outbound TCP. Splitting them keeps the vault process network-free and
puts the only network-facing code under a different uid that holds no master
key. The one exception is an opt-in cloud key-service sealer (P4.6), which
the daemon calls when it starts. It also keeps `hyper` and tokio out of the
daemon: they are dependencies of `kepr-gate` only, so the daemon's
dependency tree and attack surface don't grow.

### 4.3 Sealed credentials (daemon side)

- `.meta` gains `sealed: bool` and `bindings: [{host, port, scheme, inject}]`
  where `inject` is one of `header:Authorization:Bearer`, `header:x-api-key`,
  `query:key`, `basic:password`, `sigv4`.
- `handle_get` returns the generic `"credential unavailable"` for sealed
  credentials (same sanitised error, so callers can't probe which ones are
  sealed) and audits op `get` with `KEPR_RESULT=fail: sealed`.
- The daemon **starts the gate itself** (`Request::StartGate`), with a
  cleared environment and one end of a private socket pair on fd 3. Sealed
  values are resolved only over that socket pair (`GateRequest::Resolve
  { name, host, port }`), never on the public socket. That rules out an agent
  launching its own gate under a debugger or with `LD_PRELOAD`, and needs no
  `/proc` inspection of the gate (which a same-uid daemon couldn't do once
  the gate is non-dumpable). In system mode the gate is its own service
  account and the daemon accepts the private channel only from that uid.
  The daemon checks the host against `bindings` itself; it does not trust
  the gate's policy alone.
- `Unseal` is deliberately absent. Changing a binding or un-sealing requires
  re-entering the value (`kepr agent add` again) or a FIDO2 touch plus polkit.
  The user "sees it once" when pasting it, and never again unless they choose
  to re-paste.

### 4.4 kepr-gate modes

**API mode (P1).** The harness's base URL points at
`http://127.0.0.1:7878/<provider>`. The gate maps `/<provider>` to a pinned
upstream (`/anthropic` → `https://api.anthropic.com`, `/xai` →
`https://api.x.ai`, `/openai` → `https://api.openai.com`, …), checks that the
request's auth header carries this session's placeholder, swaps in the real
key, and streams the response (SSE) back. Plain HTTP on loopback is fine
here: it carries only placeholders, and under `--isolate-net` it never
leaves the session's private network namespace.

**Egress mode (P2).** For tools the agent runs (`curl`, `gh`, `git`, SDKs),
the sandbox sets `HTTPS_PROXY` / `HTTP_PROXY` to the gate and trusts a
per-session CA (`SSL_CERT_FILE`, `NODE_EXTRA_CA_CERTS`, `REQUESTS_CA_BUNDLE`,
`GIT_SSL_CAINFO`). On `CONNECT` to a host that has a binding, the gate
terminates TLS with a leaf minted from that CA, substitutes placeholders found
in the bound header or field, and re-originates TLS to the real host. By
default, hosts with no binding are tunnelled blind and each `CONNECT` is
journalled; the session holds no real key, so no key can ride the tunnel.
With `kepr agent run --isolate-net` the harness gets a private network
namespace where only the gate, database and `--tunnel` ports are reachable,
and the gate refuses unbound hosts other than the `--tunnel` targets
(bound-only). The CA private key exists only in gate memory for the life of
the session.

| Consumer | Mechanism |
| --- | --- |
| Bearer / API-key headers (OpenAI, Anthropic, xAI, GitHub, Stripe, GCP) | straight substitution |
| HTTP Basic (registries, Jira) | decode, substitute password, re-encode |
| AWS SigV4 | client signs with placeholder secret; gate verifies against the placeholder, then **re-signs** with the real key (`kepr_core::sigv4`, shared with `kepr sync`, implements the derivation chain) |
| git over HTTPS | `git-credential-kepr` returns the placeholder inside a session; gate substitutes |
| SSH | `kepr ssh-agent` (P2.4): private keys stay in the daemon, only sign operations cross the socket |
| Postgres / MySQL / Redis | P7.1 protocol proxies: the agent authenticates to the gate with the placeholder, the gate does SCRAM/native auth upstream |

### 4.5 Caller authentication

- Under `--isolate-net`, the sandbox listens on the gate's port inside the
  session's network namespace and **passes** each connection out (via
  `SCM_RIGHTS`) to a relay that connects it to the gate. Only processes in
  that namespace can reach it. Without `--isolate-net` the gate listens on
  the host's loopback, where a request without this session's placeholder
  gets nothing.
- Placeholders encode `session_id ‖ cred_slot ‖ HMAC(session_key, …)`. A
  placeholder from session A is rejected in session B.
- Session lifetime is tied to the harness process via a pidfd. When the
  harness exits, the gate drops the session, its placeholders and its CA.

### 4.6 Harness adapters: "install once"

For harnesses that read a fixed base URL from a file (omp, Grok Build),
`kepr agent install HARNESS` edits the harness's own config so nothing has
to be exported in a shell. It writes only base URLs and placeholder
*variable names*. `kepr agent run` supplies the placeholder values. The
other harnesses read the environment `kepr agent run` sets.

| Harness | Config it writes | Notes |
| --- | --- | --- |
| oh-my-pi (`omp`) | `~/.omp/agent/models.yml`: `providers.<p>.baseUrl: http://127.0.0.1:7878/<p>`, `apiKey: KEPR_PH_<P>` | `apiKey` names an env var, so the placeholder goes there |
| Grok Build (xAI) | `~/.grok/config.toml`: `[model.<k>] base_url = "http://127.0.0.1:7878/xai/v1"`, `env_key = "KEPR_PH_XAI"` | |
| grok-cli (community) | `GROK_BASE_URL`, `GROK_API_KEY` = placeholder | env only, but values are worthless |
| Claude Code | none: `kepr agent run claude` sets `ANTHROPIC_BASE_URL` and `ANTHROPIC_API_KEY` = placeholder | env only |
| Codex CLI | none: `kepr agent run codex` sets `OPENAI_BASE_URL` and `OPENAI_API_KEY` = placeholder | env only |
| Aider | none: `kepr agent run aider` sets `OPENAI_API_BASE` and `OPENAI_API_KEY` = placeholder | env only |
| Gemini CLI, opencode | per-tool base-URL override + placeholder | open: T12.13 |

Placeholders are per session, so a fixed value in `~/.claude/settings.json`
`env`, an `apiKeyHelper` or `~/.codex/config.toml` would apply outside
sessions and compete with each session's own placeholder. Cursor CLI has no
adapter: it sends model calls to Cursor's own service, not to a provider API
the gate could front.

Then a shell shim (`~/.local/bin/omp` → `kepr agent run omp -- <real omp>`)
or a one-line alias means the user just types `omp` or `grok` as before. A
`kepr agent doctor` check verifies each harness's config still points at the
gate after harness upgrades rewrite their config files.

### 4.7 Capture once

- `kepr agent add NAME [--for HOST…]` prompts with masked TTY entry (existing
  `cli_input.rs`) or reads the clipboard once (`--from-clipboard`, Wayland
  `wl-paste` / X11 `xclip`) and then **clears the clipboard**.
- Known key formats (`sk-ant-`, `xai-`, `sk-`, `ghp_`, `AKIA`, `glpat-`…)
  pre-fill `--for` bindings so the user normally types nothing but the paste.
- `kepr agent adopt` scans `.env`, `.env.local`, `.envrc`, `~/.bashrc`,
  `~/.zshrc`, `~/.config/fish/config.fish` and the other shell startup files
  for known key formats (harness config files and shell history: open,
  T12.18, T12.19). It lists what it found (file:line, NAME, provider; never
  values) and changes nothing without `--yes`, which imports each key
  sealed; `--remove` also deletes the adopted lines. No backup is kept: the
  keys are sealed now, and a backup of the old lines would be a second copy
  of a sealed value that someone could read back.

### 4.8 `kepr mcp`

For agent platforms that prefer tools over base-URL rewiring:

- `list_secrets` returns names, bindings and expiry, never values.
- `call_api(provider, method, path, headers, body)` sends the request to
  that provider's API host through a gate session (the key is
  binding-checked and added by the gate) and returns the response.
- `db_query(target, sql)` runs one SQL statement through the gate's PostgreSQL proxy with
  the session placeholder (`--read-only` refuses writes), and `ssh_run(host,
  cmd)` runs a command over ssh through a private agent socket whose keys
  sign in the daemon (T9.05).
- No tool ever returns plaintext. This is the inverse of Keeper's MCP server,
  which returns secret values into the model's context.

### 4.9 What an agent can still do

A compromised or prompt-injected agent inside a session can still **use** a
bound key toward its bound host (for example, burn API credit or call a
GitHub endpoint the token allows). Mitigations: per-credential rate and
spend caps in the gate, path-template allowlists (`api.github.com` `GET
/repos/**` only), per-use approval for high-risk credentials (polkit / FIDO2,
already shipped), anomaly alerts (P7.5) and the request journal. It cannot
**read**, **copy** or **redirect** the key. That is the guarantee.

## 5. Storage: the sealed vault image

### 5.1 A note on "random disk addresses"

Putting secrets at random offsets is security through obscurity if it is the
only defence: an attacker with a disk image can read every block. In this
design randomised placement has one specific job, **metadata hiding**: an
attacker who images the disk cannot tell how many secrets exist, how large
they are, which slot changed between two images, or which slot is "the AWS
key". Confidentiality and tamper detection come from cryptography bound to
hardware (section 5.3). Both together are worth having.

### 5.2 Format

- **Fixed-size image.** `kepr vault init --size 64M` creates `vault.img` in
  the store directory (1 to 4096 MiB), reserved with `fallocate`. The 64 MiB
  default and the `64M` spelling are open (T12.26); today the default is
  16 MiB and `--size` takes whole MiB. The image is filled with CSPRNG output, so
  empty and used slots look the same. Size never changes, so it leaks
  nothing about the vault's contents. A raw partition or LVM volume is not
  supported: the system unit runs with `PrivateDevices=yes`, and a device
  would hide only the file's timestamps.
- **Slots.** The image is divided into 4 KiB slots. Each record (value +
  `.meta` + history) is padded to a size bucket and written to a slot index
  drawn from `HMAC(slot_key, record_id ‖ epoch)` mod N, with linear probing.
  Every write also rewrites a few random decoy slots with fresh noise, so a
  before/after diff of two images doesn't reveal which record changed.
- **Per-slot AEAD.** AES-256-GCM with a fresh random 96-bit nonce for every
  seal and AAD = `image_id ‖ slot_index ‖ epoch`, so a slot cannot be moved
  or replayed into another position. Record pages are sealed under a record
  key drawn fresh on every write, so each key seals only that record's few
  pages. The header, journal and index keys seal at most a few hundred slots
  per commit, far inside GCM's limit for random nonces at any realistic
  write rate. A nonce-misuse-resistant mode (AES-256-GCM-SIV or
  XChaCha20-Poly1305) would need a new image version and is not planned.
- **Merkle root.** A hash tree over the slots the current state uses (index
  and record pages; free slots are noise), with the leaf count hashed into
  the root. The root and epoch are authenticated in the header. The daemon
  keeps the highest epoch it has seen in its rollback state
  (`cred-versions.json`) and refuses an older image; binding the epoch to a
  counter off the disk, such as a TPM NV index, is open (T12.27, T12.30;
  anti-rollback, section 5.3).
- **I/O.** Slots are sealed in memory before they are written, so only
  ciphertext reaches the page cache or the disk. Writes are positioned
  `pwrite`s with an `fdatasync` after each phase of a two-phase commit
  (journal slot, then the new pages, then the header flip, then scrubbing
  what was freed), which makes writes crash-safe. `O_DIRECT` is not used: it
  would add alignment rules and protect nothing, since the page cache never
  holds plaintext.
- **Erasure.** SSD wear-levelling means overwriting a block does not erase
  it. Deletion is **crypto-shredding**: each record has its own key, wrapped
  under the vault master key; deleting the record destroys its wrapped key
  and bumps the epoch.
- **Migration.** `kepr vault migrate` moves each per-file credential into
  the image and reads it back, then deletes the file and tombstones its
  rollback counter, so a restored copy is refused. The files are not
  crypto-shredded: the image's keys derive from the same daemon master key,
  so an older backup of the credential directory plus that key still opens
  them. That is the same limit as the image's own crypto-shred, which covers
  the current image only; shredding them would need a master-key rotation,
  which kepr does not have. The per-file store stays the default.

### 5.3 Key hierarchy

```text
sealer, chosen with KEPR_MASTER_KEY_SEAL and KEPR_TPM2_* (section 9, P4):
  TPM2: optional PCR policy (KEPR_TPM2_PCRS), PIN (TPM dictionary-attack
        lockout), NV anti-rollback counter; salted, encrypted TPM sessions
        against LPC/SPI bus sniffing are open (T12.29)
  or the host key, a key service (AWS, GCP or Azure KMS, PKCS#11),
  the macOS keychain, an owner-only file (user mode),
  or, after kepr lock, an Argon2id passphrase [+ FIDO2 hmac-secret]
  └─ daemon master key, the image's KEK (256-bit random, sealed at rest;
     │                    where it sits in RAM: section 6)
     │  per operation, never stored, wiped after use:
     │  HKDF-SHA256(master key, image salt) gives
     ├─ header key, journal key
     ├─ placement key   (slot placement PRF)
     └─ vault master key (VMK)
          ├─ index key = HKDF(VMK, "index")   (seals the name → record index)
          └─ record keys (a fresh random AES-256 key on every write,
             AES-256-GCM-wrapped by the VMK)
               └─ value, fields, history, attachments
```

- **Anti-rollback.** A TPM NV monotonic counter stores the epoch. On open,
  an image with an older epoch than the counter is rejected. Restoring an
  old disk image does not resurrect a revoked key. Open: T12.27, T12.30.
  Today the TPM2 counter guards the sealed master key, and the image's
  epoch high-water mark sits in `cred-versions.json` on the same disk, so an
  old copy of the image alone is refused, but not one restored together
  with that file.
- **Evil maid.** A changed bootloader, kernel or cmdline changes PCRs, so the
  KEK will not unseal. The daemon fails closed and asks for the recovery
  passphrase (Argon2id path, already shipped; for a sealed master key,
  open: T12.32).
- **Recovery.** At enrolment the master key is also wrapped under a
  high-entropy recovery key that is shown once, printable as words and a QR
  code, and optionally Shamir-split (P6.3). Today a passphrase-protected
  store can export its master key as words or Shamir shares
  (`kepr recovery-kit create [--words]`); a recovery key for a sealed master
  key is open (T12.31, T12.32).
- **Backends without a TPM** fall back to the shipped Argon2id envelope,
  clearly reported by `kepr status` and never silently (naming the sealer
  in `kepr status`: open, T12.33).

## 6. RAM: the secret enclave

The key has to be in plaintext somewhere while it's in use. The aim is to
make that place as small, short-lived, hidden and hostile to readers as Linux
allows, and to put it in a process the agent cannot touch.

### 6.1 Where plaintext may exist

| Process | Holds | Never holds |
| --- | --- | --- |
| `kepr-daemon` | master key, the image keys derived from it (VMK), record keys, decrypted values on demand | network sockets, except with an opt-in cloud key-service sealer (T4.11, T4.12), which makes its HTTPS call when the daemon starts; the system unit allows IP only through the `kms.conf` drop-in |
| `kepr-gate` | values its session has resolved. Each is fetched from the daemon again after 5 min (cache TTL), and all are dropped at once when the store changes, and when the gate stops: `kepr panic`, suspend or screen lock (user mode), session end. Until then the prompt DLP and the journal and recording scrubbers match against them. A plain `kepr lock` emptying them too is open (T12.23) | master key, VMK, other users' values |
| agent and its tools | placeholders only | any real value |

### 6.2 Kernel and process hardening (daemon and gate)

- **`memfd_secret(2)`** (Linux 5.14+; check `secretmem.enable` on older
  kernels): pages are removed from the kernel's direct map, cannot be
  swapped, are excluded from core dumps and hibernation images, and cannot be
  reached through `/proc/pid/mem`, `process_vm_readv` or ptrace peeks. Hold the
  VMK, record keys and the gate's value cache here. Fallback when unavailable:
  `mmap` + `mlock` + `MADV_DONTDUMP` + `MADV_WIPEONFORK`, reported by
  `kepr doctor`.
- **Random placement + guard pages.** Each secret region is mapped at a
  CSPRNG-chosen, page-aligned hint address in the 47-bit user space, with
  `PROT_NONE` guard pages on both sides. A stray read or overflow faults
  instead of leaking a neighbour.
- **Relocation.** Every 60 s (and after each unlock) the enclave allocates a
  fresh region at a new random address, copies, and zeroises + unmaps the
  old one. A memory snapshot taken at one moment doesn't tell you where the
  key will be later.
- **XOR splitting.** The VMK is stored as two shares `A` and `B = VMK ⊕ A` in
  separate random regions, re-randomised on every relocation. It is
  recombined into a stack buffer only for the microseconds an AEAD call takes,
  then zeroised. This defeats scanners that look for AES key schedules in
  cold-boot dumps.
- **Process posture.** `prctl(PR_SET_DUMPABLE, 0)` (also makes
  `/proc/pid/mem` root-owned), `PR_SET_NO_NEW_PRIVS`, `mlockall` (already
  shipped), `RLIMIT_CORE = 0`, Landlock ruleset, seccomp allowlist, and a
  dedicated uid for the gate.
- **Host recommendations** surfaced by `kepr doctor`: Yama
  `ptrace_scope ≥ 2`, `lockdown=confidentiality` (blocks root reading kernel
  memory via `/dev/mem`, kprobes, eBPF), swap encrypted or disabled,
  hibernation disabled or encrypted, IOMMU enabled with Thunderbolt DMA
  protection.

### 6.3 Hardware memory protection

| Technology | Protects against | kepr action |
| --- | --- | --- |
| Intel TME / TME-MK, AMD SME | cold-boot RAM removal, bus snooping on DIMMs | `kepr doctor` detects and recommends enabling in firmware |
| AMD SEV-SNP, Intel TDX | a malicious hypervisor reading guest RAM | supported transparently; documented for cloud VMs |
| IOMMU (VT-d / AMD-Vi) | DMA attacks through Thunderbolt / PCIe | doctor check; documented as required for "physical attacker" claims |
| TPM2 | offline disk theft, evil maid, rollback | section 5.3 |
| Intel SGX | — | not used: deprecated on client CPUs and repeatedly broken by side channels |

### 6.4 When a process must hold a key itself

Some consumers can't go through the gate (your own service reading a DB
password). For those, **pull-on-demand** sits beside inherited memfds: the
process connects to the daemon socket and sends `FetchFd`. The daemon
applies `Get`'s checks (the `SO_PEERCRED` uid, expiry, re-authentication,
consent, and the credential's executable-digest binding if it has one),
replies `FdOk`, then passes a sealed, close-on-exec memfd via `SCM_RIGHTS`.
The consumer reads it and closes it, and nothing it starts inherits it. Its
pages are ordinary shared memory, so encrypt swap. There is no per-launch
token: the same uid may call `Get` on that credential anyway, and the
executable binding already narrows which programs may. A `memfd_secret` fd
is not used either: it can't be sealed or `read()`, so every consumer would
need `mmap`. `kepr_core::fdfetch` is the Rust helper; the Python client has
`fetch_fd` and the Go client `FetchFD`. Node.js has none, because it can't
receive descriptors.

## 7. Threat model: physical and local attackers

| Attacker | Defence | Residual risk |
| --- | --- | --- |
| Steals a powered-off laptop / disk | TPM-sealed KEK + PIN, fixed-size noise-filled image | none beyond brute-forcing the PIN, which the TPM's lockout throttles |
| Evil maid (modifies boot chain, returns laptop) | PCR policy; KEK won't unseal | user must notice the recovery prompt and not type the recovery key into a tampered system |
| Sniffs the TPM bus | salted, parameter-encrypted TPM sessions | firmware TPM (fTPM) avoids the bus entirely |
| Cold-boot RAM dump | TME/SME memory encryption, memfd_secret, XOR splitting, relocation | without TME/SME, a skilled attacker with liquid-cooled DIMMs can still try; splitting raises the cost |
| DMA via Thunderbolt / PCIe | IOMMU + kernel DMA protection | firmware with IOMMU disabled |
| Rolls the disk image back to an older snapshot | TPM NV monotonic counter (for the vault image, open: T12.27, T12.30) | none |
| Edits ciphertext on disk | per-slot AEAD + Merkle root | denial of service (corrupt image); keep encrypted backups |
| Prompt-injected agent | sealed creds, gate, namespaces, destination binding | can *use* bound keys toward bound hosts until revoked (section 4.9) |
| Same-uid malware outside the sandbox | gate uid separation, non-dumpable processes, `ptrace_scope` | can drive the gate like the agent would: same residual as the row above |
| Root on the running, unlocked machine | `lockdown=confidentiality` raises the bar | root can ultimately read any process memory or load a module. No pure-software vault defends against live root, and kepr won't claim to |

## 8. Kernel and OS feature detection

`kepr doctor` gains a "hardening" section that reports, for each item above,

- P3.4 `kepr doctor` hardening section (section 8).

  `kepr unlock`. Lid close is covered through logind, which turns it into
  suspend or lock. A store without a passphrase keeps its key in RAM: its
  key file is on the same disk and is read back without user input, so
  wiping the key would not protect a sleeping laptop (`kepr lock` sets a
  passphrase). `kepr panic` does the same on demand. The system daemon
  doesn't watch for sleep. Open: screen locks that only set logind's

  emptying all gate caches, with root's `kepr panic` stopping every user's

`--memfd`, which still hands the command inherited descriptors. P3.5
(T3.05): on suspend or screen lock the user-mode daemon stops every gate
and locks a passphrase-protected store, and `kepr panic` does the same on
demand. Not built: P3.2 (T12.21, T12.02). Only the gate's
session key uses `secmem`; the daemon's master key and the gate's value
cache sit in ordinary memory, zeroized on drop. The system daemon locks
all its pages with `mlockall`; a user-mode daemon under a small
`RLIMIT_MEMLOCK` locks only the pages mapped at start, so later
allocations, the master key's among them, are not guaranteed to be
locked. Also not built: the relocation timer (`SplitKey::relocate`
exists, but nothing calls it; T12.22) and locking when a security key is
removed (T12.25). With `KEPR_FINGERPRINT_UNLOCK` set (P10.3), the sleep and idle
locks keep a passphrase-protected store's master key in memory for that
window too.

### P4: vault image and hardware-bound keys (shipped)

- P4.1 Vault image format (slots, noise fill, AEAD, Merkle root, journal),

- P4.2 Record keys + crypto-shred delete; `kepr vault init | migrate | verify`.

- P4.3 TPM2 sealer (feature `tpm2`, `tss-esapi`): PCR policy + PIN, salted

- P4.5 Recovery key (words + QR) at enrolment.
- P4.6 External key wrapping (bring your own key): AWS KMS, GCP KMS, Azure
  Key Vault and PKCS#11 HSMs (YubiHSM among them) as alternative KEK

  the daemon starts with a key service configured, and the system unit

**Status (2026-10-14): shipped** (T4.01–T4.14). The vault image is opt-in:
run the daemon with `KEPR_STORE=image`, then `kepr vault init` (16 MiB by

The per-file store stays the default. Slots use AES-256-GCM with random
nonces (section 5.2). P4.3's PIN
and NV counter (T4.08) run tpm2-tools rather than a `tpm2` cargo feature
(`KEPR_TPM2_PIN`, `KEPR_TPM2_PIN_FILE`, `KEPR_TPM2_NV_INDEX`,
`KEPR_TPM2_PCRS`); the counter guards the sealed master key, and the image
refuses an older copy of itself through an epoch high-water mark. P4.4 is
`kepr lock --fido2`, P4.5 `kepr recovery-kit create --words`, P4.6
`KEPR_MASTER_KEY_SEAL` set to `aws-kms:`, `gcp-kms:`, `azure-kv:` or
`pkcs11:`. Not built: salted, encrypted TPM sessions on the tpm2-tools
path (T12.29), an anti-rollback anchor for the image's epoch off the disk,
such as a TPM NV index (T12.27, T12.30), resizing an image, and moving back
to per-file storage.

### P9: agent safety extras (shipped)

These turn the gate from "the agent can't read the key" into "the agent
can't misuse it quietly either". P9.1–P9.3 should ship right after P1.

- P9.1 Approvals (A3): a credential marked `--requires-consent` is released
  to a gate only after the user approves the agent process: through polkit
  by default, or through a desktop notification or ntfy push when the
  credential has `approve_via` set (`kepr approvals set`) and
  `kepr approvals serve` is running. An approver that doesn't answer within
  60 s denies. The gate keeps an approved value for at most 5 minutes, or
  until the store changes, so one approval covers a burst. Standing approval
  is a time-boxed JIT grant (`kepr grant KEY --to HARNESS --for 2h`, closed
  with `kepr grant KEY --revoke`) or an M-of-N window (P7.4); there is no
  stored "always".
- P9.2 Prompt DLP (A1): before forwarding a request, the gate scans its body
  (raw and JSON-unescaped), path, query and header values for every value
  this session has resolved (8 bytes or longer, a substring search) and for
  known key formats, and refuses compressed request bodies it can't scan.
  Other stored values are deliberately not matched (section 2.6, A1). A match
  **blocks** the request: the gate never forwards it, returns an error the
  harness shows to the agent (HTTP 403 with a provider-shaped JSON error body:
  "kepr blocked this request: it contains the stored secret NAME; remove it
  and retry"), and audits the event. It never redacts silently.
- P9.3 Output masking (A2): `kepr exec --mask` and gate egress responses
  replace any stored secret value in stdout/stderr or response bodies with
  `****`.
- P9.4 Agent tools for databases and SSH through the gate (P7.1 / P2.4),
  with optional read-only mode and an "AI context" note per target.
- P9.5 Spend and rate guard (A4): parse token usage from provider responses;
  per-session and per-day caps; hard stop with a clear error to the harness.
- P9.6 Governance report: which agent used which secret, where, how often,
  cost, plus unused / stale / over-scoped keys (A15).
- P9.7 Honeytokens (A5): `kepr canary plant` writes decoy keys; the gate and
  optional provider-side canaries alert on use.
- P9.8 Leak response (A6): `kepr leaked NAME` stops the user's gate sessions
  (their placeholders die with them), deletes the key and its history,
  records a `leak-incident` in the audit chain, and points at the
  provider's revocation page. With `--rotate`, an AWS IAM user key that
  `get` can read is replaced through IAM; STS and GitHub App tokens expire
  on their own.

**Status (2026-10-14): shipped** (T9.01–T9.09). P9.1 approvals are asked
per use, through polkit or, with `kepr approvals serve`, a desktop or ntfy
notification; `kepr grant` opens a time-boxed window per harness. P9.2
scans each HTTP request the gate reads (not traffic it tunnels to unbound
hosts) for the keys the session has resolved and for known key formats.
P9.3 is `kepr exec --mask`. P9.8 is `kepr leaked KEY [--rotate]`. Not
built: masking of stored values in gate responses (T12.01), and rotation of
a sealed key or through other providers' APIs.

## 10. Decisions (resolved 2026-10-04)

1. **Gate dependencies: `hyper`.** It is the more robust choice: a
   battle-tested HTTP/1.1 implementation with streaming bodies, upstream
   connection pooling and well-handled edge cases (chunked encoding,
   keep-alive, backpressure) that a hand-rolled parser would have to re-earn.
   Raw speed is not the deciding factor (the gate's latency is dominated by
   the upstream LLM API). HTTP/2 is left off: it would add about 400 KB to
   `kepr-gate`, every provider API serves HTTP/1.1, and pooled keep-alive
   TLS connections already avoid a handshake per request. The egress CA's
   TLS server offers ALPN `http/1.1` only, so HTTP/2-only clients (gRPC)
   can't use an intercepted host. Turning on hyper's `http2` features is a
   later change, if the request journal shows a need. Cost: tokio and hyper
   join the dependency tree, of `kepr-gate` only.
2. **Sealed by default: yes.** `kepr agent add` seals by default, and so do
   `kepr import --seal`, `kepr discover --seal` and `kepr agent adopt` for
   the provider keys they recognise. Plain `kepr set` stays readable for
   backwards compatibility, and a `kepr set` over a sealed credential keeps
   it sealed. There is no `kepr set --sealed`: a sealed key needs the
   destination bindings that `kepr agent add NAME --for …` sets, and
   without one no gate could ever release it.
3. **Unprivileged user namespaces: ship an AppArmor profile** for `kepr`
   (needed on Ubuntu 24.04+). No setuid helper. `kepr doctor` reports when the
   profile is missing or namespaces are disabled.
4. **Vault image: 64 MiB default (open: T12.26); the per-file store stays
   the default** on hosts without a TPM until P4 has a release behind it.
5. **Prompt DLP: block and tell the agent.** No silent redaction (P9.2).
