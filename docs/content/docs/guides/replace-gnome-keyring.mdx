---
title: "Replace GNOME Keyring"
description: "Make kepr the desktop's Secret Service, so browsers, GNOME and KDE apps, git helpers and NetworkManager keep their passwords in kepr: one store, one lock, per-program rules and a log of who read what."
---

Almost everything on a Linux desktop that remembers a password talks to the
**freedesktop Secret Service** (`org.freedesktop.secrets` on the session
bus): Chrome and Firefox-based browsers, `libsecret` programs, Evolution,
NetworkManager's Wi-Fi and VPN passwords, `git-credential-libsecret`,
`secret-tool`. On GNOME that service is GNOME Keyring, on KDE it is KWallet.
`kepr secret-service` is a third implementation of the same API, backed by
the kepr store. Once it is the session's Secret Service, those programs need
nothing else, and kepr is the only place the passwords live.

## Why this is better than a second keyring

| | GNOME Keyring | kepr |
| --- | --- | --- |
| Lock | Follows your login. Once open, it stays open for the session. | Follows kepr's lock: the idle timer, suspend and screen lock, `kepr panic`. Unlocked by your login password (login unlock) or a dialog. |
| Who may read | Any process on your session bus, once it is unlocked. | A rule file, per program (by its path) and per operation (search, read, write), and a `sandboxed` test. First matching rule wins. |
| Record of use | None of its own. | A log of every call: which program, which item (label and id, never an attribute value or a secret), and the result. The kepr daemon's tamper-evident audit chain records each secret read too. |
| AI agents | A sandboxed or confined agent that can reach the bus can ask for everything. | `kepr agent run` hides the bus socket (and GNOME Keyring's own sockets) from the sandbox. A rule can refuse anything that still gets through. |
| At rest | One keyring file per collection. | One encrypted credential per item (AES-256-GCM under kepr's master key), or records in the vault image. Sealed by the TPM2, KMS or passphrase you chose for kepr. |
| Backup, sync | Copy the files. | `kepr export --encrypted`, multi-device sync and the vault image carry the items like any credential. |
| Other keys | Separate (SSH, certificates, API keys live elsewhere). | The same store as `kepr ssh-agent`, `kepr exec`, `kepr agent run`, git and docker helpers. |

It is not a hardened boundary against a program that can already read your
memory or ptrace your processes: a process running as you can also run
`kepr secret lookup`. What the policy and the log do is keep the unexpected
program out (a browser extension's helper, a build script, an agent) and
make the expected ones visible.

## Switch in two commands

```bash
kepr secret-service takeover        # copies the items, then wires the bus to kepr
kepr secret-service takeover --now  # ...and starts kepr in GNOME Keyring's place now
```

`takeover` does this, in this order, and stops at the first problem:

1. **Imports** the current provider's items into kepr. GNOME Keyring shows
   its own unlock dialog if it is locked; nothing is deleted from it. Items
   kepr already has (same collection and attributes) are kept. Try it first
   with `kepr secret-service import --dry-run`, which lists what would be
   copied and reads no secret.
2. Writes `~/.local/share/dbus-1/services/org.freedesktop.secrets.service`,
   so the session bus starts `kepr secret-service run` (through the
   `kepr-secret-service.service` user unit when the package installed it) the
   first time a program asks. The user directory outranks the system one.
3. **Masks** `gnome-keyring-daemon.socket` and `.service` in your user
   systemd, and hides its *secrets* autostart entry. Its SSH and PKCS#11
   components are left alone.
4. With `--now`, asks the running keyring (GNOME Keyring, KWallet) to exit
   and starts kepr in its place. Without it, log out and in once.

Everything it changed is listed in `~/.config/kepr/secret-service-takeover.json`;
**`kepr secret-service restore`** undoes exactly that. It never edits
`/etc`.

One thing it can only report: `pam_gnome_keyring.so` in a PAM service starts
GNOME Keyring *at login*, before kepr, and it would win the name.
`kepr secret-service status` names those services; ask root to take the lines
out (Debian and Ubuntu: `sudo pam-auth-update --remove gnome-keyring`).
Replace them with kepr's own login unlock: [Unlock at login](/docs/guides/login-unlock).

```text
kepr secret-service status
  ·  org.freedesktop.secrets is served by kepr (/usr/local/bin/kepr (pid 4121))
  ·  takeover: on (the bus starts kepr when a program asks; `kepr secret-service restore` undoes it)
  ·  policy: none (…/secret-service.toml would restrict programs); every program in this session may use it
```

## Locked, unlocked, and the first ask

Programs do not know about kepr's lock; the Secret Service API has its own
way to say "locked", and kepr uses it.

* **Unlocked:** everything works as in any keyring.
* **Locked after it was used (suspend, `kepr panic`, the idle timer):**
  searches still answer from a cache of *labels and attributes only* (never a
  secret), so a program can find its item; reading the secret fails with
  `IsLocked`. A program that calls `Unlock` gets a prompt, and kepr shows the
  passphrase dialog. kepr tells every program the moment the lock changes.
* **Locked when the first program asks** (login with login unlock off, a
  reboot): the first call that needs the store shows the dialog and waits for
  it (up to 20 seconds, as libsecret clients give up at 25). If it is
  dismissed or times out, the program gets `IsLocked`, and no dialog is shown
  again for ten seconds (by the first-ask path or by a program calling
  `Unlock`), so a program retrying in a loop does not flood you. A program the
  policy refuses everywhere gets neither a session nor a dialog.
* **The `session` collection** (programs' throw-away secrets) lives in memory
  and never needs kepr to be unlocked.

The dialog is `$KEPR_ASKPASS` (a program that prints the passphrase, like
`SSH_ASKPASS`), else `pinentry-gnome3` / `-qt` / `-gtk-2` / `pinentry`, else
`zenity`, else `kdialog`, and only when there is a display. With no display
and none of those, the error says to run `kepr unlock`. A wrong passphrase is
shown in the next try (three tries; the daemon's back-off applies).

Because a login unlocks kepr, the usual desktop case needs no dialog at all:
set the store passphrase to your login password and turn on login unlock.

## Who may use it: the policy file

`~/.config/kepr/secret-service.toml` (no file means every program of your
session may use it, as with other keyrings):

```toml
default = "allow"             # or "deny": then only `allow` rules pass

[[rule]]                      # nothing inside an agent sandbox reads secrets
sandboxed = true
op = "read"
action = "deny"

[[rule]]                      # a browser may store and search, not read them back
exe = "/usr/lib/chromium/chromium"
op = "read"
action = "deny"

[[rule]]
exe = "*/secret-tool"
op = "search"
action = "allow"
```

* `exe` is a glob on the calling program's path, read from `/proc` for the
  process the bus names (on every call, so a program that execs another one
  is judged by what it is now).
* A program whose entries in `/proc` kepr cannot read (one that made itself
  non-dumpable, so even its path is hidden) cannot be matched by any rule.
  Once the file holds a rule or `default = "deny"`, such a caller is refused
  everything; with no file, as with other keyrings, it is not.
* `op` is `search`, `read` (a secret), `write` (create, change, delete) or
  `all` (default).
* `sandboxed = true` matches a caller in another PID namespace (a container,
  or a `kepr agent run` sandbox).
* A broken file refuses everything, with the reason on stderr. `SIGHUP` (or
  `systemctl --user reload kepr-secret-service.service`) re-reads it.
* Check a rule without waiting for a program:
  `kepr secret-service policy check /usr/bin/secret-tool read`.

Flatpak apps do not talk to the Secret Service themselves: the desktop
portal fetches a per-app secret from it, so the caller the policy sees is the
portal backend, not the app.

## The log

```bash
kepr secret-service log -n 20
```

```text
2026-10-28 21:36:56 ok       GetSecret    /usr/bin/secret-tool (pid 12277)  YRTTTAM4…  Mail
2026-10-28 21:36:57 denied   GetSecret    /usr/bin/python3.13 (pid 12301) [sandboxed]  YRTTTAM4…  Mail
```

`$XDG_STATE_HOME/kepr/secret-service.log` (JSON lines, mode 0600, rotated at
1 MiB) names the program, the operation, the item's id and label and the
result. It never holds an attribute value (a user name or an account is
often one) or a secret. Reading a secret is also in kepr's own audit chain
(`journalctl -t kepr-daemon KEPR_OP=ss-secret`).

## Agents and the bus

An AI agent that can open the session bus can ask the Secret Service for
every password in it, whichever implementation runs. Inside `kepr agent run`'s
sandbox:

* the session bus socket (`$DBUS_SESSION_BUS_ADDRESS`'s path and
  `$XDG_RUNTIME_DIR/bus`) is covered with `/dev/null`, so a connection is
  refused;
* `$XDG_RUNTIME_DIR/keyring` and `/gcr` (GNOME Keyring's and gcr's own
  sockets, which include its SSH agent) are hidden like the kepr directories;
* `KEPR_SANDBOX_DBUS=allow kepr agent run …` keeps the bus reachable, for an
  agent that needs desktop services. The log marks its calls `[sandboxed]`
  and a `sandboxed = true` rule can refuse them.

A bus on an *abstract* socket (X11 `dbus-launch` sessions) is not a file; only
`--isolate-net` separates it.

## Working with the items yourself

`kepr secret` is `secret-tool` without libsecret, against the same store:

```bash
printf %s "$TOKEN" | kepr secret store --label "GitHub" service gh user me
kepr secret lookup service gh user me      # the secret, no trailing newline
kepr secret search --all service gh        # labels and attributes, not secrets
kepr secret ls                             # every item
kepr secret clear service gh user me
```

A second `store` with the same attributes replaces the item, as with
`secret-tool`. The items are ordinary encrypted credentials named `SSI_…` in
the folder `secret-service`, but `kepr ls` folds them into one line (`kepr ls
--folder secret-service` lists them) and `kepr get` refuses them: they are
read through the Secret Service or `kepr secret`, which apply the policy and
the log.

## What is not replaced

* **GNOME Keyring's older `org.gnome.keyring` API** and its **SSH agent**
  (`kepr ssh-agent` replaces the latter; `login-unlock on --ssh-agent`),
  **PKCS#11** module and certificate store.
* **KWallet's own API** (`org.kde.kwalletd`). Programs that use KWallet
  directly and not the Secret Service still use KWallet. Chromium and most
  current programs speak the Secret Service.
* **Secrets larger than 32 KiB**, more than 10,000 items or 64 collections.
* **Windows and macOS:** this is the freedesktop API. (macOS has its
  keychain integration for the master key; see the features reference.)

## If something goes wrong

| What you see | Why, and what to do |
| --- | --- |
| `org.freedesktop.secrets is already owned by …` | Another keyring took the name first. `kepr secret-service status` names it and any PAM line that starts it; `takeover --now` stops a running GNOME Keyring or KWallet. |
| Programs say the keyring is locked, no dialog appears | No display, or no dialog program: install `pinentry-gnome3` or `zenity`, set `KEPR_ASKPASS`, or run `kepr unlock`. The server prints the reason. |
| `cannot ask kepr … answering as locked` on stderr | The kepr daemon is not reachable. `kepr status` shows why; it is started on demand in user mode. |
| A program was refused | `kepr secret-service log` shows `denied`; `kepr secret-service policy` shows the rules. |
| You want GNOME Keyring back | `kepr secret-service restore`, then log out and in. Your kepr items stay in kepr. |

`tests/secret_service_e2e.sh` runs all of this against a real session bus:
`secret-tool`, `python3-secretstorage` (the encrypted session), a locked and a
cold-started store, the policy, takeover, restore, import between two kepr
profiles, and a sandboxed agent. It needs `dbus-daemon`, `secret-tool` and a
built tree, and touches only a temporary home.
