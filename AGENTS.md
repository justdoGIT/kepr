# CLAUDE.md

## Build / Install / Run

- `cargo build --release` — produces the root-package binaries (`kepr`, `kepr-daemon`, `docker-credential-kepr`, `git-credential-kepr`) in `target/release/`; `cargo build --release --workspace` adds `kepr-gate`, `kepr-eso-provider` and `kepr-relay` (`-p kepr-gate` etc. for one of them). Workspace contains the bins plus the `kepr-core` library member at `crates/kepr-core/`, the `kepr-gate` agent proxy at `crates/kepr-gate/` (its own crate so hyper and tokio never reach the daemon; the daemon links rustls only through `ureq`, for the opt-in key-service sealers in `daemon_seal/http.rs`), `crates/kepr-eso-provider/` and the optional share-link relay at `crates/kepr-relay/` (std only, no dependencies).
- `cargo build --release --features fips,aws-lc-rs/fips --bin kepr-daemon` and `cargo build --release -p kepr-gate --features fips,rustls/fips` — FIPS mode (T7.16): the daemon's AES-256-GCM / SHA-256 and the gate's rustls + session CA on the FIPS 140-3 validated AWS-LC module (needs Go and CMake; CI's `fips` job runs the same with `-- --include-ignored` tests). `--features fips` alone links AWS-LC's ordinary build (what `--all-features` compiles); `kepr status` claims FIPS only when the validated module passed its self tests.
- `cargo clippy --workspace --all-targets --all-features -- -D warnings` — lint everything; zero warnings enforced.
- `cargo test --workspace` — fast, hermetic unit tests across the buckets: `kepr` (CLI modules incl. every `src/cli_<batch>/`), `kepr-daemon` (handler / store / crypto-error / rate-limit / umask / audit, and every `src/daemon_<batch>/`), `kepr-core` (framing / generate / protocol and the shared batch modules), `kepr-gate`, `kepr-relay` and `kepr-eso-provider`; plus the integration tests in `tests/`: `vault_image.rs` (`KEPR_STORE=image`), `records_cli.rs`, `bundle_cli.rs` and `sync_cli.rs` each start user-mode daemons in temp HOMEs and drive the real `kepr` binary; `file_size_limit.rs` (350-LOC rule) and `systemd_unit.rs` (unit hardening) pin repo rules. `store.rs` lives in the daemon bin only — it's not `mod`-included from `main.rs`, so its tests only compile under the daemon target.
- Non-Rust parts, as CI runs them: `python3 -m unittest discover -s sdk/python/tests` and `-s integrations/ansible/tests`; `node --test test/*.test.js` in `sdk/node` and `integrations/vscode`; `ruby test/test_kepr.rb` in `sdk/ruby`; `bash sdk/java/test.sh`; `test -z "$(gofmt -l .)" && go vet ./... && go test ./...` in `sdk/go`, `integrations/csi-provider` and `integrations/terraform-provider-kepr`; `bash integrations/ci/test_kepr_ci.sh` and `bash integrations/podman/test_kepr_podman_driver.sh` (both shellchecked); `actionlint` over `.github/workflows/` (the example workflow `kepr-action-example.yml` lints the Action's inputs).
- `cd crates/kepr-core && cargo +nightly fuzz run frame_fuzz -- -max_total_time=60` — fuzz `read_frame` for 60 s. Requires `rustup install nightly` and `cargo install cargo-fuzz` once. Targets live at `crates/kepr-core/fuzz/fuzz_targets/`; corpus and crash artifacts are gitignored.
- `cd crates/kepr-core && cargo +nightly fuzz run protocol_fuzz -- -max_total_time=60` — same idea against `serde_json::from_slice::<Request>`.
- `./tests/e2e.sh` — end-to-end against the installed daemon. Requires `kepr.service` running, the invoking user in the `kepr` group, and `jq`. Cases 7 (error sanitization), 8 (audit log), 14 (on-disk magic), 15 (master-key perms) and 16 (legacy-cred sweep on daemon restart) skip gracefully without sudo / journal-read access / `systemctl`. All creds it creates use the prefix `E2E_<pid>_<epoch>_` and are cleaned up on exit.
- `./tests/agent_e2e.sh` — self-contained "malicious agent" test for sealed credentials and kepr-gate: starts its own user-mode daemon in a temp HOME using `target/debug` binaries (`cargo build --workspace` first; `KEPR_BIN_DIR` overrides). Run it as a non-root user for the full check; root skips the gate memory/environ checks. It also checks `kepr agent logs`, sealed credentials staying sealed across `set` / `rotate --hook` / `restore`, and the sandbox's Landlock rules in `KEPR_LANDLOCK=strict` (store dir denied) and default mode (a file in `$HOME` can be replaced by rename).
- `kepr-relay [--listen ADDR] [--max-ttl SECS] [--rate PER_MINUTE]` — optional relay for one-time share links (T6.04); defaults 127.0.0.1:8737, 7 days, 60 requests/min per address; plain HTTP, put it behind a TLS reverse proxy.
- `./install.sh` — full install: builds, creates `kepr` system group, installs binaries to `/usr/local/bin/kepr` and `/usr/local/sbin/kepr-daemon`, installs and starts the systemd service.
- `sudo systemctl restart kepr.service` — reload the daemon after rebuilding. `sudo systemctl reload kepr.service` (SIGHUP, `ExecReload`) or `kepr policy reload` re-reads `policy.toml` (T6.11) without a restart.
- `journalctl -t kepr-daemon -f` — follow the audit log (structured fields: `KEPR_OP`, `KEPR_NAME`, `KEPR_UID`, `KEPR_USER`, `KEPR_RESULT`).

## Architecture

Four binaries share the root crate (see `Cargo.toml` `[[bin]]` entries; `git-credential-kepr` is the fourth, `src/git_helper.rs`), plus three workspace crates with their own binaries: `kepr-gate` (agent proxy, `crates/kepr-gate/`), `kepr-eso-provider` (`crates/kepr-eso-provider/`) and `kepr-relay` (optional one-time share-link relay, `crates/kepr-relay/`). SDKs and integrations outside the Cargo workspace live in `sdk/` and `integrations/` (last entry of the module split):

- `kepr` (`src/main.rs`) — unprivileged CLI. Never invokes the encryption backend directly, never needs root/sudo. Connects to the daemon over a Unix socket and exchanges JSON.
- `kepr-daemon` (`src/daemon.rs`) — root systemd service. Owns all encrypt/decrypt/delete operations and audit logging. Dispatches connections to a bounded worker pool (`daemon_pool.rs`) to cap concurrency and prevent thread exhaustion.
- `docker-credential-kepr` (`src/docker_helper.rs`) — Phase 1 ε. Implements the docker credential-helper protocol (get/store/erase/list over stdin/stdout JSON). Wraps `client::send_request`. Same socket, same `kepr` group gate as the main CLI.

**Socket contract:** `/run/kepr/kepr.sock`, owned `root:kepr 0660`. Any user in the `kepr` group can connect; the daemon reads the peer uid via `SO_PEERCRED` and uses *that* uid for namespacing — never trust a uid from the request body.

**Per-user namespacing:** credentials live in the shared `/etc/credstore.encrypted/` directory but are named `kepr-<uid>-<lowercased-name>` (see `src/store.rs`). `list_for_uid` filters by this prefix so users only ever see their own credentials. This is the *only* access-control boundary for reads — there is no per-file unix permission separation between users. With `KEPR_STORE=image` (T4.06) the same `kepr-<uid>-<name>` names key records inside one vault image (`store_dir()/vault.img`, `src/daemon_vault/`) instead of files, and `store::list_for_uid` / `cred_exists` read the image; the per-file store stays the default.

**Sealed credentials:** `.meta` `sealed: true` + `bindings`. `Get` refuses them (generic "credential unavailable"); only a daemon-spawned gate can resolve them, and only for a bound host. Never add another path that returns a sealed value. The same holds for SSH keys (`.meta` `ssh`) and history slots: history only ever lists metadata or restores a value back into the store. The one place earlier values leave the daemon is the passphrase-encrypted bundle export (T6.09, `daemon_syncx/export.rs`): it carries a credential's history only when that credential is itself exported (`CredMeta::gated` is `None` and the policy and `get`'s precheck pass), and never a version saved while sealed (`daemon_history::export_versions`); keep it that way. Every path that compares or copies values (dupes, search, diff, health, breach checks, export, sync, folder bundles) asks `CredMeta::gated` first. **The one documented exception** is the recovery kit (`daemon_recovery.rs`): `RecoveryKitCreate` returns Shamir shares of the master key, and only on a passphrase-protected store, after re-checking the passphrase, for the owner (root in system mode), with no agent gate running, audited as `recovery-kit`. `RecoveryRestore` must prove the rebuilt key against the credential files and refuses while the loaded key still works (a locked store, i.e. a forgotten passphrase, is the case it exists for). Don't widen either path.

**Recovery words (T4.10)** are the same exception in another form, and stronger: `RecoveryWordsCreate` (`daemon_seal/recovery.rs`) returns the master key itself as 24 words (not shares), behind exactly the recovery kit's fences (passphrase-protected store, passphrase re-checked, owner / root only, no agent gate running; shared helpers in `daemon_recovery.rs`), audited `recovery-words`; `RecoveryWordsRestore` must prove the key against the credential files like `RecoveryRestore`, then re-locks the store under a new passphrase, audited `recovery-restore`. Anyone holding the words can decrypt the store files. Don't widen it.

**Break-glass (T6.07)** is the second documented exception and the only path that returns a sealed value: `BreakGlass` (`daemon_sharing/breakglass.rs`) needs k recovery-kit shares that rebuild exactly the running key (constant-time compare; one error message for any mistake, never which share), works only on sealed credentials (never SSH or share keys), is refused while any agent gate of any user runs, writes `.meta` `must_rotate` before decrypting (the next `set` clears it; `kepr list` shows it), and is audited as `break-glass`. It adds no capability (k shares plus the credential files already decrypt everything offline); it makes that access loud. Don't widen it.

**Escrow (T6.14)** is the third: `EscrowEnable` (`daemon_sharing/escrow.rs`) wraps the master key to an administrator's share key in `escrow.bin`, fenced exactly like `RecoveryKitCreate` (passphrase-protected store, passphrase re-checked, owner / root only, no agent gate running, audited `escrow-enable`); `EscrowOpen` returns the key only as a 2-of-2 recovery kit, only to the holder of that admin share key, with none of their gates running, audited `escrow-open`. `kepr status` shows when escrow is on. Don't widen it.

**Recovery key (T12.31)** is the fourth, for stores with no passphrase: `RecoveryKeyEnrol` (`daemon_seal/recovery_key.rs`) keeps the running master key wrapped under a 32-byte recovery key in `master.key.recovery` (the `kepr_pw1` Argon2id envelope). The key is made by the CLI and sent as 24 words; the daemon never makes or returns key material, and the reply is only the fingerprint. Fences: owner / root only, no agent gate of any user running, refused on a passphrase store (that one has the recovery kit and words), the store unlocked; replacing an enrolled key needs its words, which must open the old envelope to the running key (one error for any mistake); audited `recovery-key-enrol`. `RecoveryKeyUnlock` (T12.32) is the only path that opens the envelope: only while the sealed key did not unseal at start-up (`daemon_seal/startup.rs` starts the daemon locked then, and when the key file is gone, instead of exiting or making a new key), under the same fences (owner / root, no gate, not a passphrase store); wrong words get one error after a 1 s pause; the recovered key must open at least one credential file or the vault image before it is installed; it is then sealed again for the current boot state over the key file, audited `recovery-unlock`. Anyone holding the words and that file can decrypt the store files. Don't widen it.

**P2–P11 ticket batches (2026-10-05).** New work from `docs/content/docs/agent-vault-tickets.mdx` (*Open work*) is grouped into batches (vault, seal, store, records, share, sync, policy, gate, aws, eco, platform, session). Each batch registers in fixed places, each under its own `// batch: NAME` marker so parallel branches merge cleanly: an untagged variant wrapping its own request enum (`crates/kepr-core/src/protocol_<batch>.rs`) at the end of `Request` / `Response`, an arm in `daemon_extra.rs`, a `mod daemon_<batch>;` line in `daemon.rs` (directory module), a `mod cli_<batch>;` line in `main.rs` registered in `cli_more.rs` (verbs + help), and new `.meta` fields in `cred_meta.rs`. `daemon_dispatch.rs` holds the main request match (moved out of `daemon.rs`). Four batches use a different name where the plain one was taken: records → `protocol_records.rs` / `Request::Records` / `daemon_recordsx/` / `cli_recordsx/`; share → `protocol_sharing.rs` / `Request::Sharing` / `daemon_sharing/` / `cli_sharing/`; sync → `protocol_syncx.rs` / `Request::Syncx` / `daemon_syncx/` / `cli_syncx/`; gate → `protocol_gatex.rs` / `Request::Gatex` / `daemon_gatex/` / `cli_gatex/`. Shared non-wire modules a batch needs in `kepr-core` go under the same marker in `lib.rs`; flags a batch adds to core verbs are parsed through its `FLAGS` in `cli_args.rs`.

When adding a new command, touch all three layers: add a variant to `Request`/`Response` in `crates/kepr-core/src/protocol.rs`, a client function in `cli_cmds.rs` (with transport via `client.rs`), and a handler + audit call in `daemon_handlers.rs`. A command that belongs to a batch goes in that batch's `protocol_<batch>.rs` enum, `cli_<batch>/` and `daemon_<batch>/` instead.

## Workflow

- **TDD by default.** For new features and bug fixes: write a failing test first (RED), confirm the failure mode is what you expect, implement the minimal code to make it pass (GREEN), then refactor with the suite as a safety net. Use the `verify-first` skill to lock down the success command + failure mode + rollback *before* any code change. The exception is pure mechanical refactors that preserve all external behaviour (file moves, crate splits) — there the existing suite is the contract.
- **Self-review every PR.** After `gh pr create`, before asking for merge, walk the diff yourself: re-read changed files, check error-message hygiene, look for missed test coverage, confirm the PR description matches the code, and consider edge cases the tests do not yet exercise. Post a self-review summary as a PR comment that names the riskiest assumption you made. Do this even when Codex / Copilot say nothing or 👍 — automated reviewers catch a slice; the rest you have to find before merge. Skill: `pr-review-lean`.
- **350 LOC per file.** No `.rs` file under `src/` or `crates/*/src/` may exceed 350 lines of production code. "Production" excludes the `#[cfg(test)] mod tests { … }` block at the bottom of the file (test count is unbounded; `super::*` access keeps tests next to the code). Pinned by `tests/file_size_limit.rs` — adding a new file >350 LOC fails the test; growing an allowlisted file beyond its pinned ceiling fails the test. Refactor pressure: when a module trips the limit, split by *concept* not by line count (two 200-line files that just depend on each other don't fix anything). Existing violators are grandfathered in `ALLOWLIST` with a refactor backlog.

## Conventions that matter

- **Never log secret values.** Audit entries include op/name/uid/user/result only — see `DOCS.md` §3.3.
- **Hide the encryption backend from users.** Error strings never carry the sealing tool's name, flags or stderr (the master-key sealer reports only "seal/unseal failed"); `crypto::sanitize_lookup_error` collapses not-found/undecryptable into one message; the systemd unit uses a neutral `SyslogIdentifier`. Preserve this stance in any new code, error strings, and docs — refer to it generically as "the credential backend."
- **Validate names in the daemon**, not just the client. `store::validate_name` (A-Z/0-9/underscore, ≤128 chars) is the boundary against path traversal; every handler that takes a `name` must call it.
- **Secrets use `ZeroString`** (from `generate.rs`) so memory is wiped on drop. Don't convert to plain `String` except at the socket boundary.
- **Names are uppercased** on the client (`cli_args.rs` / `cli_cmds.rs`) and re-uppercased in the daemon. The lowercase form only exists inside the on-disk cred name.
