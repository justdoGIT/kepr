description: "Give AI coding agents (Claude Code, Codex, grok-cli, Aider, oh-my-pi, Grok Build) API keys they can use but never see."

## The idea

Paste a key once. From then on an agent can **use** it but never **hold** it:

- the key is stored **sealed** (write-only): `kepr get` refuses it, and so
  does every other API;
- the agent receives a worthless **placeholder** (`kepr-ph-…`) and a local
  base URL;
- **kepr-gate**, a local proxy started by the kepr daemon, swaps the
  placeholder for the real key on the wire, and only toward the host the key
  is bound to (`api.anthropic.com` for an Anthropic key, and so on).

The real key is never in the agent's environment, files, inherited file
descriptors or memory.

## Quick start

```bash
kepr agent add ANTHROPIC_API_KEY     # paste the key (input hidden)
kepr agent run claude                # starts Claude Code with a placeholder
```

The provider is detected from the key's prefix (`sk-ant-`, `xai-`, `sk-`,
`sk-or-`, `gsk_`, `AIza`). For keys without a recognisable prefix, say which
provider it belongs to:

```bash
kepr agent add MISTRAL_API_KEY --for mistral
kepr agent add DEEPSEEK_API_KEY --for deepseek
```

Supported providers: anthropic, openai, xai, google, mistral, deepseek,
groq, openrouter.

## Already have keys in `.env` or your shell profile?

```bash
kepr agent adopt                 # lists keys found in .env, .envrc, ~/.bashrc, ~/.zshrc …
kepr agent adopt --yes           # imports them as sealed keys
kepr agent adopt --yes --remove  # …and deletes the plaintext lines
```

Values are never printed. A name found with different values in two
places, or already stored in kepr, is skipped rather than overwritten.
`--remove` keeps no plaintext backup, on purpose.

## Harnesses

| Harness | Command | Key it uses |
| --- | --- | --- |
| Claude Code | `kepr agent run claude` | `ANTHROPIC_API_KEY` |
| OpenAI Codex CLI | `kepr agent run codex` | `OPENAI_API_KEY` |
| grok-cli | `kepr agent run grok-cli` | `XAI_API_KEY` |
| Aider (OpenAI path) | `kepr agent run aider` | `OPENAI_API_KEY` |
| oh-my-pi | `kepr agent install omp` once, then `kepr agent run omp` | `ANTHROPIC_API_KEY` |
| Grok Build | `kepr agent install grok` once, then `kepr agent run grok` | `XAI_API_KEY` |

`kepr agent install` edits the harness's own config file
(`~/.omp/agent/models.yml`, `~/.grok/config.toml`) to point at the gate on
port 7878, after writing a timestamped backup. It also installs kepr's
plugin for that harness (below). Running it twice changes nothing.

### Plugins for omp and Grok Build

`kepr agent install omp|grok` installs a plugin that makes the harness
itself keep secrets out of the conversation. Both plugins ask
`kepr hook` for their decisions, so the rules are the same in each.

| What it does | omp | Grok Build |
| --- | --- | --- |
| Sends provider calls through the gate with the placeholder (no config edit needed) | yes (`anthropic`, `openai`, `xai`) | via `config.toml` |
| Refuses tool calls that would print a stored value (`kepr get`, `env`, `exec`, `totp`, `inject`, `copy`, `record`, `recovery-kit`, `share`, `sync-push`) | yes | yes |
| Refuses tool calls that contain a real key (a command, or file content) | yes | yes |
| Refuses a prompt with a pasted key, before it reaches the model | interactive sessions | yes |
| Removes keys from user messages before every model request | yes (covers `omp -p` and RPC) | – |
| Tells the model that its keys are placeholders | system prompt | a `kepr` skill |
| `kepr mcp` as an MCP server | – | yes |
| Status command | `/kepr` | – |

- **Where they go:** the omp extension goes into `~/.omp/agent/extensions/kepr/`,
  where omp finds it on its own. The Grok Build plugin's source goes into
  `~/.local/share/kepr/plugins/grok/kepr/`, and kepr registers it with
  `grok plugin install … --trust`, or `grok plugin update kepr` after an
  upgrade. If `grok` isn't on your `PATH`, kepr prints the command to run.
- **What they don't do:** the plugins are a guard for sessions that run
  without the sandbox. The boundary is still the gate and the sandbox: under
  `kepr agent run`, the agent only ever holds placeholders, and the kepr
  socket is hidden from it.
- **Tested against:** omp 18.6.0 and Grok Build 1.0.46.

Pass your own command line after `--`:

```bash
kepr agent run claude -- claude --model claude-sonnet-5-5
```

Any real key already exported in your shell (for example
`ANTHROPIC_API_KEY=sk-ant-…`) is removed from the agent's environment.

## The sandbox

`kepr agent run` starts the harness in its own user, mount and PID
namespaces (when the kernel allows it):

- the credential store, the daemon's state (master key, audit log) and the
  daemon socket are covered by empty read-only directories;
- only the session's own processes are visible, so other processes'
  `/proc/PID/root` can't be used to reach the host filesystem;
- the harness has no capabilities, `no_new_privs`, and a seccomp filter
  that denies `ptrace`, `process_vm_readv/writev`, `bpf`,
  `perf_event_open`, kexec and module loading (debuggers don't work inside
  a session).

Networking stays as normal, so package installs work. Add `--isolate-net`
to give the session nothing but loopback: the gate is still reachable
(connections are relayed to it), but nothing else is.

```bash
kepr agent run claude                 # sandboxed (default when available)
kepr agent run claude --isolate-net   # sandboxed, gate-only network
kepr agent run claude --strict-sandbox  # refuse to run unsandboxed
kepr agent run claude --no-sandbox    # opt out
```

If the kernel refuses unprivileged user namespaces (Ubuntu 24.04+ restricts
them through AppArmor), kepr warns and runs unsandboxed; `install.sh`
installs an AppArmor profile that allows it for `/usr/local/bin/kepr`.
`kepr doctor` shows what your kernel supports.

## Asking before a key is used

```bash
kepr agent add ANTHROPIC_API_KEY --requires-consent
```

Before the daemon hands such a key to a gate, polkit asks you to approve
the agent process (the desktop's authentication dialog). No answer within
60 seconds, or no polkit agent, means no. One approval covers the gate's
cache window (5 minutes, or until the key changes).

## MCP: `kepr mcp`

For agent platforms that talk to tools over MCP, `kepr mcp` is a stdio MCP
server with these tools:

- `list_secrets`: names of your sealed keys and the hosts they're bound to;
- `call_api`: an HTTP call to a provider API (`provider`, `method`, `path`,
  optional `body` and `headers`). The call goes through a gate session, so
  the key is injected by kepr, prompt DLP applies, and the model never sees
  the key.
- `db_query`: one SQL statement (`target`, `sql`) on a sealed PostgreSQL
  login (`kepr agent add-db`), through the gate's database proxy: the gate
  logs in, the model never gets the password.
- `ssh_run`: a command (`host`, `cmd`) over ssh, signed with a key that
  stays in the daemon (`kepr ssh generate`). Only for hosts you list with
  `--ssh`; ssh runs in batch mode, so the host must be in `known_hosts`.

```bash
kepr mcp --read-only --ssh deploy@web1 \
  --context "APP_DB=Analytics replica: tables orders, users" \
  --context "deploy@web1=Ubuntu 24.04, app in /srv/app"
```

`--read-only` runs every statement read-only (`SET
default_transaction_read_only = on`, inside a `READ ONLY` transaction): a
guard against mistakes, not a permission boundary, so give the login a
read-only role for that. `--context` attaches an `ai_context` note that is
returned with each result for that target.

No tool returns a secret value, and key-shaped strings in results are
masked. Example client entry:

```json
{ "mcpServers": { "kepr": { "command": "kepr", "args": ["mcp"] } } }
```

## Tools the agent runs: `gh`, `curl`, SDKs

Model calls use the gate's base URL. Tools that talk to a host by name can't,
so every session also gets the gate as its HTTPS proxy:

```bash
kepr agent add GITHUB_TOKEN          # paste a ghp_/github_pat_ token: bound to api.github.com
kepr agent run claude                # GH_TOKEN / GITHUB_TOKEN are placeholders now
```

- **Bound hosts:** for a host a sealed key is bound to (here
  `api.github.com`), the gate terminates TLS with a CA made for this
  session. It swaps the placeholder for the real key and re-encrypts to the
  real host, trusting only its compiled-in roots.
- **The CA:** it lives only in the gate's memory, lasts 24 hours, and is
  name-constrained to the session's bound hosts, so its key can't sign a
  certificate for any other site.
- **How tools trust it:** the harness gets the CA through `SSL_CERT_FILE`,
  `REQUESTS_CA_BUNDLE`, `CURL_CA_BUNDLE`, `GIT_SSL_CAINFO` and
  `NODE_EXTRA_CA_CERTS`. Those point to the system bundle plus the session
  CA, so other HTTPS keeps working.
- **Real tokens in your shell:** a `GH_TOKEN` or `GITHUB_TOKEN` you exported
  is replaced by the placeholder and never reaches the agent.
- **Other hosts:** they are tunnelled unchanged. With `--isolate-net` they
  are refused, so the agent reaches only the providers its keys are bound
  to.

## Databases

```bash
kepr agent add-db PROD --url postgres://app@db.internal:5432/prod   # asks for the password
kepr agent run claude
```

- **What the agent gets:** `DATABASE_URL` and `PGHOST`/`PGPORT`/`PGUSER`/
  `PGPASSWORD`/`PGDATABASE`, pointing at a local gate port, with the
  session placeholder as the password. With several databases, each one gets
  `KEPR_DB_<NAME>_URL`.
- **What the gate does:** it checks the placeholder, then logs in to the
  real server with the sealed login using SCRAM-SHA-256 or cleartext (MD5 is
  refused). From then on it relays the session unchanged.
- **TLS to the server:** it's verified against public roots by default.
  Pass `--ca FILE` for a managed database's own CA, or `--sslmode disable`
  to allow plaintext, for local databases only.
- **The login itself:** the user name, database and password stay sealed,
  and `kepr get PROD` is refused. The agent can run queries as that user but
  can't take the password anywhere.

### Rotating the password

```bash
kepr agent rotate-db PROD
```

- **How it works:** the daemon adds a random 48-character password to the
  sealed record as pending. A gate started for this database logs in with
  the current password and runs `ALTER ROLE CURRENT_USER PASSWORD` with a
  SCRAM verifier, so the new password never appears in SQL text or server
  logs. The daemon then makes the pending password the current one.
- **Who sees it:** nobody. Neither the old nor the new password reaches
  the CLI, the terminal or the agent.
- **If it's interrupted:** the pending password is kept. Running the
  command again finishes the job, even when the server already has the new
  password. `kepr agent rotate-db PROD --abort` drops a pending password.
- **What the role needs:** it must be allowed to change its own password,
  which PostgreSQL allows by default.

## Spending and rate limits

```bash
kepr agent run claude --max-requests 500 --max-tokens 2000000 --rate 30
```

The gate enforces these per session:

- `--max-requests`: total forwarded requests.
- `--max-tokens`: total tokens, counted from the provider's own `usage`
  fields as responses stream back. A response that crosses the limit
  completes; the next request is refused.
- `--rate`: requests per rolling minute.

When a cap is reached, the agent gets `403` with error type `kepr_limit` and
a message naming the limit. That stops it rather than leaving it to retry.
The rate limit answers `429` with `Retry-After`. Refusals appear in the gate
journal as `"blocked":"limit"`.

## Emergency stop

```bash
kepr panic
```

Stops every running gate for your user (their cached keys die with them)
and, if the store is passphrase-protected, locks it until `kepr unlock`.

The user-mode daemon also does this by itself when the machine suspends or
the screen locks. That keeps keys out of RAM while a laptop sleeps. It
follows logind through `gdbus`; `kepr doctor` reports whether it can. Turn
it off with `KEPR_LOCK_ON_SLEEP=0`.

## When a key leaks

```bash
kepr leaked ANTHROPIC_API_KEY
```

This command:

1. Stops every agent session for your user, along with their cached copies.
2. Deletes the credential and its saved history.
3. Records a `leak-incident` entry in the audit chain.
4. Tells you where to revoke the key at the provider; kepr can't revoke it
   for you.

Then store the new key with `kepr agent add`. To see where the old one was
used: `journalctl -t kepr-daemon KEPR_NAME=ANTHROPIC_API_KEY`, or
`kepr usage`.

## SSH keys the agent can use but never read

```bash
kepr ssh generate DEPLOY_KEY            # or: kepr ssh import DEPLOY_KEY ~/.ssh/id_ed25519
kepr ssh list                           # authorized_keys lines to install on servers
eval "$(kepr ssh-agent)"                # sets SSH_AUTH_SOCK for ssh and git
```

The Ed25519 private key stays in the daemon. `kepr get` refuses it, and the
agent socket only lists keys and signs. Requests to add, export or remove
keys fail. Add `--requires-consent` to get a prompt before each signature.
Encrypted key files must be decrypted (on a copy) before import.

## What the gate enforces

- **Placeholder check:** a request without this session's placeholder gets
  `401`. Placeholders are HMAC-bound to one session and useless elsewhere.
- **Destination binding:** the daemon releases a sealed key to the gate only
  for a host in its bindings, and the gate only talks to the provider's real
  host over TLS with compiled-in public roots (it ignores proxy and CA
  settings from the environment, which the agent could control).
- **Prompt DLP:** a request whose body contains a stored key (or something
  shaped like an API key) is **blocked** with `403`, and the agent is told
  why, e.g. `kepr blocked this request: it contains the stored secret
  ANTHROPIC_API_KEY. Remove it and retry.` Nothing is redacted silently.
- **Lifetime:** the gate exits, and wipes its cache, when the agent exits.
  Any `set`, `delete` or expiry in the store invalidates cached keys at
  once, so `kepr agent revoke` takes effect immediately.
- **Journal:** one metadata-only line per request on the daemon's stderr
  (provider, method, path without query, status, sizes, time). Never
  headers or bodies.

## Managing keys

```bash
kepr agent ls                        # sealed keys and their bound hosts
kepr agent revoke ANTHROPIC_API_KEY  # delete (asks for confirmation)
kepr history ANTHROPIC_API_KEY       # previous values kept (no values shown)
kepr restore ANTHROPIC_API_KEY --version 1   # undo the last change
kepr usage --days 30                 # uses, refusals, last use; never-used keys
```

A sealed key can't be unsealed. To change its value or provider, run
`kepr agent add` again.

## Commands you run yourself: `kepr exec --mask`

For your own scripts that need a readable key, `--mask` replaces stored
values in the command's output with `****`, so a script that echoes a key
can't leak it into a log or an agent's context:

```bash
kepr exec --env DEPLOY_TOKEN --mask -- ./deploy.sh
```

## Current limits

- **System mode needs `kepr-gate.service`.** The root daemon forbids
  itself network sockets, so its agent sessions run in this service, under
  an unprivileged dynamic user with no access to the credential store.
  `install.sh` enables it. The daemon passes each session's channel to it
  over a root-only socket. `kepr panic` reaches these gates too.
- **TLS-inspecting networks:** if your network intercepts TLS with its own
  certificate authority, the gate refuses the connection, because it trusts
  only public roots. A root-owned CA setting is planned.
- **Root:** an attacker with root on the running machine can read any
  process's memory. Run agents as your normal user.
- **Use, not read:** an agent can still make calls with the key toward its
  bound provider. It cannot copy it or send it anywhere else.
- **FIDO2:** sealed keys can't require a FIDO2 touch yet (use
  `--requires-consent`).

`kepr protect-agent` is retired: it now explains why and exits.

## Auditing

```bash
journalctl -t kepr-daemon KEPR_OP=resolve
```

Every release of a sealed key to the gate is logged as `op=resolve`; every
refused `get` of a sealed key as `result=fail: sealed`. `kepr usage` sums
these per key from the hash-chained audit log.

## Binding the store to this machine

Set `KEPR_MASTER_KEY_SEAL=tpm2` (or `host+tpm2`) in the service
environment, optionally with `KEPR_TPM2_PCRS=7`. The master key is then
sealed to this machine's TPM, so a copied disk can't be decrypted
elsewhere, and with PCRs, not after the boot chain changes either. The
commented lines in `systemd/kepr.service` show the setting.
